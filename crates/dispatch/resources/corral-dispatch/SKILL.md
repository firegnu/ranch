# corral-dispatch：当主控，按任务文件分派、审查、收尾

开 agent、送话、等待、取回复、关掉，一律按 corral 技能做。本技能只管：怎么拆、怎么交代、交给谁用哪一档、怎么审、怎么收尾。

安装技能不使所有项目自动委派。

## 先确认三件事

1. **你是主控。** 你如果是被委派的 agent（任务文件里写明了你的身份），不要用本技能：照任务文件做，也不要再开别的 agent。
2. **corral 能用。** 按 corral 技能的自检做，你自己也必须是用 corral 开的。
3. **读项目的 AGENTS.md**（或 CLAUDE.md），找下面这些项目规矩。和本技能冲突时，以项目规矩为准；没写的问用户一次，并参照本技能同目录的 `项目AGENTS模板.md`，建议补进 AGENTS.md：
   - agent 名字前缀；任务文件放哪；按什么拆（里程碑、分支、worktree 放哪）
   - 怎么合并（本地合并还是开 PR）、推不推送
   - 私有数据在哪、哪些不能读、哪些操作花钱

   交给哪家、几档、要不要交叉审查，一般不写在 AGENTS.md 里，按第 3 节定，不用问用户。项目确实写了（包括「不用路由」），照它的。

## 1. 拆任务

- 派新活之前，先确认上一件已经收尾：worktree 和分支清掉了，或者写明为什么留着。没收尾不派新活。
- **刚接手、或者不确定还开着谁时，跑一次 `corral ls` 核对**：cwd 指的目录已经不存在的，是上一任主控留下的残骸——工作目录没了，那个 agent 干不了活。名字后面的数字后缀不是判据（`--unique` 第一次开就补 `-1`），判据只有 cwd 在不在。列给用户问关不关，**不要自己关**：你分不清哪个是用户自己在用的。

  ```sh
  corral ls | python3 -c 'import json,os,sys;[print(a["name"],a["cwd"]) for a in json.load(sys.stdin)["agents"] if not os.path.isdir(a["cwd"])]'
  ```
- 架构级的决定（数据模型、模块边界、里程碑怎么划）不要自己拍板：已经有方案或开发计划的，照它拆；没有的，先问用户要不要先定架构，等他给了结论再拆。
- 一件事、一个 agent、一个分支、一个 git worktree。一个 agent 一次只做一件事。
- 地基（数据模型、公共约定）先串行做完，再按需并行，不要一开始就开很多个。
- 并行之前：
  - 把接口约定写进任务文件（字段名照写），两边照同一份约定做；
  - 查文件范围：两个任务要改同一批文件，就不并行，改成先后；
  - 指定谁负责集成（例如后端合并后，由前端 agent 接真实接口验收）。
  - **有集成关系的两半不分别合并**：两个 worktree 都留着，集成验过再一起合并、一起清、一起关。先合并的那半 worktree 一清，它的 agent 就废了，集成时发现要返工只能重开。
- 拿不准的设计问题，可以分别问一个 Claude Code 和一个 Codex，把分歧列给用户，不要自己挑一个就开工。

## 2. 写任务文件

开出来的 agent 看不到你和用户的对话，所以每次委派都先写任务文件。**任务书只写做成什么、范围、怎么算做完，不写怎么证明**：在验证预算内怎么验，由对方自己判断。任务书写得越重，对方做得越重。

分两步写：先写正文（要做的、范围、不要做、验收），这些和交给谁无关；正文写好了，再照第 3 节问路由、定交给谁，最后补上开头的「交给谁、几档」、路由那一行和「怎么算做完」里的验证预算。不要先问路由再按结果写正文：路由先说「轻」，正文就容易写薄。

模板。没有内容的节整节删掉，不要为了填满而写：

```markdown
# 任务：<一句话>

<日期>，<你的名字> 交给 <对方名字>（<哪家 agent>，<档：模型 / 强度>）。
路由：<见第 3 节的记录格式>
类型：<见本节「定类型」>
依据：<一句话：本轮做什么、不做什么>
提示：<这一类的提示，照「定类型」表里的原文；类型是「其他」就删掉这一行>
你是被委派的 agent：照本文件做，不要再开别的 agent。

## 先读
- <和这件事直接相关的文件，写到节名，例如「docs/设计.md 第 4 节」。不要整份读交接文件、README>

## 在哪里干活
- worktree：<路径>，分支 <分支>（已从 main 建好）。只动 <目录或文件>。
- <要装依赖才写：命令>
- <有并行任务才写：谁在哪个分支动哪些目录；你不要动 <目录>>

## 要做的
<目标和要求。和别的任务之间的接口约定照写字段名。用户说的「好看」「优雅」这类，译成两三条能看出来的规则>

## 怎么算做完
- <一条条能检查的结果。用户给了验收原话的，照抄，不补不改>
- 验证只做这些：<照第 3 节影响面那一档的预算写具体命令或检查>。觉得不够，在回复里说，不要自己加。

## 不要做
- <范围外的事>
- 不要按项目名或路径批量杀进程（`pkill -f <项目名>` 这类）：主控和别的 agent 的进程命令行里都带着项目名和工作目录，一条命令能把它们全杀掉。停自己起的服务用起的时候记下的 PID，或者固定端口后 `lsof -ti:<端口>`。
- 碰到要拿主意的事（包括 <某种情况>），停下来，在回复里写清问题、可选办法和你的建议，然后结束这一轮，等主控回复再接着做；不在自己窗口里问用户，不开着命令等，不要自己换别的办法。主控的决定写进完成记录。
- 不合并到 main，不推送。只在 <分支> 上提交。

## 做完
在本文件末尾追加「## 完成记录」（在你的分支里提交）：做了什么、验证了什么、拿主意的地方、没做的事、踩过的坑，各几句话。踩过的坑指试了不行、换了办法的，工具或环境的行为和预想不一样的；没有就写「没有」，不要凑。回复里只写这几样，加上有没有要主控决定的事。命令都在前台跑完，全部做完后，回复最后一行写 DONE。
```

写完自查一遍，删掉这些：

- 超出预算的验证：覆盖矩阵、跑全套、录屏截图、交证据目录、往代码里植入缺陷看测试红不红。只有「碰要害」那档才可能要，见第 3 节。
- 用户没要的东西：用户的顾虑被你扩成了新功能的，先问用户，不要直接写进去。用户给了验收原话的，验收就是那几条，不补验收点；你觉得该加的，列出来问用户。
- 「主控会审查、会重跑」这类话：只会让对方多做证明。
- 以前某件活的教训：这件活有同样的风险才写，不当成每件的默认条款。

**定类型**：每件活由你定一个主类型，写进任务文件开头。依据是用户的描述、和用户确认过的交流、你调查到的情况；用户不用给类型，也不用按格式写。路由不分类，被委派的 agent 也不再分类。类型回答「本轮做什么」，只选一个，不加第二个维度或标签。

| 类型 | 判定 | 提示 |
|---|---|---|
| 调研 | 查明事实、定位问题、回答疑问，本轮不修复或实现 | 区分已查证事实、推测和未知，给出直接依据；结论限定在本轮调查范围。 |
| 设计 | 形成方案、接口或取舍建议，本轮不实现 | 围绕已知约束给出推荐及关键取舍；有实质备选时再比较，不凑方案数量。 |
| Bug 修复 | 让已有功能恢复到明确的预期行为 | 依据证据定位并修复导致问题的原因，保持无关行为不变。 |
| 功能变更 | 新增能力，或有意改变现有行为 | 围绕已确认的使用目标完成变更，优先沿用现有机制。 |
| 重构 | 改善内部结构，保持外部行为不变 | 围绕指定的结构目标调整，保持约定的外部行为不变。 |
| 样式／文案调整 | 调整视觉呈现或文字内容 | 沿用现有视觉和用语约定，聚焦指定的呈现结果。 |
| 其他 | 无法明确归类 | 不附加提示 |

重叠时这样选：

- 先看授权范围：「调查为什么按钮失效」是调研；「查明并修复」才是 Bug 修复。
- Bug 与样式：修复文字被截断、按钮样式偏离既定规范，归 Bug 修复；主动换配色、改措辞，归样式／文案调整。
- 功能与重构：为实现功能调整结构，归功能变更；只整理结构且行为不变，归重构。分类本身不授权顺手重构。
- 调研与设计：「现在怎样、原因是什么」归调研；「应该怎么做、推荐哪个方案」归设计。设计所需的调查不单独分类。
- 设计和实现已经分开派发的，各自分类；不因为分类额外拆任务，拆不拆照第 3 节分工表下面的规则。
- 返工范围没变的，可以沿用原类型。
- Bug 修复不等于一定要改逻辑；样式／文案调整也不自动代表影响面低。

任务书只写本轮这一类的提示，被委派的 agent 不用读本技能。类型一般不决定几档、验证预算、要不要交叉审查、交给哪家，这些照第 3 节定。例外：本轮不改代码的调研、设计，第 3 节规定一律算「看得见」、不交叉审查。提示服从用户授权和任务范围，不据此新增需求、验收、交付物，也不重复写测试要求。例如：

```markdown
类型：调研
依据：本轮只定位列表自动收起的原因，不实施修复。
提示：区分已查证事实、推测和未知，给出直接依据；结论限定在本轮调查范围。
```

## 3. 交给哪家、几档、要不要交叉审查

每件活都要定这几样：交给哪家、模型和强度、影响面、要不要交叉审查。**先把任务书正文写好（第 2 节），再定这几样**，顺序是：

1. 从写好的正文提炼摘要，问路由。路由只判难度、要不要交叉审查、影响面，不判交给谁。
2. 照下面的档位和类别选格子，调读表命令取当下的家、模型和强度。
3. 照影响面定验证预算，写进「怎么算做完」；补上任务文件开头的「交给谁、几档」和路由那一行。打算交给 pi、omp 的，看正文要不要写得更具体。

用户点名、项目 AGENTS.md 写了的先于默认分工；下面禁止的配置一律不开。主控只在用户明说或任务文件写了 `执行：主控` 时自己做。

**问路由**：从写好的正文提炼三五句摘要，中文即可：做什么、改哪些目录、做错了会影响什么，不写私人数据。不写验收和打算怎么验证：摘要里写了测试矩阵、录屏，路由就会照着判重。运行 ranch 的路由命令：

```sh
echo "<摘要>" | ranch dispatch route
```

- 等命令结束、stdout/stderr 收齐再判断。退出码 0 且 stdout 是 `"ok": true` 的 JSON 时，照用：
  - `tier.level`（轻 / 常规 / 重）：三档里概率最大的那档，总有值。不用 `tier.verdict`，它在置信度不到 0.8 时是 `null`，用了就常常判不出；
  - `cross_review.verdict`（要 / 不要）；
  - `impact.verdict`（看得见 / 改行为 / 碰要害）。

  后两项为 `null` 时自己按下面的规则定。项目写了「不用路由」时不调用。
- 其他任何情况都是路由不可用：档按「常规」算，另外两项自己按下面的规则定，继续项目规则或本次用户已明确要求的分派流程；不要重试，不要改用旧 route.py，不要追加询问。没有分派要求的项目不因此自动委派。
- 路由行的不可用原因：退出码 1 且 stdout 是 `"ok": false` 的 JSON 时，照它的 `error` 写；其他情况（找不到 `ranch`、别的退出码、stdout 不是 JSON）只写「路由不可用，原因未知（退出码 N）」。
- 只有在知道路由看不到的情况时（比如这件活返工过、审查发现过问题），才推翻它的结论，写一句理由。
- 在任务文件开头记一行：`路由：<档> / 交叉审查<要或不要> / 影响面：<档>（路由：<tier.level>（置信 <tier.confidence>）、<交叉审查结论>、<影响面结论>，null 写拿不准，不可用写原因；推翻：<理由，没有就不写>）`。

**先看指定，再判档位和类别**：

- 任务文件写了 `执行：主控`，或者用户明说让主控自己做，才由主控自己做。
- 用户点名的照用户说的；其次照项目 AGENTS.md 的规定。没说的部分按下面规则读表补齐。
- 其余按下面的档位和类别读对应格子。

**档位**：从上往下，第一条命中的算数。

1. 要改代码，并且碰要害（路由的交叉审查是「要」，或主控判断碰了数据模型、并发和事务、安全和隐私、核心规则）→ 碰要害。
2. 要出方案、做取舍：架构、模块边界、新界面、新交互、跨模块；本轮只出设计 → 高。
3. 路由 `tier.level` 是「重」，或主控判断是跨好几个文件、原因不明的 bug → 高。
4. 路由 `tier.level` 是「轻」，并且不碰要害、改动点能一条条列出来、没有待定的设计问题 → 低。
5. 项目代码之外的杂活：本机清理、一次性脚本、核对数据、跑命令汇报 → 低。
6. 其余 → 中。

查事实、定位问题的调研按上表定档；涉及界面或产品取舍的调研算第 2 条。

**类别**：界面、设计（含涉及界面或产品取舍的调研）算「界面和设计」，其余算「其余」。

**默认表**：

| 档位 | 界面和设计 | 其余 |
|---|---|---|
| 低 | `low-design`：pi 或 omp，各自默认模型 | `low-other`：pi 或 omp，各自默认模型 |
| 中 | `middle-design`：Claude Code，`opus[1m]`，high | `middle-other`：Codex，`gpt-6-astra`，high |
| 高 | `high-design`：Claude Code，`opus[1m]`，xhigh | `high-other`：Codex，`gpt-6-astra`，xhigh |
| 碰要害 | `critical-design`：Claude Code，`opus[1m]`，xhigh | `critical-other`：Codex，`gpt-6-astra`，xhigh |

默认只有碰要害两格配交叉审查：Claude Code 写的交 `review-codex`（`gpt-6-astra` xhigh），Codex 写的交 `review-claude`（`opus[1m]` xhigh）。低档返工后升到同类别中档，中档升到同类别高档；高、碰要害没有升档格子。执行照第 5、6 节。

每次派活都读一次，不沿用上次的结果：

```sh
ranch dispatch cell middle-other
ranch dispatch table
```

`cell <格子>` 的 `cell.choices` 是可任选的家，每项给 `agent`、完整的 `command` 和等价的 `argv`、`labels`，还可有 `env`（`KEY=VALUE` 字符串数组）；模型和强度在 `cell.model`、`cell.effort`，`null` 表示各自默认。`cell.review` 有交叉审查格子的名字、模型、强度和 `choices`；`cell.rework` 是返工后升档的格子名或 `null`，不会自动执行，返工仍按第 5 节。命令只读数据，不开 agent。退出码 0 且 `ok:true` 才用；读表失败就报告错误并停下，不拿旧表或记忆里的参数凑。读到所需的 `choices` 为空时（包括审查、升档），停下告诉用户，不派。

`table` 列出整张生效表和各家的模板，`source` 标明 `builtin` / `user`；格子和它引用的家分别标来源。用户改 `~/.ranch/dispatch.toml`，只写要改的格子或家、要改的字段，其他继承内置表；数组整项替换，也能加新格子。下一次读表就生效，不编译、不重装技能。例如只换中档「其余」格子的模型：

```toml
[cells.middle-other]
model = "用户选定的模型"
```

- 用户或项目指定了家，碰要害的活照样要交叉审查，验证预算照样按影响面定。点名 pi、omp、amp、agy、Kimi 做碰要害的活时，交叉审查读 `review-codex`；Claude Code、Codex 仍按上面的新表互审。
- 只指定了家、没定模型或强度时，Claude Code 读同档「界面和设计」格，Codex 读同档「其余」格；低档点名这两家时用对应中档格补齐，强度只用 high、xhigh。pi、omp 从同类别低档格选对应一家，amp、agy、Kimi 读同名格子（Kimi 为 `kimi`）。明确指定的模型或强度按 `table` 返回的该家模板代入，同时更新命令和标签；只补没指定的部分，禁止的配置照下文处理。
- pi、omp 两家同类，任选，一家手上有活就开另一家，各自用默认模型，不另选模型。amp、agy、Kimi 的分工还没定，只在用户或任务文件点名时派。
- 交叉审查读该格的 `review`，按实际开发者换家，见第 6 节。
- 既要设计又要实现、又不是界面的活，拆成两步：先按「高／界面和设计」读表派人出方案，用户定（架构级的决定照第 1 节由用户拍板），再按档位和类别派人实现。新界面的设计和实现都按「界面和设计」读表。
- 新界面、或者没有现成示意的大改，派人实现之前先给用户看样子：一张文字线框或示意，用户选定了再派。规则明确的小调整（换个颜色、加一个提示）直接做。
- **一件活一个 agent、一个 worktree**：新活不要塞给已经开着的写代码 agent，它的工作目录钉在自己那个 worktree 上，换不了目录，也换不了模型和强度。同一个 agent 只在自己那个 worktree 里接后续：返工、复核；升档时按第 5 节在同一个 worktree 换新 agent。按当次档位和类别读表选家。

**模型和强度**：不带参数时，开出来的 agent 用它自己的全局默认，**不继承你的模型和强度**。每次开 agent 都照读表返回的完整命令带参数，并在任务文件和汇报里写明实际模型和强度。

- Claude Code、Codex 只用 high、xhigh；默认中档用 high，高和碰要害用 xhigh，交叉审查用 xhigh。
- 不用 `low` 强度标签；这里的「低」是任务档位，pi、omp 用默认，不带强度标签。看板使用 high、xhigh 标签。
- Claude Code 一律不用 `max` 强度和 `fable` 模型，Codex 一律不用 `ultra`；用户点名也先说明，不开。本机表覆盖也不绕过这条。
- pi、omp、amp、agy、Kimi 用它们的默认，不分强度。派 Kimi 不指定模型，用用户自己设的默认。
- 模型名会随版本变，过时了改本机数据表，下一次派活重新读；实际家、模型、强度、命令和标签以读表结果为准，并遵守上面的配置限制。

**影响面**：定验证预算，写进任务书「怎么算做完」。难度定模型和强度，影响面定验证，两件事分开定。

| 档 | 什么活 | 开发的验证 | 审查 |
|---|---|---|---|
| 看得见 | 只影响显示、文档、文案、配色，或只读研究；做错了一眼看得出，随时能改回 | `git diff --check`，加一条能直接看出结果的检查。不要求先写失败测试 | 主控看 diff，不重跑套件 |
| 改行为 | 写功能、修 bug，不碰下一档 | 一条针对这件活的测试（修 bug 先写测试，确认它因为这个 bug 失败）+ 项目的标准测试跑一次 | 主控看 diff，重跑一次标准测试 |
| 碰要害 | 数据模型和迁移、并发和事务、安全和隐私、核心规则 | 上一档，加上边角用例。覆盖矩阵、植入缺陷自检只在这一档可以要 | 同上，加交叉审查（第 6 节） |

- 照路由的 `impact.verdict`；它是 `null` 时你按上表判，拿不准定「改行为」，不要往重的一头靠。
- 类型是调研或设计、本轮不改代码的活，一律算「看得见」，不交叉审查，不管路由说什么：路由一看到摘要里提安全、并发，就会判成碰要害。
- 录屏、真实终端录制、在真浏览器里走一遍：哪一档都不是默认。用户要求了，或者验收除此之外确实查不了，才写进任务书；集成验收只走主路径一遍。
- 预算照档执行，不往上加：一项验证通过、相关代码没再改的，不重复跑（主控审查按第 5 节重跑的那一次照旧）。标准套件出现疑似和这件活无关的失败，可以单独复跑一次帮助判断，原来的失败结果照样留着；复跑通过不等于根因已经修好。觉得还要多验，先报告原因，不自己扩大预算。返工只跑针对这次修正的检查和直接相关的回归，不再重跑标准套件或静态检查。

**要不要交叉审查**：见第 6 节。

## 4. 派出去

按 corral 技能开 agent，另外注意：

- 名字用 AGENTS.md 规定的前缀，`--cwd` 指向它的 worktree。把读表选中的 `choices` 项的完整 `command` 放在 `--` 后，每条 `labels` 各加一个 `--label`（空数组就不带）。下面是拼接示意，占位符须替换为实际返回值；也可以用 `argv` 逐项传参。第一句话很短，只让它去读文件：

  ```sh
  corral start demo/dev-backend --unique --cwd <worktree> --env CAIRN_DISABLE=1 <读表 env 对应的 --env 参数> <读表 labels 对应的 --label 参数> --prompt "先读 AGENTS.md，再读 <任务文件>，照做。命令都在前台跑完，全部做完后，回复最后一行写 DONE。" -- <读表 command>
  ```

  若所选 `choices` 项有 `env`，每项原样作为一个 `--env` 的参数传在 `--` 之前，按 shell 规则引用整个 `KEY=VALUE`，不执行其中的变量或命令；缺省或空数组就不带。

  派给 amp 时不能带 `--prompt`：先 `corral start <名字> --unique --cwd <worktree> --env CAIRN_DISABLE=1 <读表 env 对应的 --env 参数> -- <读表 amp 的 command>`，下面的 `corral wait` 等到 `idle` 后，再用 `corral send <名字> "<同样那句话>"` 送第一句（见 corral 技能）。
  派给 agy 照上面的样子带 `--prompt`（agy 不带它就一直是 `starting`），不带 `--label`，`--` 后用读表 agy 的 `command`。
  派给 Kimi 同样带 `--prompt`，用 `kimi` 格的 `command`，把该项 `env` 每项各传一个 `--env`；内置值为 `KIMI_CODE_TRUST_WORKSPACE=1`，只对这次启动生效，不写 Kimi 的信任记录。内置命令为 `kimi --auto`，不加模型、强度，标签为空；`--auto` 不会打开提问框，需要提问的普通模式按 corral 技能启动。

- 本技能开的 agent（干活的、交叉审查的）一律带 `--env CAIRN_DISABLE=1`，不用 cairn（工作接续记忆）：它们的进度写在任务文件里，cairn 留给用户直接对话的主控。没装 cairn 时这个变量不起作用，照写即可，不要删。
  Codex 的默认启动模板还会关闭这个会话的 Codex 记忆（不改全局配置），直接使用读表返回的完整命令。`~/.codex/memories/` 是跨项目的，会把别的项目、工作上的内容带进来，旧约定也会和任务文件打架。

- `--label` 使用读表返回的 `labels`，和命令里的参数一起取，不自己猜。默认 Claude Code、Codex 带强度和模型，看板靠它显示档位；pi、omp、amp、agy、Kimi 不分档，默认标签数组为空。

- 被委派的 agent 一律免确认启动，中途不弹权限框，也不会被自动检查拦下。各家的启动命令和标签在数据表里只写一次，使用第 3 节读表得到的完整命令，不再另加分档参数：

  | agent | 命令来源与说明 |
  |---|---|
  | Claude Code、Codex | 所选格子的 `choices`；点名时照第 3 节补缺省部分 |
  | pi、omp | 所选格子的 `choices` 中任选一家；pi 本来就没有权限框 |
  | amp | `amp` 格；没有免确认的启动参数，要不要确认看用户自己的 amp 设置；卡在确认上时状态是 `blocked`，请用户去点 |
  | agy | `agy` 格；首句仍按上面的规则带 |
  | Kimi | `kimi` 格；逐项传 `env`，首句带 `--prompt`，用用户自己的默认模型 |

  免确认也就没有安全网：能约束它的只剩任务文件里「不要做」那几条，所以那一节要写全。免确认跳不过「是否信任这个目录」的框，见下一条。
  Kimi 的信任框由读表给的 `KIMI_CODE_TRUST_WORKSPACE=1` 免掉；仍一直 `starting` 时先让用户用 `corral integration status` 查钩子，没装就 `corral integration install --agent kimi`，不要自己装，见 corral 技能。
- 开完运行 `corral wait <名字> --timeout 60`，不要用 sleep 等。60 秒到了状态还是 `starting`，就是卡在「是否信任这个目录」这类对话框上（新项目、新仓库第一次开时常见；amp、agy 还可能是 corral 的插件没装好或被停用，见 corral 技能）。这时请用户在另一个终端窗口运行 `corral attach <名字>`，或者在看板里选中它去点。不要替它点，也不要让用户在你这里用 `!` 运行。卡在启动中时，提醒不会来，不要干等。
- 前台这次 wait 如果对方已经停了，按第 5 节收到提醒的规则查状态和回复、判断 DONE，不能当成「起来了」就结束；没写 DONE 且仍在的，回复里问要拿主意的事由主控照第 8 节处理。主控自己定的，**以用户的回答为准**：送决定前再运行一次 `corral status <名字>`；`last_human_input` 晚于这次停下的 `state_started`，或 `state` 又是 `working`，就当成用户已经在回答，主控不送，只按 corral 技能「长任务」一节重挂提醒（Claude Code 连后台 wait 一起）。`corral send` 报 `not_idle` 或 `human_active` 时同样不送、不加 `--force`，重挂提醒；没送时告诉用户 agent 问了什么、主控原本打算怎么定。第 8 节先问用户的情况、等人操作的对话框照旧按第 5 节处理并重挂提醒；被打断的照原规则处理，已经退出或不在了的不再挂。
- 写代码都是长任务：仍在干活的，按 corral 技能「长任务」一节挂提醒（Claude Code 连后台 wait 一起），交出去就结束这一轮。
- 已识别为被打断的这一轮不触发 `--after` 提醒，原提醒继续等下一轮正常结束；等满 `--timeout` 仍会送。Claude Code 从对话记录末尾识别晚于最近一次输入的明确打断标记；调用方和提醒进程需用新版，且该 CORRAL_HOME 的 `.runtime/helper` 要经新版 `corral upgrade` 等方式切到能记录路径的版本；单纯切换 CLI 或重开不够，记录读不到或格式不认识时仍认不出。收到提醒先查 `status`，不能只凭提醒认为完成。
- omp 最终 `agent_end` 的最后一条 assistant 消息同时带 `stopReason: "aborted"`、`errorMessage: "Interrupted by user"`、`errorId` 的 UserInterrupt 位（67108864）时按打断处理，wait 返回 `interrupted`，reply 报 `no_reply` 带 `interrupted: true`。调用方和提醒进程用新版即可，采集器不用换、omp 不用重开。Esc 只取消命令、模型继续正常结束不算打断；其他中止和 `willContinue` 照旧。
- 告诉用户：开了谁、哪家哪一档、在哪个 worktree、做什么、做完怎么通知。
- 开出来的 agent 默认不关；写代码的 agent 活到它那个 worktree 被清掉为止（第 7 节）。例外：按第 5 节升档时，先把原开发 agent 的完成记录留在任务文件里，再关掉它，不用问用户。

## 5. 主控审查：核实，不重做

每件都审，按这件活影响面那一档的预算审（第 3 节），不超出。重点是核实对方说的，不是自己再证一遍：

- 收到提醒（或被后台 wait 叫醒）先查 `corral status <名字>`；`interrupted: true`、wait 的 `result: "interrupted"`，或 reply 的 `no_reply` 带 `interrupted: true`，都表示这一轮被打断，不进入完成审查。告诉用户，等它继续；没有中断标记时再读 reply，核实回复最后一行是 DONE 和完成记录。
- 对方停了但回复最后一行不是 DONE（包括 `no_reply`），且 `corral status` 的 `sandbox` 不是 `null`：先看 `fence denials --agent <名字>` 的网络拦截记录（`type: "network"`），用 `corral read <名字>` 看屏幕末尾的报错，把被拦的域名和报错告诉用户；已退出读不到屏幕时说明这一点，并查看 denials 的 `exit.message`。之后仍按下面的规则告诉用户、重挂提醒或不再挂。
- 对方停了、仍在，回复最后一行不是 DONE，且回复里在问要拿主意的事：主控照第 8 节自己定，但**以用户的回答为准**。送决定前再运行一次 `corral status <名字>`：`last_human_input` 晚于这次停下的 `state_started`，或 `state` 又是 `working`，就当成用户已经在回答，主控不送，只按 corral 技能「长任务」一节重挂提醒（Claude Code 连后台 wait 一起），告诉用户 agent 问了什么、主控原本打算怎么定，结束这一轮。否则用 `corral send <名字> "<决定>。命令都在前台跑完，全部做完后，回复最后一行写 DONE。"` 回给它；报 `not_idle` 或 `human_active` 时同样不送、不加 `--force`，重挂提醒，告诉用户 agent 问了什么、主控原本打算怎么定，结束这一轮。送成功后重挂提醒、结束这一轮，事后在对话里告诉用户定了什么、为什么，决定也记进这件活的「主控审查」。第 8 节「先问用户再做」那几类，或主控真的拿不准（几个办法各有明显代价、又没有依据可选），仍照旧先问用户，带上选项和主控的建议；用户定了再回给 agent、重挂提醒。
- 等人操作的对话框（信任目录、登录，或 `blocked` 的权限框、提问框）主控替不了，照旧告诉用户去 `corral attach <名字>` 处理，同时按 corral 技能「长任务」一节再挂一次提醒（Claude Code 连后台 wait 一起），结束这一轮。其他空闲或 blocked、没写 DONE 且回复里没有上述问题的，也照此请用户去看并重挂提醒。用户在对方窗口里直接聊，或通过主控转话，都要继续盯；下次被叫醒仍按同样规则判断，直到看到 DONE。对方又在干活，是被叫早了，同样重挂；对方已经退出或不在了但没有 DONE，告诉用户，不再挂提醒或后台 wait。
- 对方的完成回复是待核对的说明，不替代代码和检查结果。重点核对任务目标和关键行为断言，不因此另列审计清单或加验证。
- 读完成记录和回复，看 diff：只动了该动的，「不要做」里的一件都没做，「怎么算做完」逐条达到。
- 测试：看得见的活不重跑套件；改行为、碰要害的重跑一次项目的标准测试，核对数字和对方说的一致。
- 不自己录屏、不做覆盖矩阵、不另写脚本测边角。真怀疑某一处，挑那一条实测。
- 对方说「用户同意了」「用户说过」的，找用户核实。
- 对方列的取舍逐条表态：同意的记下，不同意的交回去改。
- **只有两种情况交回返工**：「怎么算做完」有一条没达到；做了「不要做」里的事。「没达到」指按验收正常使用会碰到的情况；只在罕见输入组合下才出错的，和清单外发现的边角问题一样记「建议改」，写进审查结论、告诉用户，要不要另开一件活由用户定，不交回返工。
- 完成记录和审查结论只写证据撑得住的：局部通过不写成全套通过，没确认的不写成成功。
- 结论写三五行，追加到任务文件末尾「## 主控审查」。最后一行记结果，四选一：`结果：一次过`、`结果：返工 N 次`、`结果：返工 N 次，升到 <档位>`、`结果：最高档返工仍不达标，已停下问用户`。N 是这件活累计返工次数，升过档的写最终档位，每件都记。主控不自己按结果调规则；用户要复盘时，把各件的结果行按档位和家汇总成表给用户。
- 给用户汇报时，对方写的「踩过的坑」用自己的话转述一句（写的「没有」就不提）。你自己说的话会完整留在会话记录里，工具输出可能被截掉；坑出现在你的会话里，才能被记下来。

要返工的写清楚是哪一条，交回原来的 agent：用 `corral send` 交过去，同样带 DONE 约定、挂提醒。复核只看改动的部分，只重跑和改动有关的检查。**每档最多返工一次**；再不过就重新读当前格子，按返回的 `rework` 读升档格子。先把原 agent 的完成记录留在任务文件里，再关掉原开发 agent，不用问用户；用升档格子的命令和标签开新 agent，仍在同一个 worktree、同一个分支，接着前一个的提交做。默认低 → 中、中 → 高，类别不变。没有升档格子的（默认高、碰要害）返工一次再不过，停下问用户。

## 6. 交叉审查：只给出错代价大的

只给影响面是「碰要害」的活（第 3 节）：路由的交叉审查结论是「要」，或者你判定它碰了数据模型、并发和事务、安全和隐私、核心规则。看得见、改行为的活不做；本轮不改代码的调研、设计也不做。

- 另开一个 agent 只读审查，重新读原任务所选格子，使用其 `review.choices` 的完整命令、标签和可选环境变量。交叉审查换一家：Claude Code 写的交 Codex，Codex 写的交 Claude Code。用户、项目指定或本机覆盖改变了开发者，或原格没配审查时，按实际开发者读对应的审查格：Claude Code、pi、omp、amp、agy、Kimi 写的读 `review-codex`，Codex 写的读 `review-claude`。默认分别为 `gpt-6-astra` xhigh、`opus[1m]` xhigh，实际参数照读表；所需 `choices` 为空就停下告诉用户、不派。只给新审查者任务文件和 diff，不用原开发 agent。审查任务也写成文件（放主仓库工作区，派的时候给绝对路径，并写明它不在审查 worktree 里、只写这一个文件），依次写：
  - 背景：谁在哪个分支做了什么，主控已经审过什么；
  - 先读；
  - 要审查的代码：**它自己的 worktree**（`git worktree add --detach <审查 worktree> <分支>`；同一个分支不能在两个 worktree 里同时 checkout，git 会拒绝，所以只能 detached，顺带防它手滑提交；也不要和 dev 共用一个，它掉个文件就会挡住清理）、`git diff main...<分支>`，**只读，不改、不提交、不切分支**；写明可以跑哪些测试、不能碰什么；验证照「碰要害」那档的预算，不录屏、不做覆盖矩阵；
  - 重点看：主控列 3 到 5 条，都是这件活碰到的要害；
  - 输出：追加到审查文件「## 审查意见」。先写一句结论（可以合并 / 改完再合并），每条意见写级别（必须改 / 建议改 / 可以不改）、位置、问题、改法，最后对取舍逐条表态。**「必须改」只给两种**：任务书「怎么算做完」没达到；碰到的要害上有真实缺陷（会丢数据、并发出错、泄露或越权、核心规则算错）。其余一律「建议改」；
  - 回复：只写结论和条数，最后一行 DONE。
- 主控逐条判断。只有「必须改」挡合并；「建议改」可以不采纳，写明理由。认可的交给开发 agent 改。
- 改完请同一个审查者复核，只看上一轮的「必须改」修好没有、改动有没有引入新问题；复核时才看到的、和这次改动无关的问题记「建议改」。**先把它的 worktree 推到新提交**：`git -C <审查 worktree> checkout <新 sha>`（仍是 detached）——不推的话它 `git diff` 看得到对象，跑测试却还是旧代码。**复核两轮还没到「可以合并」，停下来问用户**，不再往返。
- 主控和审查者有分歧的，列给用户。

## 7. 合并和收尾

- 合并前：测试全过、主控审查过、要交叉审查的已经是「可以合并」。任务说了不合并的，停在审查，汇报给用户。
- 按 AGENTS.md 的方式合并，合并提交里写一句摘要；推不推送按 AGENTS.md，没写就问。
- 合并后：审查结论追加到任务文件末尾；有集成方在等的，现在通知它。
- **合并后立刻清掉这件活的 worktree 和分支（dev 的和审查的都算），不用问用户。** 按顺序核对，并在回复里说明结果：
  1. 住在这个 worktree 里的 agent 现在是 `idle`（`corral status`）。还在 working 就等它这一轮完，别边跑边删；
  2. `git -C <worktree> status --short` 没有未提交的改动；
  3. 分支已合进 main：`git merge-base --is-ancestor <分支> main`；
  4. `git worktree remove` 不加 `--force`，分支用 `git branch -d` 删；
  5. 关掉住在这个 worktree 里、你自己开的那个 agent（`corral stop`），回复里写一句「工作目录已删，一并关闭」。关掉之后，之前挂在它身上的 `--after` 提醒照样会送到你这里（corral 就是这么设计的），查到 `not_found` 忽略就行。

  第 2 到 4 步是安全构造的：有未提交的改动 `worktree remove` 会拒绝，没合并 `branch -d` 会拒绝，git 自己兜底，丢不了东西。所以不需要等用户点头，**不要攒到下一个里程碑再清**。
- **第 5 步的扳机是第 4 步成功返回，不是你觉得活干完了。** worktree 一删，住在里面的进程 `pwd`、`ls`、`git`、读写文件全部失败，留着也接不了新活。下面三种照旧先问用户：放弃任务要 `--force` 强删（绕过了上面的兜底）、人正 attach 在它上面（`corral status` 的 `attached` 不是 0）、不是你开的 agent。
- 关之前确认记录都落盘了：主控审查结论、交叉审查意见、对方列的取舍都要在任务文件里（主仓库，不随 worktree 消失）——关掉就问不到它了。清完把「还开着哪些、各自在哪」报给用户。
- 项目有交接文件的，更新它。

## 8. 什么自己定，什么先问

- 小事主控先定：写进文档，事后告诉用户。
- 先问用户再做：涉及隐私；花钱（订阅额度、付费服务、真实调用）；改用户批准过的设计；删除东西（**合并后清 worktree 和分支除外**，见第 7 节）；推送；关掉 agent（**清掉 worktree 时一并关掉住在里面、自己开的那个除外**，见第 7 节；**按第 5 节升档时关掉原开发 agent 也除外**，它的完成记录先留在任务文件里，不用问用户）。
- 被委派的 agent 问的事也照本节分：小事主控定、事后告诉用户；上面那几类先问用户。主控真的拿不准（几个办法各有明显代价、又没有依据可选）时，也带上选项和自己的建议先问用户；用户定了再回给 agent。
- 问的方式：一次最多五个问题，按重要程度排，每个问题给选项和你的建议。
