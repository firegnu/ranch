# corral-dispatch 的可选遥测操作

本文随 Saddle 的 corral-dispatch 技能同版本交付，离开开发 checkout 也可使用；只组合已有公开命令。Saddle 拥有记录，Corral 只执行业务，不接收遥测上下文。此说明不授权新任务、派发、审查、合并、推送或关闭 agent，仍按项目规则和当次授权操作。

## 1. 先决定是否记录，再做一次业务

- 普通临时操作默认不记录。只有用户明确选择本链路，或 Drover 项目默认/本次选择明确要求记录时，才准备上下文。安装本技能不让所有项目自动委派，也不自动采集所有 Corral 操作。
- 一次口头授权只覆盖用户这次所指的任务，包括委派、执行、同任务返工、审查和实际收尾；任务可含多个派发或任务文件，不等于会话、项目或主题。完成并交付且没有同任务待决事项，或用户明确放弃/终止时，按第6节结束；用户不必另说“停止记录”，也不必提供 ID。设计稿、一次审查或实现候选等阶段产出不是全任务终点；还等是否合并、继续或返工的决定时不结束。
- 下一项独立任务未再次要求就不记录；再要求就新建 trace，不复用已结束的 trace。Tasks 项目默认和本次覆盖仍按已有规则。同 run 内的审查/实现返工留在同一 trace；Return 结束旧 run，新 run 按项目默认/本次覆盖决定是否记录。用户已明确要求新 run 继续记录时，绑定新 run 新建 trace，不重复询问许可。
- `saddle telemetry settings get` 只读查询总开关；首次为关闭。全局关闭、本链路未选或已关闭时不自行开启；重新开启不补录关闭期间材料。开关由用户在 Settings → General 控制；本流程不执行开启命令。
- 无记录时沿原 Corral 技能执行业务。选择记录且已具备同版本 Saddle 时，使用下文 `saddle agent`；路由用 `saddle plugin run dispatch route`。没有 dispatch 插件/插件停用仍可用独立遥测和 agent 入口；没有遥测或准备失败仍可正常委派。
- **唯一降级点在业务尝试之前**：trace/dispatch/证据准备失败或发现入口不可用时，说明本次没有有效记录上下文，按原已授权路径执行一次；不要把无效上下文硬传给入口。可用的证据链接只引用已确认保存的 ID，缺失就省略并报告。
- **一旦尝试 route/start/send/reply，就不因遥测失败、125/127、超时或缺回执改成直调再发。** 业务与记录分别报告；结果未知保持未知。即使配对回执明确 `executed=false`，本流程也不自动重试；修正后的新业务尝试须按项目规则和当次授权另作决定。路由不可用直接自行定档继续，不回退 route.py 或 dlog。
- 命令等到退出、stdout/stderr 收齐；每次分别保存输出，不把多次 stderr 拼成一条调用。程序化调用方在 exec 前建立并记住这次独立进程组；取消只 TERM 该组，最多 250ms 后 KILL 并回收直接子进程。不按名称找进程，不 stop Corral 托管的 agent。取消不撤销已排队/已投递的消息。

以下 JSON 中 `TRACE`、`IMPL`、`REQ` 等是占位符，提交前替换为已保存的 UUID v4（新 ID 可用 `python3 -c 'import uuid; print(uuid.uuid4())'` 生成一次）。所有正文、上下文和任务书路径替换为本次真实绝对普通文件路径；不是符号链接。JSON 用正常序列化器或编辑器写入，避免把原话拼进 shell。正文保持原字节，每份至多 16 MiB；上下文至多 64 KiB。示例不是一次性全执行脚本，只执行本次授权需要的步骤。

## 2. 取得 trace，给每次委派独立身份

**没有 Drover run**：已显式选择记录的临时工作可建 ad_hoc trace，无需登记 Tasks 或虚构任务/run。把下面保存为 `trace.json`，运行 `saddle telemetry trace create --input /absolute/trace.json`：

```json
{"schema_version":1,"trace_id":"TRACE","origin":"ad_hoc","label":"本次工作的简短名称"}
```

**已有 Drover 交付**：复用本次消息附段的 trace_id、controller_handoff dispatch_id 和声明的 task/run，不再建一个“最新 trace”。先 `saddle telemetry show --id TRACE` 核对绑定；任务是否登记/当前状态由 Drover 公开接口核实（运行中宿主的 `saddle ctl plugin`，按项目既有用法），不能从 trace 存在或 task.transition 声明推断。附段不是用户原话或新的授权。压缩后可按已知完整绑定恢复候选：

```sh
saddle telemetry list --kind drover.task --scope /absolute/project --key T1 --run RUN
saddle telemetry show --id TRACE
```

`scope` 用交付中的原值，`run` 用这一轮原值，不猜最近一轮。有 Drover run 就绑定它，不另建 ad_hoc trace；已有记录附段直接复用。中途口头要求记录时，先经公开任务接口核实 task/run，再创建 origin=`task`、完整 `binding:{"kind":"drover.task","scope":"/absolute/project","key":"T1","run":"RUN"}` 的 trace，只覆盖实际开始记录的时间；绑定本身仍是未认证声明。没有足够身份时不要猜。

本任务的记录上下文要可恢复：已有任务文件或交接文件时可记下 trace_id；没有时放在主控为本次自建的记录目录，不强制用户建立任务文件。会话压缩或重启后据此恢复，核对 show 的 closed_at，不按最新 trace 猜；结束后在该处标明“本次记录授权已结束”。

每次 implementation/review/redispatch 都先生成新的 dispatch_id，用 `saddle telemetry dispatch create --input /absolute/dispatch.json`。例如实现者：

```json
{"schema_version":1,"dispatch_id":"IMPL","trace_id":"TRACE","kind":"implementation","parent_dispatch_id":"HANDOFF"}
```

- `HANDOFF` 是本次真实 controller_handoff。独立 ad_hoc 实现没有父派发时省略 parent_dispatch_id，不填 null 占位或造一个父 ID。
- 审查另建 `kind:"review", dispatch_id:"REVIEW", parent_dispatch_id:"IMPL"`，其 route/start/send/reply 全用 REVIEW。
- 新一轮返工另建 `kind:"redispatch", dispatch_id:"REWORK", parent_dispatch_id:"IMPL"`（若返的是另一轮，用实际那轮的 ID）；返工依据通过 review 事件链接表达，不用 parent 代替依据。
- 同次派发内补充要求用原 dispatch 加 followup；换 agent 或新委派不要复用旧派发身份。所有 parent 必须已存在且属于同一 trace；复用已有 agent 也要建新委派身份。

纯记录创建的 ID 和内容在首次提交前保存；回执丢失可先 show，必要时只重交相同记录，不重做业务。

## 3. 逐字提交需求、提议与授权

主控只转录当前可见、获准使用的原话，或用户明确提供的文件；不搜索私人会话数据库补挖原话。未知说话者/来源不伪造；拿不到原话时把自己的理解作为 summary/note，并明说缺少原始依据。`controller_statement` 一律未认证，不写 `execution_observed`、`system_control`、`source_auth` 或不存在的 `direct_user_input`。

将用户原话逐字存到 `/absolute/requirement.txt`。`requirement.json`：

```json
{"schema_version":1,"event_id":"REQ","trace_id":"TRACE","kind":"requirement.recorded","observed_at":null,"producer":"controller","evidence_kind":"controller_statement","payload":{"declared_speaker":"user (declared)","acquisition":"controller_transcription","declared_at":null},"links":[],"bodies":[{"role":"text","path":"/absolute/requirement.txt"}]}
```

```sh
saddle telemetry append --input /absolute/requirement.json
```

`observed_at`/`declared_at` 只有确知原时间时填 RFC3339 UTC；未知用 null，不把现在冒充旧时间。用户提供原文件可用 acquisition=`user_supplied_file`；交付方材料用 `plugin_provided` 并保留来源声明，不把 Drover 的转述当用户直输。

主控提议和用户补充授权分别 append，不混成一份“用户原文”。沿用上面的 schema_version、trace_id、observed_at、producer、evidence_kind；改为新的 event_id，正文换对应原文文件：

| kind | payload | links | bodies |
|---|---|---|---|
| proposal.recorded | `{"declared_speaker":"controller (declared)","acquisition":"controller_transcription"}` | `[{"relation":"based_on","target_event_id":"REQ"}]` | role=text |
| authorization.recorded | `{"declared_speaker":"user (declared)","acquisition":"controller_transcription","context_complete":true}` | `[{"relation":"responds_to","target_event_id":"PROPOSAL"}]` | role=text |

只有真的保存了完整被回应语境且有 responds_to 时才用 context_complete=true；否则 false，并说明缺什么。不能把“好的”脱离提议解释成额外授权。需求/提议/授权不带 dispatch_id 或 operation_id。

跨 trace 复用已经保存的需求/授权，显式 append `kind:"evidence.reused"`，payload 只有 `{"reused_by":"controller"}`（与 producer 相同），links 恰一个 `{"relation":"carried_from","target_event_id":"旧证据ID"}`，bodies 为空。Store 复制原来源和正文引用，不改成新用户消息。只有此链接允许跨 trace；旧 dlog 数据不导入。

## 4. 路由观测与主控选择分开

可先 append 主控理解（不是原话）：

```json
{"schema_version":1,"event_id":"SUMMARY","trace_id":"TRACE","dispatch_id":"IMPL","kind":"controller.summary","observed_at":null,"producer":"controller","evidence_kind":"controller_statement","payload":{"purpose":"route"},"links":[{"relation":"based_on","target_event_id":"REQ"}],"bodies":[{"role":"text","path":"/absolute/summary.txt"}]}
```

保存 `route-context.json`：

```json
{"schema_version":1,"trace_id":"TRACE","dispatch_id":"IMPL","basis_event_ids":["REQ","SUMMARY"]}
```

摘要仅三五句，不含私密内容。项目允许路由时只调用一次：

```sh
saddle plugin run dispatch route --record-context /absolute/route-context.json --brief-file /absolute/task.md < /absolute/summary.txt
```

只把摘要发给 JEV，任务书由宿主保存；尚无任务书时省略 --brief-file，后续真实交付仍应携带。route 上下文不能含 decision_event_id 或 send_kind（连 null 也不传）。Saddle 保存实际请求、完整解析响应和独立建议；append 不能伪造 route.begin/end。插件缺失/停用、无 key、失败或 verdict=null 按 SKILL 第3节自行定档，既不阻断委派，也不自动启用插件或重跑。

按配对回执取得 operation_id 后，用 `saddle telemetry show --id OPERATION` 找到实际已保存的 begin/end 事件；也可用 events 查询。主控再提交真正采用的模型、强度、验证预算与理由，不能照搬建议冒充最终选择：

```json
{"schema_version":1,"event_id":"DECISION","trace_id":"TRACE","dispatch_id":"IMPL","kind":"controller.decision","observed_at":null,"producer":"controller","evidence_kind":"controller_statement","payload":{"planned_model":"gpt-6-astra","planned_effort":"high","validation_budget":"目标检查与项目标准各一次"},"links":[{"relation":"based_on","target_event_id":"REQ"},{"relation":"based_on","target_event_id":"ROUTE_END"}],"bodies":[{"role":"reason","path":"/absolute/reason.txt"}]}
```

用 `saddle telemetry append --input /absolute/decision.json` 提交。ROUTE_END 可用真实 route.begin 或 route.end ID（不是 operation_id）；路由未保存时删掉这一 link，在理由写明自行定档的原因。未知 planned_model/planned_effort/validation_budget 可用 null。示例模型/预算不是本次路由结论，按实际决定填写。

## 5. 把真实任务书随 start/send 交付

先写好真正交给 agent 的任务书，然后显式传入 --brief-file；不能用路由摘要代替。入口保存调用当时的完整快照，记录原路径和时间，不能证明 agent 实际读过。prompt/send 里仍明确要求读该文件；--brief-file 本身不会改业务消息或替 agent 读文件。

`start-context.json`：

```json
{"schema_version":1,"trace_id":"TRACE","dispatch_id":"IMPL","basis_event_ids":["REQ","AUTH"],"decision_event_id":"DECISION"}
```

只保留实际已保存的依据。start 的 basis 只用需求/提议/授权/复用证据；审查依据可在任务书和 review/note 里陈述。实际参数沿用项目和本次选型；例如一次已授权的 Codex 实现委派：

```sh
saddle agent --record-context /absolute/start-context.json --brief-file /absolute/task.md -- start demo/dev-example --unique --cwd /absolute/worktree --label role=implementer --label model=gpt-6-astra --label effort=high --prompt '先读 AGENTS.md，再读 /absolute/task.md，照任务完成。最后一行 DONE。' -- codex --yolo -m gpt-6-astra -c 'model_reasoning_effort="high"'
```

以 Corral 公开返回的实际 name/instance 继续操作（--unique 可能改名），不要猜名字。role 标签体现 implementer/reviewer/controller，model/effort 标签是声明，应与真实参数一致；Saddle 只从显式参数识别实际模型/强度，不从标签或默认设置推断。免确认等业务参数仍按 Corral 技能与项目规则。

把新委派首次交给已有 agent 时改用 send，使用该新 dispatch 的 `send_kind:"initial"`；同一次委派补充用 `followup`；返工用相应 REWORK dispatch 的 `rework`。`send-context.json` 示例：

```json
{"schema_version":1,"trace_id":"TRACE","dispatch_id":"REWORK","basis_event_ids":["REQ","REVIEW_EVENT"],"decision_event_id":"REWORK_DECISION","previous_brief_event_id":"OLD_BRIEF","send_kind":"rework"}
```

```sh
saddle agent --record-context /absolute/send-context.json --brief-file /absolute/rework.md -- send ACTUAL_AGENT_NAME '先读 /absolute/rework.md，按本轮任务返工。最后一行 DONE。'
```

send 的 basis 可含需求/提议/授权/复用证据和 review.recorded。previous_brief_event_id 只在确实修订已存快照时传，并同时给本次 --brief-file；OLD_BRIEF 从旧 operation 的 events 中取真实 brief.snapshot ID。新快照以 supersedes 关联旧快照，仍现场读新文件，不复用旧内容冒充新交付。没有修订关系就省略该字段；任务书缺失/不可读显示 gap，不填假快照。

等待与状态查询继续按 Corral 技能（如 `corral wait ACTUAL_AGENT_NAME --timeout 60`、`corral status ACTUAL_AGENT_NAME`），不为记录改变长任务提醒、授权或队列放行规则。

## 6. 回复、审查、返工与实际收尾

reply 用该派发自己的最小上下文，不传任务书、send_kind、依据、决策或旧快照：

```json
{"schema_version":1,"trace_id":"TRACE","dispatch_id":"IMPL"}
```

```sh
saddle agent --record-context /absolute/reply-context.json -- reply ACTUAL_AGENT_NAME
```

保存的是当场公开 reply 的完整 text、name/instance/at，association=not_proven；不是某次 send 的必然回复，也不等于验收通过。没有拿到/没有保存保持缺口，不从私人 transcript 补成现场观测。

独立审查先创建 REVIEW 身份并交付真实审查任务书，采集其公开 reply；主控核实后另 append 本阶段新增审查意见（不是重复提交整份累计文档）：

```json
{"schema_version":1,"event_id":"REVIEW_EVENT","trace_id":"TRACE","dispatch_id":"REVIEW","kind":"review.recorded","observed_at":null,"producer":"controller","evidence_kind":"controller_statement","payload":{"reviewer":"controller (declared)","verdict":"changes_requested"},"links":[{"relation":"based_on","target_event_id":"IMPL_REPLY_END"},{"relation":"based_on","target_event_id":"IMPL_BRIEF"}],"bodies":[{"role":"text","path":"/absolute/review.txt"}]}
```

verdict 只用 passed/changes_requested/inconclusive，也可省略；reviewer 写真实声明的审查者。based_on 可用同链的需求/提议/授权/复用证据、任务书快照、reply.end、已有 review。只引用实际保存的 ID；审查结论由审查者给出，不从 reply 成功码自动生成。

补充决定、返工说明、收尾用 controller.note。先等本任务自己发起的公开 route/start/send/reply 调用返回，自己开的实施/审查会话按项目正常生命周期处理；不为 close 停止主控或用户 agent，也不要求保留的会话全部消失。例如实际收尾后：

```json
{"schema_version":1,"event_id":"CLOSURE","trace_id":"TRACE","dispatch_id":"IMPL","kind":"controller.note","observed_at":null,"producer":"controller","evidence_kind":"controller_statement","payload":{"note_kind":"closure"},"links":[{"relation":"based_on","target_event_id":"REVIEW_EVENT"}],"bodies":[{"role":"text","path":"/absolute/closure.txt"}]}
```

运行 `saddle telemetry append --input /absolute/closure.json`。closure 正文只写实际合并提交、清理、适用构建结果、推送成功/失败/未执行、最终 SHA，未完成步骤如实保留；不能提前记已收尾。note_kind 还可用 review/rework/decision/other；links 的 based_on 允许需求/提议/授权/复用证据、快照、路由 begin/end、reply.end、review、decision。trace 级 note 可省略 dispatch_id；以上纯记录都不填 operation_id。

closure 只是派发级或 trace 级声明，不改变记录状态；正文写清本次收尾覆盖的任务范围。本次任务确实完成并交付且无同任务待决事项时，主控对 **origin=ad_hoc** 保存 `close.json` 并执行 `saddle telemetry trace close --input /absolute/close.json`：

```json
{"schema_version":1,"trace_id":"TRACE","actor":"controller"}
```

stored 或 duplicate 表示已结束，不能重开；未成功就如实报告未能结束。**origin=task 不由主控 close**：绑定方 Drover 在 Accept/Return 业务落盘并尝试记录 transition 后结束，Submit 不结束，主控只写 closure。同任务还等用户决定时不提前结束，决定到来先在同一 trace 记录，再继续或结束。

结束后，后续命令不再携带本次 ID；下一任务未要求就不记录，新要求新 trace。记录文件可保留供审计，不删除任何用户材料；会话恢复时不把已结束的 trace 当作可续写链路。

手工补交旧材料始终是新 event_id、新 recorded_at，正文明确写“事后手工补交”、真实来源及原时间是否未知。确知原时间填 observed_at，需求还填 declared_at；落在未采集时段的声明时间会显示 late_submission。未知时间用 null、在文字中标晚交，不编造时间来触发标记。纠正同类材料可用 supersedes 指旧事件；不能覆盖旧正文/关联，不能补成旧 operation 的 end，也不能让后来授权变成旧 begin 的当时依据。旧 dlog 仅留离线历史，不导入。

已结束的 trace 不再接受补交；新记录要求须新建 trace，旧材料保留原义。

## 7. 查询与两类回执

```sh
saddle telemetry list
saddle telemetry show --id TRACE
saddle telemetry show --id IMPL
saddle telemetry events --trace-id TRACE --dispatch-id IMPL --limit 100
saddle telemetry body --sha256 HASH
```

events 首页返回 upper_seq、next_after_seq、has_more；有下一页时带同一筛选、`--upper-seq N --after-seq N`，直到 has_more=false。body 输出完整原字节，错误在 stderr，不把失败当空正文。TUI 顶部 Telemetry 或 Agents 焦点 `t` 可查询；Drover 的 Telemetry ↗ 只传任务关联，不承载通用查询。关闭总开关仍可读历史，无库查询不建库。

**纯记录**：stdout JSON 中 stored/duplicate（退出0）是记录成功；unavailable（1）存储/正文不可用，invalid（2）字段/关联/文件错误，conflict（3）同 ID 不同内容/绑定占用，disabled（4）全局/链路关闭或 generation 已失效。不自行开开关；纯记录可查 ID 后同内容重交，但不得重做业务来补记录。改内容须新 ID。

disabled 且 error.code=`trace_closed` 表示链路已结束，纯记录不重交。原本合法的旧上下文只令执行入口的 begin/end=disabled，业务照常一次执行，不重发；无效上下文仍会被拒绝，与是否结束无关。close 返回 invalid（包括旧宿主不支持命令）或其他失败时报告“未能结束”，不得重做业务补救；close 无库或未知 trace 返回 invalid，不初始化库。

**执行调用**：业务 stdout/退出码与 stderr 遥测状态分开。agent 前缀为 `saddle-telemetry: `，plugin run 为 `saddle-plugin: `。等待退出且输出收齐后：

1. 只取 stderr **字节0起第一条完整 LF 行**：前缀正确、JSON schema_version=1、final=false、call_id 是合法 UUID v4。
2. 只取完整流**最后一条完整 LF 行**：同前缀/版本、final=true、与首行相同 call_id。不能向后寻找另一个起始行或向前寻找任意 final；末尾有部分行/额外文字也不配对。
3. 配对才采信 executed/outcome、operation_id、begin/end/gaps。缺失、截断、不匹配一律 unknown，不能凭125/127或业务自己输出的同名前缀认定未执行，更不能直调重发。

agent 的125表示入口拒绝、127表示不能启动 Corral，仅配对 executed=false 才确认未执行；Corral 自己也可返回125/127。plugin 的125为拒绝、126可能是已执行后的 panic/非法业务码，也不能单看码判断。配对 error.code=plugin_disabled 才称“插件未启用”；不配对写原因未知。begin/end 的 stored/disabled/unavailable/not_requested/not_reached 等是采集结果，不是业务成功与否。operation 缺 end 不等于没执行；pending 不证明后来送达，reply 的未知只描述回复查询。业务成功、记录失败时保留业务成功；完整记录也不证明任务所有操作都已采集。
