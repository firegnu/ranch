### 必须改

1. **能从本频道停别的仓库的 agent**（`engine.rs:316-323`、`:588-593`）。

### 建议改

1. **提问提醒的线程处理过以后，一直被当成「回答」线程**（`engine.rs:449-480`）。
   - 问题：`thread.question` 处理过后只置 `handled`，从来不清掉，这个线程以后的每句话都被当成回答。实测：回答已送到、这一轮回完、agent 空闲后，在同一线程再说「再做一件事」，结果是：
     - 线程里先说「这条提问已处理过，没再按 Esc；回答排着，等空下来再送」；
     - 接着说「→ paddock/dev（正在干活，这句排在第 1 个，这一轮结束就送）」，其实 agent 是空闲的；
     - 送给 agent 的是「（这是对刚才提问的回答；关闭提问框不表示放弃作答）\n再做一件事」。
   - 确认那句写着「在这个线程接着说就行」，用户很可能接着说。按键不受影响（handled 以后不再按），话也没丢，但线程里的说明和送出的前缀都不对；agent 报 `unknown` 时这句也不送。
   - 改法：回答送出以后（或者框已经不是记下的那个时），把这个线程的 `question` 清掉，后面的话按普通规则走。「同线程连答」只看这时这个线程还有没有回答在排着。加一条用例。
2. **核对没通过、框不是 pony 关的，也加「关闭提问框不表示放弃作答」**（`engine.rs:477-480`）。
   - 问题：框已在电脑上答掉、换了框、人刚操作过，这几种情况 pony 都没按 Esc，回答等空下来才送。这时前缀说「关闭提问框不表示放弃作答」，和事实不符，agent 可能把这句当成对已经关掉的框补的答案。任务书对这种情况写的是「照现有规则排着」。
   - 改法：只在 pony 真的按了 Esc 关框时加这句前缀。核对没通过的不加，或者换成准确的说法，比如「这是你在手机上对刚才提问的回答，提问框已在电脑上处理过」。
3. **合并「这一轮被打断了，没有回复」时，会把别的线程的提示拿走**（`engine.rs:728-740`）。
   - 问题：确认停下时，删掉这个 agent 所有在等回复的话，把「这一轮被打断了，没有回复」接到「停」所在线程的确认句后面。实测：在线程 work 里送「做点事」开了这一轮，再在频道顶层发 `@pony 停`，结果 work 线程只有「→ paddock/main」，之后再没有消息；提示进了顶层「停」开的新线程。提问框也一样：这一轮是 work 线程的话开的，在 Needs you 线程里回答，work 线程就没有下文。改之前 work 线程会收到「被打断」。
   - 改法：只合并 `p.address == action.address` 的那条。别的线程的留给原来的贴回流程：`watch.turn` 已经更新，那条等回复的还在，会照旧在原线程说「被打断」。
4. **`停 <不存在的名字>` 被当成话送给主控**（`engine.rs:316-324`）。
   - 问题：实测 `@pony 停 dev-y`、`@pony 停 paddock/gone` 都回「→ paddock/main」，把「停 dev-y」原样送给了主控。设计稿 3.3 只说名字存在才算指令；但现有路由对全名的规矩是「没有这个 agent 就回『没有 … 这个 agent，没送』，不转给主控」。agent 刚退出时用户很可能这么发；主控本身会用 corral，收到「停 dev-y」可能自己去动那个 agent。
   - 改法：第二个词像 agent 名（含 `/` 或符合 `name_segment`）但不存在时，回「没有 X 这个 agent，没按」，不送；第二个词是中文等别的情况，照旧当普通话。可以和必须改 1 一起改。
5. **提问框回答这一路的提示用了「处理完再送」「框已拒绝」**（`engine.rs:509`、`:707`）。
   - 问题：实测这一路线程里依次是「→ paddock/dev（在等你处理对话框，处理完再送）」「paddock/dev 框已拒绝，会话还在，在这个线程接着说就行」「已送给 paddock/dev（排了 0 分钟）」。用户刚答完题，看到「等你处理对话框」「框已拒绝」会以为答案被拒了。
   - 改法：pony 要关框的回答，排队那句改成「（关掉提问框后就送）」这类说法；确认句在这一路改成「提问框已关，回答这就送过去」。「停」那一路的说法不变。

### 可以不改

1. 「停」只核对 `turn_started`，不核对是不是原来那个框：在 Needs you 线程回「停」时，如果原来的框已在电脑上批准、同一轮又弹了新框，而人操作完已经过了 30 秒，pony 会拒绝新框。这符合「停就是停这一轮」，也在设计稿 3.4 的核对范围内。以后要更严，可以对 Needs you 线程再比一下 `state_started`。
2. 如果崩溃正好发生在落盘之后、按键之前，重启后照常确认，会说「按了 Esc，15 秒后还在干活」，其实没按上。宁可漏按也不重按的取舍是对的，只是这句话不准；概率很低，不改也行。

### 对「拿主意的地方」逐条表态

1. 沿用单线程循环和队列；有待确认的按键时每 1 秒一轮，其余时候 2 秒：同意。

3. 回答只在 `idle` 时送，不沿用普通话在 `unknown` 时直接送：同意。但要配合建议改 1，只管真正的回答，不能扩到这个线程以后的每句话。
4. 回答前缀「这是对刚才提问的回答；关闭提问框不表示放弃作答」：pony 关了框时同意；核对没通过的也加，不同意，见建议改 2。

1. Esc 命令报错时（结果不明），线程里先说「Esc 发送失败或结果不明，没重按」，接着的排队句仍是「关掉提问框后就送」，15 秒后又说「按了 Esc，15 秒后还在等你」（实测）。结果不明时可能确实按上了，超时那句也照实说了还在等你，回答仍排着、只在空闲时送，不影响安全。

## 主控对复核意见的决定

- 复核建议改 1（agent 重开过、或框已不在且空闲时，回答前缀和排队句不准）：本次不改。只在提醒发出后、回答前 agent 被重开或框已答掉这类少见情况出现，按键和送话时机都对；记下，真机用起来碰到再开一件修。
- 可以不改 1：不改。
