# 任务：人按 Esc 打断被委派的 agent 后，主控不再误以为它做完了

**草稿**（用户 10-19 提出）。派之前要用户定：下面「待定」几条。

2026-10-19，ranch/main 起草，待用户看过、定验收。交给谁、几档、路由，派之前照 corral-dispatch 第 3 节再定。
类型：Bug 修复
依据：人在被委派 agent 的窗口里按 Esc 打断它，corral 把这一轮当成结束，主控的 `--after` 提醒照送，回复还可能是上一轮的。本轮修 corral 的这处判断（以及要跟着改的技能文字），不改别的状态规则。
提示：依据证据定位并修复导致问题的原因，保持无关行为不变。

## 用户原话

- 10-19：“我在使用的时候，我发现一个问题，如果被委派的agent正在干活，我按下esc打断了他，这时候，主控会认为它做完了。这个要修复”

## 主控查到的（10-19 读代码，没实测）

- 共用状态机 `crates/corral/src/events.rs`：`Stop`、`StopFailure`、`Interrupt` 三个事件一样处理，都把状态置为 `idle`。只有 `Stop` 会更新 `reply`；`Interrupt` 不动它，`reply` 还是上一轮正常结束时的那段。
- 哪几家会报 `Interrupt`：Codex 有 `Interrupt` 钩子（`agents/codex.rs`）；agy 的 `USER_CANCELED` 记成 `Interrupt`（`agents/agy.rs`）；amp 插件把 `cancelled` 记成 `Interrupt`。Claude Code 没有打断的钩子，被打断后大概要等它自己的 `idle_prompt` 通知才变 `idle`（推测，要实测）。pi、omp 走原始事件，打断时报什么没查。
- `corral send --after` 的提醒（`crates/corral/src/after.rs`）等到 `idle` 就送；人 30 秒内在窗口里打过字时才先等一会儿。打断以后人不再打字，提醒就送了。
- 所以主控收到「这一轮结束了」，去看 `reply`：
  - 上一轮的回复最后一行就是 DONE 的（比如返工、复核那一轮被打断），主控会当成做完了；
  - 不是 DONE 的，照 corral-dispatch 技能，主控也会当成「停了」去处理，而人其实还要接着用它。
- 10-19 的一个实例：R21 时用户在 ranch/dev-r21-1（Codex）的窗口里打断它、问了一句「你在做什么？」，提醒照送到主控，主控就去看结果了（用户：“等，他还没干完”）。

## 要做的

被人打断的那一轮，corral 不再当成一轮正常结束报给主控；主控也不会把上一轮的回复当成这一轮的。具体怎么表示，见「待定」。

## 待定（派之前问用户）

1. 打断之后提醒怎么办。主控建议：提醒不送，接着等这个 agent 下一次正常结束一轮（超时照旧）。另一个办法是照送，但写明「被人打断了」。
2. 状态和回复怎么表示。主控建议：
   - `status` 加一个兼容的新字段，说明最近这一轮是被打断的；
   - `wait` 碰到打断，返回新的结果值 `interrupted`，不返回 `idle`；
   - 被打断的一轮，`reply` 不再给出上一轮的回复。
   
   这三样都改公开约定，要写清对 paddock 的影响。
3. 范围：哪几家要修。主控建议：报 `Interrupt` 的几家先修；Claude Code、pi、omp 先实测打断后各报什么，再定修不修。
4. 验收（主控建议，待用户定）：在一个测试 agent 干活时按 Esc 打断，主控挂的 `--after` 提醒不送、`wait` 不返回 `idle`、`reply` 不给出上一轮的回复；之后人在窗口里让它接着干，正常结束这一轮时提醒照送。

## 不要做

- 不改别的状态规则（`blocked`、`starting` 等）。
- 不碰用户的 agent；实测用自己开的 `ranch/test-<名字>`（`--label role=test`），用完 `corral stop`。
- 不按名字或路径批量杀进程。
