### 意见

1. **必须改**：`crates/corral/src/agents/canter.rs:106`（`Translation::event`；兜底的 `_ => "StopFailure"` 在 `:199`）
   - 问题：canter 终端的 Esc 带 `retract`（canter DESIGN P2-59「Esc 撤回」，协议 README 152–158 行）。模型还没开口时，事件是 `session.status working` → `item.completed`（userMessage）→ `turn.retracted` → `session.status idle`，**没有 `turn.completed`**（临时检查实测 seq 13–16）。翻译不认 `turn.retracted`，`turn` 停在 `"running"`，到 idle 时落进兜底，写成 `StopFailure`。实测：`state:"idle"`、`interrupted:false`、`last_event:"StopFailure"`；`corral wait` 返回 `idle`；`corral reply` 以 `ok:true` 返回**上一轮**的回复；`interaction.running` 一直是 `true`。这违反 CONTRACT 第 117–118 行（被打断的一轮 `wait` 报 `interrupted`，`reply` 报 `no_reply`、不给上一轮的回复），也就是任务「要做的」第 2、3 条没做到。派活方发完话、人马上按 Esc，或者 pony 的「打断」按得早，都会碰到；方案第 9 节让 pony 对 canter 设 `require_interrupted`，这时会一直等不到 `interrupted:true`。现有真 canter 测试的假模型（`tests/canter.rs:824` 起）总是先吐一个字再挂住，只走得到普通打断，所以没测出来。
   - 改法：加一个分支 `"turn.retracted" => { self.running = false; self.turn = Some("interrupted".into()); None }`，后面的 idle 就会写 `Interrupt`（实测顺序是先 retracted 后 idle）。照上面的真实帧序补一个纯函数测试；真 canter 测试的假模型加一种「出字之前就挂住」的提问，按 Esc 后断言 `interrupted:true`、`reply` 报 `no_reply`。

2. **建议改**：`canter.rs:83`（`dialog()` 在框全关时写 `PostToolUse`）、`canter.rs:197`（idle 时 `turn` 为空就什么都不写）、`canter.rs:181`、`canter.rs:741`
   - 问题：框一关就回到 working，不看有没有轮在跑。canter 的子 agent 由 `spawn_agent` 立即返回，主会话空闲时它还能接着跑（canter DESIGN 503、515、521 行）；通用子 agent 要批准时，父流会来 `agent.request.opened`，corral 报 blocked，这是对的。批准以后来 `agent.request.resolved`，写的是 `PostToolUse`，corral 变成 working；可主会话一直是 idle，之后再没有能把 corral 拉回 idle 的事件，要等子 agent 做完、叫醒主 agent 的那一轮结束才恢复。用户在 `/agents` 里按 s 停掉这个子 agent 时不会叫醒主 agent（DESIGN 535 行），corral 就一直报 working：`send` 退回 7，`wait` 等不到 idle。另外两处同根：`session.status working` 不带轮（`:181`）之后再来 idle，也一样卡住；`initialize` 补写的那条事件（`:741`）没有同步 `translation.state`。派活默认 `--yolo`，平时很少弹批准框，所以列为建议。
   - 改法：框全关并且 `!self.running`（没有轮在跑）时，写 `{"ev":"Stop","idle_only":true}` 代替 `PostToolUse`；`session.status idle` 到来时 `turn` 为空但 `self.state != "idle"`，也写同一条。按 `events.rs` 现有规则，`idle_only` 的 Stop 只把状态改回 idle，不动 `reply` 和 `interrupted`。这一条没实测，联调「子 agent 的批准」时核对。

3. **建议改**（重点 5：上限和超时）：`canter.rs:594`、`:900`、`:974`、`:605`、`:586`、`:630`、`:658`，`pen.rs:876`
   - 问题：
     - SSE 帧缓冲（`:594`）、chunk 累积（`:900`）、JSON 正文（`:974`）都没有字节上限。对端一直不发帧尾，或者报一个极大的 chunk 长度，pen 的内存会一直涨。
     - 碰到坏 JSON（`:605`）就断开重连，再从同一个 seq 收到同一帧，循环不停；每次连上都 `contact()`（`:586`），`last_contact` 一直是新的，永远不会报 `unknown`，状态停在旧值。`contact()` 还会清掉 `error`，所以 `pen.log` 每秒多记一行。
     - 会话文件和 `server.json` 用 `fs::read` 读（`:630`、`:658`）：跟随符号链接，不限大小，碰上 FIFO 会一直阻塞。
     - pen 退出只等 `w.finished()`（`pen.rs:876`），pen 这边没有自己的上限。线程一旦卡住（比如上面那种阻塞读），pen 就不退出，`corral stop` 要等到 `--timeout` 才报超时。
     - 这些都要 canter 写出异常的文件或数据才会碰到，所以不算必须改。正常路径上每次请求都有上界，停线程实测最多约 1.5 秒。
   - 改法：单帧、单个 chunk、JSON 正文都设上限（比如 64 MiB，留足 canter 一帧的实际大小），超了按出错处理；解析不了的帧按它的 `id:` 推进游标、记一次日志，或者「连上了但没收到一帧合法数据」时不刷新 `last_contact`。两个文件先确认是普通文件，再用 `take` 限长读（比如 64 KiB）。pen 退出加一个自己的上限（比如 agent 退出后 15 秒），到时把跟过的会话全写进 `remaining_sessions`，照常退出。

4. **建议改**：`pen.rs:836`、`canter.rs:516`
   - 问题：
     - 判断要不要重起线程用的是 `watcher.finished()`。收尾函数一置 `shared.finished` 它就为真，这时线程还没真正退出。旧的 `Running` 在这时被丢掉，JoinHandle 跟着丢，线程成了游离线程。紧接着同一轮循环里如果有 `pending_upgrade`，只停新线程就 fork，和「fork 前要等 JoinHandle 确认线程没了」（`watcher.rs:94`）的约定不符。窗口只有几微秒，还要先有一次「停不下」，实际很难碰到。
     - 重起后的新线程会把收尾再走一遍，最多再等 12 秒。
     - 退出分支对当前会话也调了 `track()`（`:516`），把它的 `initialized` 置回 false；之后重起或升级，会多写一条 `SessionStart`。
   - 改法：重起只看 JoinHandle（`thread.is_finished()`），已经在收尾（`exiting`）就不再重起；退出分支只在会话和 `cursor.current` 不同时才 `track()`。

5. **建议改**：`cli.rs:723`、`pen.rs:632`
   - 问题：`resume` 也一律报 `unsupported_kind`。部署前的旧 corral 把 canter 当未知程序处理，`pause`（或 paddock 的「全部暂停」）会真的冻住 canter 终端，连带冻住它起的共用服务端（方案第 7 节、实测 16）。部署新 CLI 以后，或者这个 pen 升级以后，这个 agent 就再也 `resume` 不了，用户的所有 canter 会话一起卡住，只能 `corral stop`。
   - 改法：只在 pen 报 `paused:false` 时拒绝 `resume`：CLI 先看 status 里的 `paused`；pen 端 `self.paused.is_some()` 时照常 resume。不改的话，至少在部署说明里写一句「被旧 pen 冻住的 canter 用 `corral stop` 解开」。

6. **建议改**（文档）：`cli.rs:599`
   - 问题：`corral upgrade NAME` 换到跟不了 canter 的程序时，新加了 `{"ok":false,"error":"incompatible",…}`、退出码 9（`--all` 时只出现在 `results` 里）。这和别的升级失败不一样，别的都是 `result:"failed"`、错误嵌在结果里。CONTRACT「canter（R56）」没写这一点。
   - 改法：在 CONTRACT 那一节加一句。对 paddock 没影响（paddock 不调 upgrade），主控部署时用得上。

7. **可以不改**：`canter.rs:513`
   - 问题：agent 退出后，线程直接去确认会话关没关，不再读事件流，`session.status closed` 多半来不及翻成 `SessionEnd`。确认期间（服务端连不上时最多 12 秒），`status` 还报退出前的 idle 或 working。正常情况下会话关得很快，影响小。
   - 改法：进退出分支时，给当前会话补写一条 `SessionEnd`。

8. **可以不改**（联调时核对）：`canter.rs:686`
   - 问题：新会话一律从 `after=0` 补发。`/fork` 出来的会话「显示历史保留，使用既有事件重建」（canter DESIGN 33 行），补发会把源会话里做完的轮重算一遍，`input_count`、`last_prompt` 跟着变；`reply` 仍是这个会话最新的回复，内容不算错。别的客户端在本实例启动后新建、再被 `/resume` 进来的会话，情况相同。
   - 改法：联调时 `/fork` 一次看看结果。真要改，可以跳过时间戳早于会话 `createdAt` 的帧。
