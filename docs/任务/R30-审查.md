### 1. 必须改：Claude／Codex 将 key 明文暴露在进程参数中

- 位置：`crates/fence/data/agents/claude.toml:8`、`data/agents/codex.toml:9`，以及 `src/runs.rs:205`。
- 问题：`mcp::resolve` 把 key 序列化进 header 后，两份模板分别将它放进 `--mcp-config` 的 JSON 和 `-c` 的 TOML。`runs::run` 原样传给墙外 runner，runner 又把相同参数交给启动 shell 和客户端。具有进程参数查看权限的本机其他进程能取得完整 key，不需要读取 0600 的源文件，也不需要模型主动泄露。现有带 key 回归已经证明这两家的 argv 含明文；本次假参数的 `ps` 检查进一步确认了本机同 UID 的可见性，没有声称验证跨 UID 访问。用户接受的是接收 key 的 agent 能看到它，不能据此忽略审查任务明确要求检查的进程参数暴露。
- 改法：Claude 使用现有 `[mcp.files]` 写 0600 的 JSON，再让 `--mcp-config` 只带路径；官方 CLI 明确支持文件形式，见 [Claude CLI reference](https://code.claude.com/docs/en/cli-reference)。Codex 可继续用随机 server 名，但 `-c` 只放 `env_http_headers` 的「请求头名 → 本次专用环境变量名」映射，真实 header 由 fence 通过 `Command::env` 单独传给子进程；不要把它放回可输出的 `resolved.value["env"]` 或 shell 的 `VAR=秘密` 参数。此字段由 [OpenAI MCP 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) 明确支持。专用变量只由对应 server 引用，保留用户已经接受的进程内可见性边界。
- 修复验证：延用合成 runner，检查 key 正确进入文件或专用环境变量、所有启动 argv 不含 key、其他 server 和 fence 记录不含 key；保留 Codex 随机名断言。

### 2. 必须改：遗漏 pi 的 `$VAR` 展开，会把其他环境凭证当作 MCP key 发送

- 位置：`crates/fence/src/mcp.rs:158–164`、`data/agents/pi.toml:13`。
- 问题：当前仅拒绝以 `!` 开头或含 `${` 的 header，仍接受 `$REVIEW_OTHER_TOKEN`、`Token $REVIEW_OTHER_TOKEN` 和 `abc$$def`。pi 1.3.0 的 `dist/extensions/mcp/runtime.js:51–56` 在建立 HTTP transport 前调用 `resolveHeadersOrThrow`；`dist/core/resolve-config-value.js:21–72` 同时识别 `$VAR`、`${VAR}`，且把 `$$`／`$!` 当作转义。JSON 转义不会阻止客户端做这一步解释。
- 具体触发条件：假设源 key 的字面内容为 `$REVIEW_OTHER_TOKEN`，继承环境中该变量为 `fake-other-provider-secret`。fence 会接受它并原样写入 pi 扩展；pi 最终给搜索服务的 header 值却是 `fake-other-provider-secret`。换成真实的其他服务商环境凭证名就是错误发送凭证；不需要 agent 主动调用工具读取环境。变量不存在时会连接失败，`$$` 则会静默改变合法 ASCII key。因而“拒绝客户端插值”和“按字面携带指定 key”的完成声明不成立。
- 改法：在保持当前“仅支持字面值”的设计下，最小修复是统一拒绝组合后的 header 值中的 `$`，并同步 README；或者提供经各客户端语义验证的字面值编码，但不能只靠 JSON/TOML 字符串转义。保留已有 `!`、控制字符和空值检查。
- 修复验证：只用假变量、假 key，覆盖 `$VAR`、`${VAR}`、`$$` 的拒绝或严格字面传递；不用真实客户端或真实服务。现有合成 runner 只检查生成文本，不能证明客户端不会二次展开。

### 3. 必须改：切换选择会解除未选中 key 的外部链接目标禁读

- 位置：`crates/fence/src/mcp.rs:118–143`、`src/rules.rs:549–558`。
- 问题：强制禁读集合只包含 `keys` 目录及**本次选中**的 key 路径。解析一个目录的真实路径不会遍历其中各文件的符号链接；因此未选中 key 指向目录外的目标完全不在集合里。这个缺口也存在于 `mcp = []` 时。普通目录内的未选中 key 仍受目录禁读保护，问题限定于外部链接目标。
- 具体触发条件：`$FENCE_HOME/keys/research -> /private/tmp/project/provider-token.txt`，工作目录为 `/private/tmp/project`，`local.toml` 从 `mcp = ["research"]` 改为 `mcp = ["exa"]`。前一次规则会禁止读取 `provider-token.txt`；后一次只解析 `keys` 和 `keys/exa`，该目标不再被禁止，墙内可按原本的工作目录读权限直接读到它。默认 HOME 禁读也救不了 HOME 外的目标。换服务商本是本轮主要功能，不应连带解除旧 key 的保护；它也不属于“已交给本次 agent 的 key 可见”这一接受的局限。
- 改法：源 key 的路径保护与 MCP 选择分开。枚举 `keys/` 下的 key 文件元数据，把所有符号链接的真实目标加入禁读，仍只读取选中服务器的 key 内容；`check` 可只检查元数据，继续不读 key 内容。若不支持外置链接目标，则应明确拒绝这种布置，不能默默失去保护。
- 修复验证：用假文件和外部符号链接，在选中、改选、空选择时都断言目标仍在禁读集合；选中 key 的单链接、目录链接和 HOME 外／工作目录内场景可沿用同一夹具。现有 `tests/cli.rs:1058–1063` 只断言目录名在列表中，覆盖不到此缺口。
