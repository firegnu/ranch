     - 实测：插话等待中途发 `corral keys lab/main text:z`，这条命令等了 2.7 秒，要等插话放弃后才写出去。
     - `keys` 不算真人输入（pen 只把接入窗口里的打字记成真人输入），所以不会让插话放弃。如果有人用 `keys` 按 Esc 打断，或者看到框后用按键回答，要等最多 3 秒，而且若这时正好等到空隙，插话的回车会先按下去。
     - 等待前这个排队最多 0.3 秒，现在最多 3.3 秒。
   - 改法：等空隙时，如果队列后面已经排了非插话的块，就放弃提交、留草稿（reason 如 `input_queued`），或者把 `keys` 请求也当作放弃的理由。不改的话，至少在 CONTRACT 写明「插话等待期间，后来的 keys／send 排在它后面，最多晚约 3 秒」。

2. **建议改：调用方在等待中途断开，回车仍会按下去**
   - 位置：同上，等空隙分支不看发起插话的客户端还在不在。
   - 问题：实测：等待中把 `corral send --steer` 进程杀掉，过一会儿回车照样按下，`recent_sends` 记为 `written`。以前这个时间窗只有 0.3 秒，现在最多 3.3 秒，调用方等不及按 Ctrl-C 的情况更容易碰到。人以为取消了，消息其实提交了。不会误按菜单，状态检查照常起作用；能用 `corral status` 的 `recent_sends` 按 request_id 查到。
   - 改法：等空隙期间，发现 guard 里的客户端已经断开，就放弃提交、留草稿，记 `draft`；或者在 CONTRACT 写明「中途断开不撤回，按 request_id 查 recent_sends」。

3. **建议改（和这次改动无关，以前就有，低优先）：pen 控制输入间隔用的是系统时钟**

   - 问题：系统时钟往回调时，队列里的输入会停住，停多久就等于回调了多久。普通 send 的 0.3 秒间隔、keys 的延迟都受影响。这次等空隙的截止时间用的是单调时钟，没这个问题。
   - 改法：输入间隔改用单调时钟。注意 `next_input` 是 upgrade 快照里的字段，改的时候要保持快照兼容（比如快照里照旧存一个时间点，pen 内部改用 `Instant` 计算）。

  - 实测：一直有事件、等到超时的 3.3 秒里，pen 回了 110 次 read 请求，最慢不到 1 ms。
  - 每 50 ms 算一次状态，最多约 60 次，读的都是本地小文件（事件按 cursor 增量读，转录只读尾巴 64KB）。
- **blocked 时不按提交键**：
  - 放行要同时满足：`steer_status` 通过（没暂停、近 30 秒没真人输入、不在停止、状态是 idle 或这家能插话的 working）；证据和上次看到的一样；已经安静满 300 ms。
  - 变成 blocked、starting，被暂停、有真人输入或正在停止时，`steer_status` 直接报错，立刻留草稿。working 变 idle 时报 `state_changed`。
  - 原本 idle 的请求变成 working 时不会借机插话（`/model` 测试覆盖）。
  - 测试 `block_during_gap` 覆盖了等待中变 blocked 立刻放弃。
- **超时和计时**：
  - 截止时间用单调时钟，从第一次看到变化起算 3 秒，新事件不续期。
  - 安静时长从「看到变化的时刻」算起，这个时刻比事件实际发生得晚，只会更保守。
  - 实测：最后一个事件之后 303–353 ms 才按回车，所以计时会按新事件重新开始；一直有事件时总共 3.311 秒（0.3 + 3 + 轮询）。
  - `--timeout` 在 pen 回复之后才开始算，和契约一致。
- **普通 send、keys、接入输入**：`check_steer` 遇到不是插话的块仍然第一步就返回 false，字节和顺序都没变；排在等待中插话后面的会被拖住，见第 1 条。
  - 待写插话和 upgrade 的互斥窗口从 0.3 秒变成最多 3.3 秒，upgrade 仍是立刻被拒、不会卡住。
