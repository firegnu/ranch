### 意见

1. **建议改：`draft_not_submitted` 用退出码 7，和 `not_idle` 同码**
   - 位置：`crates/corral/src/cli.rs` `deliver` 里 `Some("not_idle" | "draft_not_submitted") => 7`；`docs/CONTRACT.md` R57b 表格；`crates/corral/resources/AGENT_USAGE.md`、`SKILL.md`。
   - 问题：7 现在的处理是「先 wait 再 send」，两份技能里的退出码表也这么写。只看退出码的调用方遇到 7 会等空闲后再送一遍，可输入框里还留着草稿，两段话会合并提交，修正被送两次。现在还不出错：pony 按（退出码, error）成对匹配，`(7,"draft_not_submitted")` 不会走「放回队首」（`crates/pony/src/core/engine.rs` 约 1914 行）；pony、paddock 也还没用 `--steer`。契约写清了 error 名和处理，但技能表里 7 那一行没变，仍是「先 wait 再 send」。
   - 改法：改成 3，error 仍叫 `draft_not_submitted`。3 现在的意思就是「已写出、没确认，不重送、不补回车」，处理完全一样。这样 7 永远表示「本次没写入，等空闲可以重送」，3 永远表示「写进去了，别重送」。也可以另开新码，但 3 最省事。

2. **建议改：把留草稿有多常见写进文档；证据变化另起一个 reason 名**
   - 位置：`crates/corral/src/pen/steer.rs` 的 `evidence()`，以及 `check_steer` 里的 `Error::new(7, "not_idle", "state evidence changed before writing input")`；`docs/DESIGN.md`「干活时显式插话（R57b）」；`docs/CONTRACT.md`。
   - 问题：证据里有 `last_event`/`last_event_at`，所以 working 时的任何工具事件都会让提交前的复查失败。
     - 实测：临时给合成 agent 加了一种模式，粘贴后只追加一条 `PostToolUse`，状态还是 working。结果 exit 7、`draft_not_submitted`、`reason:"not_idle"`、`state:"working"`，没按回车。复现完已撤掉，worktree 是干净的。
     - 频率：用本机 4 个 agent 的事件日志估算（只取 `ev`、`t`、`session_id` 字段，没读内容，没对 agent 发任何请求）。working 期间，随便取一个 0.35 秒窗口，里面落进主会话事件的时间占比：
       - Codex 开发 agent：2.2%
       - 三个 Claude Code：5.2%、6.4%、11.9%
       - 窗口按 0.5 秒算：3.0%–15.4%

       也就是工具调用密集时，大约每 8～20 次插话有一次留下草稿。三家实测都是在 sleep 45 这种没有事件的时段做的，所以没测出来。
     - 不建议放宽证据：去掉 `PostToolUse` 只降三分之一左右（1.5%–7.8%）。剩下的大头是 `PreToolUse`，而它正是审批框弹出前的那一下，留着是对的。
     - 后果：留下的草稿会在下一次 send 时一起提交（`merged_with_draft:true`），旧的修正会跟着新消息一起进去。
     - reason 名会误导：写的是 `not_idle`，可对方明明在 working、正是能插话的状态，调用方会读成「对方不空闲」。
   - 改法：
     - 证据不变。
     - DESIGN 和 CONTRACT 写明：工具调用频繁时 `draft_not_submitted` 不算少见（按本机日志估计 2%–12%）。技能里说清楚：留下的草稿会被下一次 send 合并提交，要先让人接入核对或清掉。
     - 证据变了但状态还能插话时，reason 换一个名字（比如 `state_changed`），和真正的 `not_idle` 分开。
     - 如果用户嫌留草稿太多，可以另外问用户要不要「证据一变，就再等一个安静窗口后复查」。这会让误按的机会略多一点，属于改需求，这一轮不做。

3. **建议改：pen 里算状态那一段加 panic 防护**
   - 位置：`crates/corral/src/pen/steer.rs` 的 `steer_status`，它调用 `cli::status_from_pen`。
   - 问题：
     - 风险：`events::read`、`raw::apply_raw`、Claude 读转录尾巴这几段，以前只在 CLI 进程里跑，出问题只是一条命令失败。现在在 pen 主循环里跑，一旦 panic，pen 会退出，agent 也会被一起带走。
     - 没找到正常数据下能触发的 panic：出错都走 `Result`，返回给调用方，pen 不会卡住；几处 `unwrap` 都有前提保证（cursor 字段先检查过，raw 会话的结构由同一份代码写入）。
     - 开销：读转录有 64KB 上限，读事件按 cursor 增量读。每次插话在 pen 里算 3 次状态，都是本地小文件，不会让 pen 卡住。
     - pen 解析终端时已经用了 `catch_unwind`（`screen.rs`），这里照样包一层，成本很低。
   - 改法：在 `steer_status` 里用 `catch_unwind(AssertUnwindSafe(..))` 包住 `status_from_pen`。万一 panic，就当作检查失败：正文前按 rejected 返回，提交前按 draft 返回。

4. **可以不改：插话和 upgrade 的互斥**
   - 位置：`crates/corral/src/pen/upgrade.rs` 的 `prepare_upgrade` 新加的那条。
   - 问题：
     - 不会卡住 upgrade：插话的块最多在队列里待 0.3 秒多一点。这期间 upgrade 会立刻被拒，CLI 的 `upgrade::one` 收到 `ok:false` 就报这个 agent failed，不等待也不重试，新旧 CLI 都这样。
     - 回复不会丢：插话一直不进快照（guard 带 `serde(skip)`，SCHEMA 不变）。
     - 唯一的代价：`corral upgrade --all` 刚好撞上时会多一条 failed，重跑就行。
     - 小不一致：这条新的 `upgrade_busy` 回复没带 `upgrade` 字段，另外两条带。现在没有调用方读这个字段。
   - 改法：要的话补上 `"upgrade":self.upgrade.public()`。

5. **可以不改：未知程序用 `--steer` 时的提示**
   - 位置：`steer_status` 里的 `Some("working" | "unknown")`。
   - 问题：未知程序永远不会是 idle，所以 `--steer` 一律报 `unsupported_steer`，提示「wait for idle and use ordinary send」，可它等不到 idle。canter 的观察器失联时状态也是 unknown，也走这条。不影响安全，调用方直接用普通 send 就行。
