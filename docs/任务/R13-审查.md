## 重点看

1. **信任列表会不会伤到用户的配置**（`trust.rs`）：
   - 只删 corral 记下的条目，用户原有的、或用户后来自己点信任加的，任何路径下都不会被删；
   - 文件不存在、不是 JSON 对象、字段类型不对时一字不写；写入是原子的，失败不留半截文件，权限保留；
   - 符号链接、路径规范化（如 macOS 的 `/tmp` → `/private/tmp`）会不会让「上级目录已信任」判错，或加进去的路径 agy 认不出。
2. **并发和残留**：多个 pen 同时加删、两个 agent 共用一个目录、pen 被强杀、`corral upgrade` 交接 pen（旧 pen `_exit`、新 pen 接管）时，条目会不会丢、删早了或永远删不掉。`alive` 用 `meta.json` 的实例和 `agent_pid` 判断活着，有没有漏洞。
3. **会话认领**（`events.rs`）：只对声明了的适配器生效，别家的状态机完全不变；认领后再来的 `SessionStart` 照旧换主会话；会不会把子 agent 或别的目录的会话误认成主会话；游标里积压的旧事件补算顺序对不对。
4. **pen 里的调用点**：`trust::add` 出错不影响启动；`trust::remove` 只在 agent 真正退出后调用；不会阻塞 pen（加锁等待）到影响 agent。
5. **对 paddock 和旧版 corral 兼容**：CONTRACT 的说法和实现一致；旧版 corral 同时在用时不出错。

1. **启动中的实例被另一个 pen 当成残留清掉。**

   - 问题：实际顺序是 A 写信任条目并放开 trust 锁，然后 spawn agent，最后才写 `meta.json`。B 在中间进入 `add_in` 时，`alive(A)` 因没有元数据返回 false，删掉 A 的信任条目和记录。A 继续启动后可能重新弹框；两个 agent 用同一个目录时，也可能只留下 B 的引用，B 一退出就把仍在运行的 A 所需条目删掉。现有 `concurrent_pens_lose_no_entry` 预先给全部实例写了 `meta.json`，绕开了真实窗口。

2. **缺输入钩子时，认领成功仍被公开状态改回 `starting`。**

   - 验证：两个临时测试直接调用真实 `cli::status`，用临时 Unix socket 合成 pen 状态，不启动 agent。`public_state_recovers_when_only_tool_and_stop_hooks_return` 和 `public_state_recovers_after_more_than_fifty_pending_events` 均已读到 `DONE`，公开状态却为 `starting`，期望 `idle` 的断言失败。
   - 改法：让首句保护区分“只有会话开始、首句尚未处理”和“已认领并有工具/结束事件”，只为声明认领的适配器放行后者；不要靠捏造输入事件或计数解决。补测公开 status/wait 路径和已有长游标。

3. **整份配置按旧快照写回，会覆盖用户或 agy 的并发修改。**
   - 位置：`crates/corral/src/trust.rs:98–110,127–148,197–228`。
   - 问题：`List` 保存完整 JSON，之后无条件 rename 覆盖；corral 的私有 flock 不约束 agy 或用户编辑器。在 read 与 rename 之间，用户增加的信任目录和其他设置都会被旧文档抹掉。“原子写”只保证没有半截文件，不能保证不丢更新。

4. **`settings.json` 是符号链接时，会被直接替换成普通文件。**

5. **配置和所有权账本分两步提交，失败后会永久失去清理能力。**
   - 位置：`crates/corral/src/trust.rs:228–233,236–246`。
   - 问题：add 先改 settings，后写 trust.json；第二步失败或中间被杀，新增条目就没有所有权记录。remove 反过来先删记录，后改 settings；后一步失败或中间被杀，同样留下无法识别的条目。以后 add 会把它视为用户原有信任，永不清理。remove 遇到配置暂时读不了时也会先丢记录。这违背“退出后删、残留能清”的目标。
   - 验证：`failed_add_record_write_does_not_leave_unowned_trust` 让账本落盘失败，settings 已加入路径却无账可清；`failed_remove_keeps_ownership_for_a_retry` 让配置写入失败，解除故障后重试 remove，路径仍在。两条均因残留断言失败。
   - 改法：采用可恢复的记录顺序/操作状态，配置写失败时保留足够的所有权与重试信息；启动失败也回收。不能只把两次写的先后顺序交换，因为反方向的中断仍会出错。覆盖写失败和两次提交之间的恢复。

6. **旧所有权记录会删掉用户后来重新授予的信任。**
   - 位置：`crates/corral/src/trust.rs:153–175,187–194`。
   - 问题：记录只表示“以前加过这个路径”，不能证明现在列表里的同名值仍是那次添加。实例已死但残留未清时，用户先取消、后来通过 agy 再次信任同一目录；下次 add 清理旧记录，会把用户新授予的条目删掉。`filter(|p| p != path)` 还会删除所有同名条目。初始就由用户信任的用例通过，不代表后来的人工信任也安全。
   - 验证：临时测试 `user_retrust_after_our_instance_is_gone_is_not_removed` 按上述顺序修改临时列表，后续 add 删掉了用户重新加入的路径，断言失败。
   - 改法：不能仅凭路径字符串保留无限期删除权。需要能辨别外部改写后所有权是否仍成立的协议；无法确认时保留用户条目、放弃旧删除权。现有列表没有条目来源标记，若这与自动清理的保证不能同时实现，应把限制及替代方案交用户决定，不能在文档中继续保证“用户后来自己点过的也一概不删”。

7. **不同 `CORRAL_HOME` 共用同一份 agy 配置时，会删早或互相覆盖。**
   - 位置：`crates/corral/src/trust.rs:22–24,41–54,161–165,210–215`。
   - 问题：配置由 HOME 决定，锁与引用账本由 CORRAL_HOME 决定，保护范围不一致。即使完全串行：根 A 给目录加信任，根 B 的 agent 在同目录启动时把它当用户原有条目而不记引用；A 一退出就删除 B 仍在使用的信任。并行加不同目录时两把锁也互不排斥，存在覆盖窗口。
   - 验证：`same_settings_shared_by_two_corral_homes_stays_trusted` 用两个隔离状态根、同一个临时 settings，两个实例都标记存活；A.remove 后目录消失，断言失败。
   - 改法：互斥与所有权跟随实际配置文件的规范化身份，共享同一配置的 corral 必须共用同一套协调记录；记录同时携带各实例的状态根。若明确不支持这种组合，应在修改配置前检测并安全退出该功能，而不是无保护地继续写。

### 建议改

8. **给 trust 锁等待设上限。**
   - 位置：`crates/corral/src/trust.rs:54`；`crates/corral/src/pen.rs:784,720`。
   - 问题：阻塞式 `LOCK_EX` 没有截止时间。锁持有者被暂停或文件系统卡住时，新 pen 可以一直等；启动客户端 25 秒后报失败，pen 仍可能在锁恢复后继续启动。退出路径也会等，延迟完成通知。正常短锁内没有发现持有到整个 agent 生命周期的情况。

9. **按 agent 最终使用的 HOME 定位配置。**
   - 位置：`crates/corral/src/pen.rs:777–789,835–839`；`crates/corral/src/trust.rs:22,36–37`；`crates/corral/src/environment.rs` 的 extra 环境合并。

10. **残留清理不要只靠 PID 存在判定。**

    - 改法：结合名字锁/pen 所有权和可校验的进程身份来判定；升级交接期间保留原实例身份，不把旧 pen 退出当 agent 退出。这里没有把操作系统 PID 复用做成新的覆盖矩阵。
