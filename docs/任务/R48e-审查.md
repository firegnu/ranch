### 意见

1. **建议改（另开任务，先问用户）：同时跑 `corral ls` 时，`corral stop` 拿不到退出记录，有残留也不报 `remaining_pids`。**
   - 位置：`crates/corral/src/cli.rs` 里 `stop` 的等待循环，锁放开后才读 exit.json；`crates/corral/src/state.rs` 里 `list()` 的清理，status 失败且拿得到锁时，会把整个目录删掉，包括 exit.json。
   - 现象：pen 一放锁，`ls` 就可能抢在 `stop` 下一次检查（每 50 ms 一次）之前删掉 exit.json，于是 `stop` 输出 `"exit_code":null,"stopped_by":null`，`remaining_pids` 也没有。paddock 侧栏默认每 1 秒刷新一次 `corral ls`（`refresh_ms = 1000`），pony 也调 `ls`。用户平时开着 paddock，实际用的时候会碰上。
   - 复现：
     - 用真程序：隔离 HOME、CORRAL_HOME，`env -i`，循环做 `corral start t/x -- /bin/cat` 再 `corral stop t/x`。后台每秒跑一次 `corral ls` 时，200 次里有 8 次（4%）`exit_code`、`stopped_by` 都是 null。`ls` 一刻不停地跑时，40 次全是 null。不跑 `ls` 时 20 次全正常（`-1`、`SIGHUP`）。
     - 针对 `remaining_pids`：在 dev 的 `final_kill_wait_is_bounded_and_records_remaining_processes` 里，`drop(lock);` 之后跑一次 `corral ls`（用同一套隔离的 HOME、CORRAL_HOME）。CLI 子进程的输出变成 `{"exit_code":null,"stopped_by":null,…}`，没有 `remaining_pids`，而那个 `/bin/sleep` 还活着。
   - 为什么不算必须改：
     - 这个竞争 R48e 之前就有，所有 agent 的 `exit_code`、`stopped_by` 一直会这样丢；R48e 没有让任何情况变得更差。
     - 碰上时 `stopped_by` 一定是 null，调用方看得出“没取到退出记录”，不会被误告知“停干净了”。
     - 真要修，得动所有 agent 共用的等待循环，超出了本任务「不改 Kimi 以外 agent 的停止逻辑」的范围。
   - 改法：
     - 现在就能顺手做（只改 CONTRACT）：在 Kimi `stop` 那条补一句「`stopped_by` 为 `null` 表示没取到这次的退出记录，这时不能因为没有 `remaining_pids` 就认为没有残留」。
     - 另开任务修：`stop` 的等待循环里，每次连不上 socket 就读一次 exit.json，记下 instance 匹配的那份；锁放开后如果再读不到，就用记下的。pen 是先写 exit.json、再删 socket 和放锁的，`ls` 又必须先拿到锁才能删，所以连不上时读到的一定是这次的完整记录。正常情况下输出不变，只是碰上竞争时不再丢。测试可以先用上面加一次 `ls` 的写法做出失败。这样会改到所有 agent 碰上竞争时的 `stop` 输出（null 变成真实值），按规矩先问用户。
2. **可以不改：Kimi 有残留时 `stop` 要 8 秒以上，`--timeout` 不到约 8 秒会先报 `timeout`，看不到 `remaining_pids`。**
   - 位置：`cli.rs` 里 `stop` 的 `--timeout`。Kimi 的停止顺序是：TERM，等 3 秒，KILL，再最多等 5 秒。
   - 影响：默认 90 秒，paddock 和技能都不传 `--timeout`，平时碰不到，只有自己传短超时的调用方才会碰上。到点后 pen 照样写 exit.json，只是前端看不到。
   - 改法（要做的话）：在 CONTRACT 那条补一句「Kimi 有残留时，停止约需 8 秒，`--timeout` 要留够」。
