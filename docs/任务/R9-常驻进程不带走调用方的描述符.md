## 问题
- **现象**：R8 期间 `cargo test --all-targets` 里 `protocol` 的 `concurrent_unique_starts_and_listing_preserve_live_locks` 卡住不返回（HANDOFF「悬着」里记过一次，之后没复现）。这个测试是 3 个线程同时跑 `corral start --unique`。
- **抓到的现场**（10-14，测试进程 73472）：
  - 3 个 pen 都正常起来了，各自带着 `/bin/cat`；
  - 测试有一个线程卡在 `Command::output()`，等 `corral start` 的 stdout 结束；
  - 其中一个 pen（main-3）多开着一个管道（fd 42），就是测试进程里另一个线程用来收 `corral start` 输出的管道。pen 常驻不退，那头就永远等不到结束。
- **推测的原因**（动手时先核实）：
  - Rust 标准库在 macOS 上建管道时，「建管道」和「设 close-on-exec」分两步。
  - 两步之间如果另一个线程正好 fork，这个管道就带进了另一个 `corral start` 子进程；
  - 它再起常驻的 pen 时又把管道带了进去。
  - corral 起常驻进程时没有关掉 0、1、2 以外继承来的描述符。
- **影响**：
  - 测试偶尔卡住；
  - paddock 这类多线程程序同时起好几个 agent 时，也可能卡在等 `corral start` 返回上；
  - 被带走的描述符一直占着，直到那个 pen 退出。

## 要做的
1. **先核实**：
   - 标准库在 macOS 上建管道的方式；
   - corral 自己起的常驻进程有哪几种：pen（`pen.rs` 的 `start`）、提醒的 worker（`after.rs`）、`corral upgrade` 起的新 pen（`pen/upgrade.rs`）、`environment.rs` 里 `setsid` 的那两处，逐个看会不会带走调用方的描述符。
2. **修**：这些常驻进程只留自己要用的描述符，其他继承来的一律关掉。做法动手时定，可选的有两种：
   - 在常驻进程启动后最先做：列出自己开着的描述符，关掉不认识的；
   - 在起它的那一刻（`pre_exec`）关。注意别关掉标准库自己用来回报 exec 失败的那个管道。
   - pen 要通过 stdin、stdout 和起它的 `corral start` 交接，这两个不能关。
3. **测试**：要能稳定复现。比如在调用方故意留一个没有 close-on-exec 的管道再起 pen，确认 pen 里没有它，调用方能等到 EOF。不能靠多跑几次碰运气。

## 完成记录（10-17，主控）

### 做了什么
- `lib.rs` 新增 `close_inherited`：读 `/dev/fd`（Linux 上是 `/proc/self/fd`），关掉 0、1、2 以外的描述符。`__pen` 和 `__after` 两个常驻进程入口最先调用。exec 之后还开着的都是继承来的（标了 close-on-exec 的已被 exec 关掉），所以不用逐个判断。
- 测试 `tests/protocol.rs` 的 `background_processes_do_not_keep_what_their_caller_leaked`：调用方用 `std::io::pipe()` 建管道，只在 `corral start` / `corral send --after` 的子进程里清掉写端的 close-on-exec（和现场一样：漏进了 `corral start`），命令返回、调用方关掉自己的写端后，3 秒内要读到 EOF。

### 核实了什么
- Rust 标准库在 macOS 上建管道：`pipe()` 后再分别 `set_cloexec()`（`library/std/src/sys/pipe/unix.rs`，Linux 等用 `pipe2(O_CLOEXEC)` 一步完成）。草稿推测的原因成立。
- 常驻进程逐个看：
  - pen（`__pen`，`pen.rs` 的 `start`）：只用 0、1 和 `corral start` 交接，2 是 null。修。
  - 提醒（`__after`，`after.rs`）：0、1、2 都是 null。修。
  - `corral upgrade` 起的新 pen：旧 pen 直接 exec 成 `__pen-resume`，故意清掉 close-on-exec 把描述符传给新映像，不能关，不动。新版起的 pen 一开始就关过了，没有可带的；旧版起的 pen 升级过来照旧带着，到它退出为止。
  - `environment.rs` 的两处 `setsid`：登录 shell 取环境，由 pen 在启动 agent 前调用，那时 pen 已经关过了。另一处是测试。
  - agent：由 pen 起，pen 已关过，不另做。
- 主线代码上复现：`protocol` 整组连跑 15 遍，第 14 遍卡在 `concurrent_unique_starts_and_listing_preserve_live_locks`；卡住的 pen（main-3）开着 fd 30、31 两个管道，fd 30 和测试进程的 fd 30 是同一个管道。按进程号停掉。

### 验证了什么
- 新测试修之前失败（「the pen or its agent kept the caller's pipe」）；只给 `__pen` 加上时，pen 那段过、提醒那段失败（「the deferred send kept the caller's pipe」），两段各自测得到；两处都加上后通过。
- `protocol` 整组连跑 15 遍不再卡（主线同样 15 遍卡 1 次）。
- `cargo test --all-targets --no-fail-fast` 连跑 3 遍：两遍 123 通过、0 失败、3 跳过；一遍 `events_filter_subagents_keep_full_reply_and_do_not_resend_unconfirmed_input` 失败 1 次。这条是原有的计时问题，和本件无关：送完立刻读输出，要看到「终端回显 + cat 自己回显」两次，偶尔只读到一次（第 203 行，1 对 2）。主线单独跑 40 遍失败 3 次，分支 40 遍失败 1 次。没改它（不在本件范围），记进 HANDOFF「悬着」。
- `cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 通过。

### 拿主意的地方
- 在常驻进程启动后关，不在起它的 `pre_exec` 里关：`pre_exec` 在 fork 之后、exec 之前，只能用异步信号安全的调用，不能读目录，只能按上限逐个 `close`，上限可能很大；还得避开标准库回报 exec 失败用的管道。启动后关没有这些限制，两个入口各一行。
- 关全部 >2 的，不判断 close-on-exec：exec 之后它们都是继承来的；`read_dir` 自己的描述符在列表里，读完已关，再关一次只是 EBADF。

### 没做的
- 旧版 corral 起的 pen 不会因为部署新版而放掉已经带着的描述符，到它退出为止。
- 回显计时那条测试没修。
