### 意见

1. **必须改**：`crates/corral/src/cli.rs:815–830`，stop 先等 `stop.lock`，拿到后才发停止请求。
   - 问题：两个 `corral stop` 同时停同一个 agent 时，后到的那个要等先到的读完记录、放锁才能拿到锁，这时 pen 已经退出，它发停止请求得到 `not_found`：`ok:false`、退出码 2（`exited` 里带着记录）。改前两个都是 `ok:true`、退出码 0、带同一份记录（pen 对第二个停止请求也回 `ok`）。实测：第二个晚 0.3 秒发，旧版两个都退出码 0；新版第二个退出码 2，`"lab/a is not running"`。paddock 的「Stop agent…」把非 0 当失败，用户在 paddock 里停、主控或另一个窗口也在停同一个 agent 时，会弹出失败。这是并发下的退出码变了，完成记录里「公开输出及退出码保持」在这种情况下不成立，任务书也写了不改退出码。
   - 改法（推荐，改动小）：记下这次拿 `stop.lock` 时有没有等过（第一次没拿到）。等过的话，发停止请求得到 `not_found`（code 2）时不直接报错，接着走后面的等待和读 `exit.json`（这时仍持有 `stop.lock`，新 ls 删不了记录）；`instance` 和开头 status 的一致就按原格式输出 `ok:true` 和记录，不一致或没有记录仍报原来的 `not_found`。没等过锁的路径不动，没有竞争时输出逐字不变。补一条测试：两个 stop 同时停一个要几秒才停下的合成 agent，两个都成功、记录相同。
   - 另一个办法：stop 持共享锁（LOCK_SH），ls 仍取排他锁；`StopLock` 释放时先把自己的锁非阻塞升级为排他，成功（说明没有别的 stop 在用）才删文件。这样多个 stop 照旧并行、各自发请求，但改了主控定的「排他 flock」，要主控决定。

2. **建议改**：`cli.rs:815` 的 `lock_deadline` 和 `:831` 的 `deadline` 各算一次 `--timeout`。
   - 问题：有别的 stop 占着锁时，最坏要等将近两倍 `--timeout` 才返回。paddock 用默认的 90 秒，而它 120 秒就杀掉 corral 子进程。正常情况占锁的 stop 几秒就结束，碰上的机会小。
   - 改法：开头算一个截止时间，等锁和等停下共用。

4. **可以不改**：`crates/corral/src/state.rs:308`，ls 用 create 方式取 `stop.lock`。
   - 问题：新 ls 每看到一个启动中或 status 超时的 agent，就在它目录里建一个 `stop.lock`。这个 agent 以后自己退出、过渡期又只有旧 ls 在清理时，旧 ls 删掉其余文件和 `lock` 后删不掉目录，留下只剩 `stop.lock` 的目录，旧 ls 从此看不见它（新 stop + 旧 ls 时也一样，见实测）。不影响同名重开，下一次新 ls 就清掉；部署切换后 PATH 上只有新版，就不会再出现。
   - 改法（如果想去掉这个副作用）：ls 先不带 create 去取 `stop.lock`。文件在且被占就跳过；文件在且拿到就照现在的流程；文件不在就照旧只取 `lock`、不建 `stop.lock`。这样做是安全的：ls 走到清理，说明 status 已失败，也就是 pen 已经删了 socket；而 stop 是在发停止请求前建的 `stop.lock`，早于 pen 收到请求、更早于删 socket，所以 stop 在等记录时 ls 一定看得到这个文件。

### 对五个重点的回答

1. 竞争已消除（只算新版之间）：stop、ls 都按先 `stop.lock` 后 `lock` 的次序取锁，全都是非阻塞加重试，不会死锁；pen 只持 `lock`。stop 持有 `stop.lock` 期间，路径一直指向它持有的那个文件：会删 `stop.lock` 的只有新 ls 和别的 `StopLock`，两者都要先拿到这个文件的锁；pen 启动时不删它，旧版程序不认识它。所以新 ls 在 stop 读完之前删不了记录，实测 0/20。stop 等锁受 `--timeout` 限制（但见第 2 条）。stop 中途被杀，锁由系统放掉，之后的 stop、ls 都能接着做，实测通过。
2. 双向兼容：旧 ls + 新 stop、新 ls + 旧 stop 都和改前一样可能拿到 null；前者会多留一个只剩 `stop.lock` 的目录，新 ls 能清掉。旧版 start 遇到留下的 `stop.lock` 照常启动，同名停了马上重开没有失败。数据方面没有比改前更糟；退出码方面有第 1 条。
3. 对 paddock：启动中的 agent 照旧列成 `starting`；正在被 stop 的 agent 在 pen 关 socket 后消失，stop 返回后的下一次 ls 删掉目录；副作用见第 4、5 条，都是暂时的、无害的。
4. `StopLock` 的 Drop 写得对：同时持有 `stop.lock` 和 `lock`、并核对 inode 一致才删，别人没法在核对和删除之间换掉这个文件；`lock` 被新实例占着时留下文件也无害，下次 stop 接着用。`lock` 已被旧 ls 删掉时留下 `stop.lock` 作记号，新 ls 才找得到这个目录，不会留下一个谁也看不见的空目录。Drop 里的 `self.file.metadata().unwrap()` 对已打开的文件取元数据，实际不会失败。
5. 测试：`pen.rs` 那条用 SIGSTOP 加 `waitpid(WUNTRACED)` 确认 stop 子进程已经停住，再删 socket、放锁、跑真实的 ls，正好是要复现的那个顺序。我在改前代码上确认它稳定失败、在分支上 3/3 通过。它不靠睡眠时间来定先后，不太会偶发失败；唯一依赖时间的是 stop 子进程要在 pen 那 5 秒内发完 status 和停止请求，改前就是这样，余量很大。`protocol.rs` 新增的三处：保留名检查和留下 `stop.lock` 那条都不依赖时间；同名重开那条见第 7 条。

### 本次改动的检查

- 共享锁升级为排他锁在 macOS 上不保证原子（`flock(2)` 手册：先放旧锁再加新锁）。Drop 只在升级成功时才做后面的事：成功说明这时没有别的 stop 持锁，接着照旧要取到 `lock`、核对 inode 一致才删文件。失败就直接返回、关闭描述符，不管旧的共享锁还在不在；这时自己已经读完记录，放掉锁也没关系。升级时旧锁先放开，ls 可能趁这一下拿到排他锁，那也是在这个 stop 读完之后，清理是对的。两个 stop 同时结束、都升级失败时，`stop.lock` 留在目录里且没人持有，下一次 ls 取得排他锁后照常清理，不会留成谁也看不见的目录。
- 取锁时文件被删的 inode 重试：共享模式走的是和排他锁同一个复核循环。拿到 flock 后，路径已删或 inode 已换，就丢掉旧描述符重新打开再取。删 `stop.lock` 的只有两处：ls 清理时（持排他锁）和 Drop 升级成功后（也持排他锁），都排斥共享锁；所以 stop 只要持着共享锁，路径就一直指向它锁住的那个文件。旧版程序和 pen 启动都不删这个文件，这一点和上一轮一样。
- ls 和多个 stop：任何一个 stop 持着共享锁，ls 的非阻塞排他锁都会失败，于是跳过，不清理也不列出，和 CONTRACT 写的一致。ls 清理时持排他锁，正在取共享锁的 stop 会等到下一次重试：这时 pen 已经退了，这个 stop 的停止请求本来也会得到 `not_found`，和改 R51 之前一样。两个 ls 同时跑，后到的拿不到锁就跳过。不会死锁：所有取锁都是非阻塞加重试，次序都是先 `stop.lock` 后 `lock`。
- CONTRACT 新段和代码一致：stop 持共享锁、ls 清理前取排他锁、stop 之间不排队、几个 stop 都返回同一份记录和退出码 0、共用一个截止时间、删除前要取得排他锁、ls 不建这个文件、新旧混用的边界。上一轮那两句（等过锁、`not_found`）已经去掉。
- 新测试：合成 pen 的 accept 和读取都有 5 秒截止，stop 等待时探测 socket 的空连接被跳过；两个 CLI 子进程断言失败时由 Drop 杀掉并回收，只动自己起的 PID。顺序靠 SIGSTOP 加 `waitpid(WUNTRACED)` 固定，不靠睡眠时间，我连跑 3 次都通过。
