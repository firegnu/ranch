### 可以不改

1. **`PONY_HOME` 原样传给目标 pony**：launchd 起的 pony 一律用 `~/.pony`，因为 plist 不设环境变量；deploy 调 `pony status` 时却继承了终端里的 `PONY_HOME`。终端里要是设成了别的目录，deploy 查到的是另一个 pony，可能漏掉重启，核对也是照那个 pony 说的，但不会去停服务。想收紧的话：调 pony 时去掉 `PONY_HOME`；或者 `PONY_HOME` 不是 `~/.pony` 就拒绝。
2. **父进程是 1，不一定是 launchd 起的**：在终端里 `nohup pony run &` 后关掉 shell，pony 会被过继给 1，实测孤儿进程的父进程就是 1。这时 deploy 会去 kickstart 服务，等 30 秒等不到 pid 变化，报失败；手动起的那个 pony 不受影响。要区分得用 `launchctl print` 拿服务的 pid，多调一次 launchctl，不值得。
3. **截断的末行后面接着写，两行会粘在一起**（R41b 就有）：`record()` 追加前不检查文件是不是以换行结尾。上次截断的半行后面直接接上新的 started，两条粘成一行无效 JSON，这条 started 就丢了。改法：打开后如果文件非空、最后一个字节不是 `\n`，先补一个换行。
4. **pony 没动时也打印 pony 状态和日志位置**：切链接或装技能失败时，也会打印「pony 现在在跑……尚未确认部署成功」和日志位置。另外 `last_exit` 是 `config_missing` 时（退出码 0，launchd 不会再起），也会说「launchd 会按服务策略再试」。都只是措辞问题，改必须改 1 时可以顺手改掉。

### 重点看的五项

1. **会不会把 pony 弄停**：只有用户确认后（或带 `--yes`）才会动 pony。kickstart 要同时满足：macOS、plist 在、定义是 same、在跑、父进程是 1、真实程序的 sha256 和目标不同。service install 要满足：定义是 replace、在跑、父进程是 1。执行前会重查 pid、父进程和定义状态，有变化就停下。判断表每一行都对，各有用例。重启失败时 pony 的状态：
   - kickstart 失败，或 30 秒内等不到新的：服务定义还加载着，launchd 会按 KeepAlive 再起，汇报是对的。
   - service install 在卸下旧服务之前就失败：旧 pony 还在跑，重跑会再做一次，也对。
   - 卸下之后才失败：见必须改 1。
2. **正在跑的程序查得对不对**：pid 来自 `pony status`，就是持有 `run/lock` 的那个进程（用 F_GETLK 查），可靠。`proc_pidpath` 报的是真实文件：实测经符号链接启动的进程报的是 `/bin/sleep`。拿来比 sha256 的就是这个文件。查不到时：计划阶段直接拒绝，什么都还没做；执行前重查时报错停下；等待阶段当作还没起来。pid 在计划之后换了，会报「运行状态在计划后变了，请重跑」；这时链接已经切了，重跑会按新的进程判断。
3. **等新 pony 起来**：每半秒查一次，最多 30 秒。条件是 running、pid 和执行前不同、父进程是 1、真实程序是目标的。旧的还没退时 pid 不变，不会误判成功。用例覆盖了三种都不能算成功的情况：同一个 pid 但程序已是目标的、新 pid 但还是旧程序、没在跑。service install 先给 45 秒，之后再等 30 秒。45 秒够用：pony 自己等 bootout 最多 30 秒，launchd 一般在 SIGTERM 后约 20 秒强杀。45 秒到点被杀的后果，并入必须改 1 处理。
4. **测试后门**：没有。生产代码只读上面那四个环境变量；假的 launchctl 和进程查询只在测试子进程里注入。还有一个隐患，见建议改 3。
5. **两条顺带修的**：`deploys.jsonl` 改成按字节分行、每行单独解析，坏行当成 `Value::Null`，「上次部署」会显示「末行不完整」，有中文截断的用例。续跑时按进程比对：链接已经切了、旧程序还在跑，照样列出重启，也有用例。corral、pony 源码、fence 都没改。

### 对「拿主意的地方」逐条表态

1. **pony 没在跑、或父进程不是 launchd 时，即使 plist 是 replace 也不换**：同意。`service install --yes` 等于 bootout 加 bootstrap，plist 里有 `RunAtLoad`，换定义就会把原本没在跑的 pony 起来；手动跑着的时候，还会多出一个 launchd 起的 pony 去抢锁，每 10 秒重试一次。但要在计划里说明定义没换，见建议改 1。
2. **旧版 status 总报 `not_installed`，所以另外检查 plist 文件在不在**：同意。plist 在、目标版本又不认 `service` 时，照 README 第 6 步拒绝，有用例。顺带一点：plist 如果不是 pony 写的（没有标记），`service install --dry-run` 报 `foreign`，deploy 会整个拒绝。这样偏保守，可以接受。
3. **系统调用用函数注入、生产程序里没有测试开关**：同意，核对过。
4. **service install 外层限 45 秒，完成后再等 30 秒**：同意这两个数。45 秒到点被杀时，可能留下服务已卸下的状态，并入必须改 1 一起处理。
5. **部署记录只留进程、退出和连接状态，不抄频道和工作区**：同意。`last_exit` 里有 pony 的退出说明，不含凭证。

- **必须改 1，续跑部分：改好了。** 沿用的未完成记录里如果 `pony_service` 失败、`pony.before.running` 为 true，就算 pony 现在没在跑，也会列出「恢复 pony 服务并启动」，确认后执行 `service install --yes`、等 30 秒、核对。等待和核对比的是最初那次的 pid（`original_before`）。记录里的 `pony.before` 一直沿用最初那份，所以连着失败几次也接得上，用例覆盖了连续失败两次再成功。上一轮那个场景（新 plist 已写、bootstrap 失败），dry-run 不再显示「没有要做的」。另外看了两种情况，都没问题：

### 新的意见

**建议改 1：判断要不要恢复，只看「`pony_service` 这一步 failed」，有两种情况会判错**（挨着必须改 1，触发条件都很窄）
- 位置：`pony.rs` 的 `plan()`，`recovery_before` 那段。
- 漏判：上次部署被打断、只留下 started 记录，或者那一步记的是 `not_done`，都不会恢复。
  - 最可能的情况：`service install` 等 bootout 的那几十秒里，用户按了 Ctrl-C。pony 子进程在自己的进程组里，收不到 Ctrl-C，会接着跑完；它要是在卸下旧服务之后失败了，记录里就只有 started。
  - 实测（只留 started 记录，再续跑 dry-run）：计划里写「pony 服务装着但没在跑，不重启；……launchd 下次启动会用新程序」，「上次部署」显示「没有结束记录（可能被中断）」，最后打印「已经是 new，没有要做的」，又回到了必须改 1 的样子。
  - `not_done` 的情况：续跑在 pony 那一步之前就失败了，那条记录里 `pony_service` 是 `not_done`，下一次也会漏判。要两次之间有人改过链接或技能才会这样，更少见。
- 误判：`execute()` 开头的复查不通过时，这一步也记成 failed。例如确认之后、执行之前 pony 自己停了，报「pony 运行状态在计划后变了」。可这时服务安装根本没跑，pony 也不是 deploy 停的。下次续跑会提议「恢复 pony 服务并启动」，提示里还写着「上次部署的服务安装失败」，这句不对。好在要用户确认才会执行，而且 pony 原本就在跑，后果不大。
- 改法：
  - 执行 pony 这一步时，在记录里写上这次 `service install` 有没有真的跑（`pony_attempted` 已经有了，记进 step 就行）。
  - 恢复条件改成：那条记录的 `pony.action` 是 `pony_service`，`pony.before.running` 为 true，没有一步 `pony_service` 是 done；并且下面三条至少满足一条：真跑过；记录不完整（只有 started）；那条记录本身就是一次恢复。
  - 提示也跟着改：记录不完整时写「上次部署可能卸下了 pony 服务」。DESIGN §3 和 pony README 里对应的那句一起改。
  - 顺带：「接着做」那行可以加一句「恢复后再跑一次 deploy，核对并记完」。不加也行，只是不跑的话，那条记录会一直是失败。

**建议改 2：测试里的保护只拦了 plist，没拦假的 status 文件**（我上一轮给的改法不全）
- 位置：`tests/deploy.rs` 的 `Home::command`。
- 问题：deploy 判断服务装没装，看的是「plist 在」或者「`pony status` 报 `installed`」，满足一个就算。用真实二进制的用例只要在临时 HOME 里写一个 `pony-status.json`（`installed`、在跑、pid 101），就能绕过现在的断言。接下来真的 `proc_pidinfo` 会去查本机的 101 号进程，那多半是父进程为 1 的系统进程；它的 sha256 和目标不同，于是带 `--yes` 时，就会真的对用户在用的 pony 跑 `launchctl kickstart -k`。现在还没有这样的用例：`pony-status.json` 只在走 `pony_run` 的用例里写。
- 改法：在 `Home::command` 里再断言临时 HOME 下没有 `pony-status.json`。
