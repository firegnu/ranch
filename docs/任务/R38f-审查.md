### 必须改

**1. plist 内容变了时重装报成功，launchd 仍按旧定义跑**（`crates/pony/src/service.rs:201-215`；`crates/pony/README.md:166-168`）

- 问题：
  - launchd 只在 bootstrap 时读 plist，不盯文件变化。同名服务已加载时，再 bootstrap 会报错（常见是 5 Input/output error），不会换成新定义。
  - 现在 `status` 为 `replace` 时的流程：先原子写新 plist；bootstrap 报错；`print` 成功，因为旧的那份还加载着；最后输出 `ok:true`、`applied:true`、`status:"replace"`。实际一直按旧定义跑，到注销重登才换。README 让部署后用的 `kickstart -k` 也只是按旧定义重起进程。这正是「报成功但实际没生效」。
  - 这一版能走到 `replace` 的情况：自有 plist 被手改过（标记还在），或者 HOME 路径变了。以后每次改 plist 模板（加 `ProcessType`、`EnvironmentVariables`，改间隔等），升级时都会走到。
  - `create` 时如果同名服务已经加载着（比如有人手删了 plist、没 bootout），也一样：报成功，跑的却是别处来的定义。
- 改法：
  - `replace`：先 `bootout gui/<uid>/local.ranch.pony`（0 或 ESRCH 算已卸下；返回 36 就等，见建议改 1），确认卸下后再原子写新 plist、再 bootstrap。先卸后写的好处：
    - bootout 失败时文件还是旧的，重试仍走 `replace`。
    - 写文件或 bootstrap 失败时服务已经卸下，重试走 `same`，这时 bootstrap 能真的加载，不会又被「print 成功」挡成假成功。
    - 报错时写明服务已经停了。
  - bootstrap 失败而 `print` 成功，只在 `same` 时算成功。`create` 时报错（比如 `already_loaded`），说明已有同名服务加载着、不是这个文件加载的，请先 bootout 或注销重登再装；不自动 bootout 别处来的定义。
  - 预览的 `commands` 里列出 `replace` 时要跑的 bootout；README 删掉「重装不会主动重启已加载的进程」，写明 `replace` 会重起服务。
  - 测试：假 launchctl 记下当前加载的内容（bootstrap 时读文件；已加载时 bootstrap 失败；bootout 清掉）。断言 `replace` 之后加载的是新内容，`create` 碰上已加载会报错。

### 建议改

**1. bootout 返回 36（EINPROGRESS）时卸载报失败；出错信息没说清已经做了哪些**（`service.rs:190-198`、`221-226`；`README.md:170-171`）

- 问题：
  - 把 ESRCH（3）当「本来就没加载」是对的。但服务还在跑时，bootout 可能先返回 36（Operation now in progress），过一会儿才真正卸下。据我所知，Homebrew 的 `brew services stop` 就是为这个，在 36 时每秒重试，直到 ESRCH 才停。
  - pony 收到 SIGTERM 后，要等最多 2 秒的轮询，加上手头那次 Slack 或 corral 调用，才会退出。所以服务正在跑时 uninstall 很可能碰上 36：现在会报 `launchctl_failed`、留着 plist；用户没注意的话，下次登录服务又起来了。
  - 能重试，也不坏东西，所以不算必须改。
  - 另外两处：报错里的退出码是 Rust 的 `Some(5)` 写法；uninstall 时 bootout 已经成功，之后才发现文件变了，报 `changed` 或 `foreign`，却没说服务已经停了。
- 改法：
  - bootout 返回 36 时轮询 `print`，直到它报找不到服务（113）再删文件。限个时（比如 30 秒；launchd 默认 ExitTimeOut 20 秒），超时就报「正在停，稍后重跑 uninstall」。
  - 退出码写成数字。bootout 之后的失败要说明服务已卸下、plist 还留着、重跑即可。
  - 必须改 1 里 `replace` 的 bootout 用同一个办法。
  - 实测清单加一条：服务正在跑时 `uninstall --yes` 一次成功。

**2. `--yes` 不核对 HOME 是不是这个用户的主目录；CLI 测试只靠 foreign 判断挡住真的 launchctl**（`service.rs:16-22`、`125-130`；`tests/cli.rs:238-254`）

- 问题：
  - plist 的位置和 `ProgramArguments` 都跟着环境变量 HOME 走，bootstrap 的域 `gui/<uid>` 却是真的。HOME 指到别处时（测试的临时目录、sudo 保留了 HOME 等），`install --yes` 会把别处的 plist 加载进用户真实的 launchd，并且马上（`RunAtLoad`）跑 `<那个 HOME>/.local/bin/pony`。
  - 那份 plist 不在真实的 `~/Library/LaunchAgents` 里，注销后就没了，`pony status` 也看不到，成了半装状态。
  - 这不算越权（调用的本来就是这个用户），也不是任务书说的「换掉 launchctl」，所以不算必须改。
  - 用 sudo 跑时 euid 是 0：会在用户目录里建出 root 所有的 plist 和 `~/.pony`，之后用户自己跑 `pony run`、`install` 都会因属主不对而失败。
  - CLI 测试 `service_preview_is_read_only_and_status_recognizes_only_owned_plists` 用编出的程序带 `--yes` 跑了三次，全靠 foreign 判断在调 launchctl 之前退出。这个判断哪天改坏了，`cargo test` 就会在开发者真实的 gui 域里加载一个指向临时目录的 `local.ranch.pony`，还会占掉真服务的名字。
  - 这条测试末尾的 `assert!(!fixture.home().exists())` 查的是 PONY_HOME，服务本来就不用它，查不出服务有没有建 `HOME/.pony`。
- 改法：
  - `run` 在真正执行之前（非预览）先核对两件事：euid 不是 0；HOME 和 `getpwuid_r(geteuid())` 给的主目录是同一个目录。不满足就报错，不写也不调。预览照旧允许任意 HOME。
  - 这样 CLI 测试里的 `--yes` 一定会在调 launchctl 之前被挡下。也可以干脆从 CLI 测试里去掉 `--yes`，`--yes` 碰上外来文件的情况留给已有的单元测试（那里的假 launchctl 一被调就 panic）。
  - 末尾那条断言改成查 `HOME/.pony`。

**3. README 和实测清单补几处 launchd 的行为**（`README.md:157-171`、`226-255`、上线实测清单）

- 「非零退出后重起，重起间隔至少 10 秒」：ThrottleInterval 管的是两次启动之间至少隔 10 秒。跑了很久才崩的会马上重起；一起来就退的（比如锁冲突）才是 10 秒后再试。照这个写准。
- 删掉整个 `~/.pony`（或 `logs/`），或者删掉 `~/.local/bin/pony`，却没卸服务：launchd 打不开日志路径或程序，进程起不来（据我所知 last exit 会记成 78 EX_CONFIG）。`SuccessfulExit` 为 false 会让它每 10 秒再试一次，pony 自己也没机会退 0。设计里「没配置时正常退出、不再重起」只对删掉 `config.toml` 成立。README 补一句：要清掉 `~/.pony` 或这个链接，先 uninstall。
- 实测清单加三条：
  - 分享消息的 `is_share` 是在第一次收到的 message 事件里，而不是之后补发的 `message_changed`。链接展开通常是事后补发的 `message_changed`，pony 不处理这类子类型；如果分享也是事后补发的，这次的修法在线上就不起作用。
  - 在系统设置的「登录项」里关掉 pony 后，install 的报错能不能看懂。
  - 必须改 1 改完后，`replace` 是否真换了定义：在 `launchctl print` 里看 path 和 arguments。

### 可以不改

1. 写 plist 中途被杀（SIGKILL、断电），会在 `~/Library/LaunchAgents` 留下 `.pony-<pid>-<时间>.tmp`，uninstall 不清它。它是点开头的文件，launchd 登录时会跳过，而且这个空档只有几毫秒。要清的话，照 R8 corral 的做法，uninstall 时顺手删掉内容带标记的 `.pony-*.tmp`。
2. plist 已经不在、同名服务还加载着（有人手删了文件）时，uninstall 报 `absent` 成功，服务一直跑到注销。按「没装过的卸一次不出错」这样做是对的；可以在 README 里提一句，用 `launchctl bootout` 收尾。
3. 没设 `ProcessType`：没写的话，launchd 会加一点 CPU 和 I/O 限制。pony 主要在等网络，影响不大；实测时觉得回复慢再考虑设成 `Standard`。

### 建议改

**1. `replace` 先停服务、后查日志权限；而 launchd 自己建的 `launchd.log` 是 0644，正好会触发**（`service.rs:259-283`）

- 问题：
  - `replace` 现在的顺序是：bootout，然后 `prepare_log`，然后写 plist。`prepare_log` 要求 `~/.pony`、`logs/` 是 0700，`launchd.log` 是 0600，不对就报 `unsafe_path`。这时原来跑得好好的服务已经停了；错误信息说得清，重试也能装上，但服务白停了一次。
  - 有一种情况很容易触发：服务装着的时候，`launchd.log` 被删或被挪走（比如手动归档日志，没先卸服务）。launchd 下次起 pony 时会自己重建这个文件，权限按 umask 算，通常是 0644。之后每次 `install --yes`（`same` 和 `replace` 都一样）都会报 `unsafe_path`；`replace` 还会先把服务停掉。这一半是第一轮就有的行为，复核时才看到。
- 改法：
  - 把 `prepare_log` 挪到 bootout 之前：它不碰 plist，不影响「先卸后写」的道理。
  - `launchd.log` 是当前用户自己的普通文件、只是权限比 0600 宽时，可以直接 fchmod 收紧到 0600（收紧不算放宽权限）；或者至少在 README 写一句「不要在服务装着时删或挪 `launchd.log`」。

### 可以不改

1. bootout 返回 0 就当已经卸下，没用 `print` 再确认一次。如果 launchctl 在服务还没完全卸下时就返回 0（手册没保证，我也不确定会不会），`replace` 紧接着 bootstrap 会失败、如实报错；但用户马上重跑时，状态是 `same`，可能又被「`print` 成功」当成成功。要防的话，把 0 和 36 一样交给后面的 `print` 循环处理即可：已经卸下的会立刻拿到 113，只多一次调用。
2. 卸下之后 bootstrap 失败时，信息里会出现两次「plist left in place」（`launch_error` 一次，补的那句里又一次）。只是读着重复。
