   - 位置：`crates/pony/src/core/engine/approvals.rs` 的 `offer`（194–241 行，正文在 230–235 行）。
   - 问题：确认框现在当作“原样的命令”给用户看，但 U+202A–202E、U+2066–2069 这类双向控制符，Slack 客户端会照 Unicode 双向规则重排显示，可以把真正执行的部分显示成像在引号或注释里（Trojan Source 一类）。零宽字符之类也看不见。探针：原始命令带 U+202E、读屏里也带同一个字符时，照样给按钮，确认框原样带着它。Claude Code 的框会不会原样画出这类字符没有实测；不原样画出的话比对不过，不给按钮。这一类在上一版显示读屏文字时就有，这次让确认框显得可信了，更值得堵上。
   - 改法：原始命令里有 Unicode 格式类字符（Cf，比如 U+200B–200F、U+202A–202E、U+2066–2069、U+061C、U+FEFF），或者有 `\n`、`\t` 以外的控制字符时，不给按钮；或者在确认框里显示成 `\u{202E}` 这样的转义。补一个用例。

2. **大段空行或空白能把危险部分推出视线，又不触发「未显示全」**
   - 位置：同上，`offer` 里按 200 字截断和加提示那几行。
   - 问题：探针用的命令是 `git status`，接着 150 个空行，再接 `rm -rf ~`，一共 173 字。结果给了按钮，也没有「未显示全」提示，因为没超过 200 字。手机上的确认框很可能只看到 `git status` 和一片空白。
   - 改法：确认框里把连续空行、长串空白显示成看得见的记号（比如「⏎×150」），或者空行或连续空白超过几个就按「未显示全」处理。主控真机实测时可以顺便看一眼 Slack 怎么显示多行的确认框。

3. **（和这次改动无关，复核时看到的）确认框正文太长被 Slack 拒收时，整条 Needs you 会丢**
   - 位置：`approvals.rs` 的 `offer` 按 Unicode 字符截 200；`crates/pony/src/core/engine.rs` 196 行，带控件发送失败后的降级重发只对提问选项做。
   - 问题：Slack 确认框正文上限 300。如果它按 UTF-16 计（没核实），命令里 emoji 一多就会超；返回 `invalid_blocks` 后会按“太长”拆段重试，按钮又跟着第一段，一直失败，最后只发出「第 1/1 段发不出去」，提醒本身丢了。
   - 改法：带批准按钮的消息发送失败时，去掉批准按钮重发一次（照选项的做法）；或者截断时保守地按 UTF-16 计数。

### 可以不改

4. 整窗计数让窗口里还留着上一个旧框时不给按钮（探针确认）。连续几条命令时，可能常常拿不到按钮。Bash 有了原始命令比对，藏前半截已经挡住了，整窗计数可以只留给计划框。先上线看看这种情况多不多再定。
5. Needs you 正文里的「屏幕末尾」仍是吞了空格的读屏，只有确认框是原始命令，两份放在一起可能让人疑惑。可以在正文里加一行原始命令，不急。
