# R12 方案（草案）：按活的大小分层派活

2026-10-17，ranch 主控。任务 `docs/任务/R12-派活规则和路由策略调整.md`（草稿）。现状和数据见同目录 `R12-路由与分工现状.md`。

**已被取代**：10-17 讨论后改成任务文件 `docs/任务/R12-派活规则和路由策略调整.md` 第 3 节的判定表。本文只留作记录。

## 1. 要解决什么

用户 10-17：现在主控派活不是 opus 就是 astra 这类顶级模型，按钮改个样式也交给 opus。其实 Claude Code 还有 sonnet，omp、pi 用的 deepseek 也能做。用户补充：担心的不是订阅额度，而是既然是多 agent 协作，就要把「什么活给谁、用什么模型和强度」讲清楚。

目标：**让每一件活该给谁、用哪个模型、几档强度，都有说得清的规则**。落到结果上就是：小活交给合适的小模型，大活和要害活照旧用顶级模型；小模型做不好，有固定的往上升的路。业界的做法见同目录 `R12-业界路由规则调研.md`。

不在本方案里：路由命令本身的问题和阈值（等 R11 升 jev-1.14.0 时一起调，第 7 节），远端 Linux 机器（那边照旧只跑 pi、omp，不派活）。

## 2. 为什么现在小活也到了顶级模型

三处规则叠在一起，主控照规则办，就只能派给顶级模型：

| 原因 | 规则原文（`corral-dispatch/SKILL.md` 第 3 节） | 后果 |
|---|---|---|
| 路由几乎不判「轻」 | 轻档只写「查资料、机械改动、按清单改文字、跑命令汇报」 | 改样式算「实现功能」，判成常规。100 件记录里路由一次没给过轻档的结论 |
| 拿不准就用常规 | 「拿不准用常规」 | 一半以上的活档位拿不准，常规就是 opus high 或 astra high |
| 界面活锁给 Claude Code，pi、omp 不碰项目代码 | 「界面实现也给 Claude」；pi、omp「项目代码里的改动再小也不给它」 | 就算判了轻档，界面活最多到 sonnet，到不了 deepseek；而因为第一条，sonnet 也没用上过 |

结果：约 19 件最后定为「看得见」（只影响显示）的界面活，都是 opus high 做的。用户点名给 omp 的 P5-127、128、129 都一次做完，看 diff 就合并了。

## 3. 分层

| 层 | 什么活 | 交给 | 模型和强度 | 影响面（验证预算） |
|---|---|---|---|---|
| **A** | 样式和文案小改 | pi、omp | 各自默认（deepseek） | 看得见 |
| **B** | 带一点判断的小界面活 | Claude Code | sonnet / high | 看得见或改行为 |
| **C** | 按方案实现、修一般的 bug（非界面） | Codex | astra / high | 改行为 |
| **D** | 新界面、交互方案、设计、跨模块的活 | Claude Code | opus[1m] / high | 改行为 |
| **E** | 碰要害：数据模型、并发和事务、安全和隐私、核心规则 | 设计和界面给 Claude Code，其余给 Codex | opus[1m] / high 或 astra / high；交叉审查 astra / xhigh | 碰要害 |
| 杂活 | 项目代码之外：本机清理、一次性脚本、核对数据、跑命令汇报 | pi、omp | 各自默认 | 看得见 |

和现在比：

- 新加 A、B 两层，A 是第一次让 pi、omp 碰项目代码。
- C、D 就是现在的「常规」档，只是按界面与否分了家。
- E 就是现在的「重」档，开发强度从 xhigh 改成 high（照用户 10-16「effort用high，不要用xhigh」，主控已经这么做了好几次），交叉审查保留 xhigh。
- amp、agy 照旧：只在用户或任务文件点名时派。

### 3.1 A 层：样式和文案小改

下面**全部满足**才算 A：

1. 只改显示：颜色、字号、字重、间距、圆角、透明度、对齐、图标替换、文案。
2. 规则写得清楚：任务书能写成「把 X 改成 Y」，或者「照 Z 处的画法，在 W 处也画一份」。
3. 不用出方案：用户已经说了要什么样子，或者给了截图，或者项目里有现成的样子可以照。
4. 范围小：一两个组件，不新建模块，不改数据、不改状态、不改输入处理。

例子：P5-127（选中的胶囊改淡、和左侧栏共用一份画法）、P5-129（小标题字号调大）、P5-48（胶囊与按钮对齐）、P5-49（胶囊按状态着色）。

pi、omp 照旧任选，一家手上有活就开另一家。

### 3.2 B 层：带一点判断的小界面活

不满足 A，但满足下面这些：

1. 单个组件或一块面板。
2. 可以有小的行为改动：悬停效果、淡入淡出、一个按钮的点击行为、显示规则的小调整。
3. 不新做交互流程，不新做窗口或面板，不需要先给用户看样稿。

例子：P5-26（侧栏图标悬停动效）、P5-25（卡片操作图标与菜单图标）、P5-8（卡片信息补回）、P5-12（agent 种类图标）。

### 3.3 D 层：设计和大界面

下面任一条成立就是 D：

- 新界面、新窗口、新面板，或者没有现成样子的大改（照现行规则，先给用户看文字线框或示意）；
- 要定交互方案、配色体系、主题；
- 跨模块，或者要出设计、方案。

例子：P5-1（侧栏改版）、P5-40（四套深色主题）、P5-51（界面再美化）、P5-4b（设置窗口）。

### 3.4 C 层和 E 层

- C：非界面的实现和修 bug。照现行分工给 Codex。
- E：只要碰要害就是 E，不管是不是界面、改动大不大。

## 4. 主控怎么定层

按顺序问，第一个「是」就停：

```
1. 碰要害吗？（路由 cross_review 是「要」，或者主控判断碰了数据、并发、安全、核心规则）
       是 → E
2. 是项目代码之外的杂活吗？           是 → pi、omp（杂活）
3. 要出方案、新做界面、跨模块吗？     是 → D
4. 是界面活吗？
       满足 A 的四条                  → A
       满足 B 的三条                  → B
       都不满足                       → D
5. 其余（非界面的实现、修 bug）       → C
```

- **相邻两层拿不准时选低的那层**，靠第 5 节的升层兜底。只有 E 不往下选：碰没碰要害拿不准，就按 E。
- **用户点名的**照用户的，任务文件里写「用户点名」。
- 交给哪家和几档都由层决定，不再分别查分工表和档位表。

## 5. 做不好就往上升一层

- **什么算做不好**：主控审查时「怎么算做完」有一条没达到（现行第 5 节的返工条件，不变）。
- **第一次没达到**：照现行规则，交回原来的 agent 返工一次。
- **返工后还没达到**：升一层，A → B → D；C → D 或 E 由主控按活的性质定。
  - 升层时在**同一个 worktree** 开新层的 agent，任务文件不变，开头加一行「升层：自 A（<原因一句话>）」。旧 agent 已经没用了，主控先 `corral stop` 它，再开新的（这是新加的「主控可以自己关」的情形，要写进技能第 8 节）。
  - 新 agent 的第一句话照常让它读任务文件，另外告诉它 worktree 里已有上一个 agent 的提交，可以在上面改，也可以推倒重做。
- **不跳层**：A 不直接升到 D，除非主控审查时发现这件活其实是设计活（那是一开始定错了层，写明理由）。
- **用户可以随时要求换层**。

## 6. 兜底规则怎么改

| 情况 | 现在 | 改成 |
|---|---|---|
| 路由档位拿不准 | 用常规 → opus 或 astra high | 不再用路由的档位定模型，由第 4 节定层 |
| 路由影响面拿不准 | 按表判，拿不准定「改行为」 | 不变 |
| 路由交叉审查拿不准 | 主控按四类要害判 | 不变；拿不准就按 E |
| 路由不可用 | 三项都自己定 | 不变；层照第 4 节定，不受影响 |

路由还照常跑、照常记在任务文件里，但只有两项结论在用：交叉审查（第 4 节第 1 步）和影响面（验证预算）。档位只记录，不用来选模型。

## 7. 路由本身（推迟到 R11 之后）

现状文档第 10 节列的问题（没有界面这一维度、一提安全就判碰要害、拿不准太多、阈值没校准）都留着。等 R11 把分类模型升到 jev-1.14.0 时，拿 A 到 E 的分层和这一阶段的记录来对，再定要不要：

- 加一题「是不是规则明确的界面小改」，直接给出 A 的建议；
- 让「碰要害」不再只看交叉审查，只读调研、文档类的活不判碰要害；
- 按实际数据校准阈值。

## 8. 要改的地方

### 8.1 corral-dispatch 技能（`crates/dispatch/resources/corral-dispatch/SKILL.md`）

| 节 | 改什么 |
|---|---|
| 第 3 节开头 | 「交给哪家、几档」改成先定层（第 4 节的顺序），路由只用交叉审查和影响面 |
| 第 3 节「交给哪家」 | 分工表换成分层表；删掉「界面活实现也给 Claude」的例外和「pi、omp 项目代码再小也不给」，改成 A 层的四条；「拿不准哪家给 Codex」只留给 C 层 |
| 第 3 节「几档」 | 档位表改成按层写的模型和强度；重档拆成「开发 high」「交叉审查 xhigh」两行；Claude Code 轻档（sonnet / medium）、Codex 轻档（gpt-5.6-luna / medium）按第 9 节第 4 条的决定删或留 |
| 第 3 节记录格式 | 路由那一行加上层：`层：<A–E>（<定层理由一句话>）`，下一行照旧记路由结果 |
| 第 5 节 | 加「返工后还没达到就升层」 |
| 第 8 节 | 加「升层时主控可以自己关掉原来那个 agent」 |
| 第 6 节 | 不变（交叉审查只给 E） |

第 4 节的启动命令不用改：A 层用现成的 `pi`、`omp --approval-mode yolo`，B 层用 `claude --dangerously-skip-permissions --model sonnet --effort high`。

### 8.2 版本和部署

技能编在程序里，改完要打新版本目录，再由用户在普通终端里跑 `ranch dispatch install-skills`（三处：`~/.claude`、`~/.agents`、`~/.gemini/config` 的 skills）。路由代码不改。

### 8.3 对 paddock 的影响

- 技能是公开约定的一部分。这次只改派活规则的文字，命令、参数、JSON 输出、退出码都不变，**paddock 不用动**。
- paddock 看板按 `--label effort=… model=…` 显示档位；B 层会出现 `model=sonnet`，看板照样能显示。A 层的 pi、omp 照旧不带标签。
- paddock 自己的 AGENTS.md 如果写了分工或档位，要不要跟着改，在 paddock 自己的任务里做。

## 9. 要用户定的

1. **A 层的边界**：3.1 的四条够不够？有没有你觉得 deepseek 做不了、要排除的（比如 GPUI 的布局计算、原生视图相关的）？
2. **B 层的强度**：sonnet 用 high 还是 medium？
3. **omp 能不能接改行为的小活**：像 P5-131a 那种只碰本机一个小 json 文件读写的，是放进 A（omp），还是至少 B（sonnet）？
4. **Codex 的便宜档**：gpt-5.6-luna 要不要排进来？比如加一个「C-」层，专做非界面的机械改动（批量改名、补简单测试）。不要的话，现在技能里的两个轻档模型一起删掉。
5. **升层**：第 5 节的做法行不行？特别是「升层时主控自己关掉原来那个 agent」。
6. **先后**：建议先改技能、试十件左右的 A、B 层活，看返工率；再做 R11 和第 7 节的路由调整。
