# R12 调研：业界怎么定「什么活给哪个模型、几档强度」

2026-10-17，ranch 主控。任务 `docs/任务/R12-派活规则和路由策略调整.md`（草稿）。现状见 `R12-路由与分工现状.md`，主控的方案草案见 `R12-分层派活方案.md`。

用户的问题：有没有成熟的、大家约定俗成的路由方案？这里指**分派规则**，不是代码上怎么实现路由器。用户关心的不是额度，而是多 agent 协作时把分工讲清楚。

标记：**【原文】** 读了官方页面或论文页；**【二手】** 只看到搜索摘要或第三方文章，细节没核对。模型名变得很快，下文的模型名只用来说明分档的思路，不当推荐。

## 结论先说

1. **没有一套统一的行业标准**，但各家的规则很像，可以归成四种做法：
   - **按角色或阶段分**：规划给强模型，执行给中档模型。
   - **按难度分档**：一个旋钮，默认放在中间，活说得清楚就往下调，出错代价大就往上调。
   - **级联升级**：先给便宜的做，过不了检查再往上升。
   - **按风险分流程**：来自软件工程的变更管理，低风险、常见、有固定做法的变更走轻流程。
2. **最常用的判据是「活说得清不清楚」，不是「改动大不大」，也不是「是不是界面」。** Amp 最低档写的是「你确切知道要什么」，并且明确把修 bug、补测试、重构、描述精确的功能都算进去。OpenAI 说便宜的 Luna 适合「专注、可重复」的活。Claude Code 的强度说明里，medium 对应「范围清楚的日常工程活」。
3. **各家的「默认档」都在中间，不在顶上。**
   - Amp：「从 medium 开始」。
   - GitHub Copilot：「拿不准就先用通用模型」。
   - Claude Code：Opus 5.5、Sonnet 5.5 的默认强度是 medium。
   - OpenAI：Astra 建议从 Light 强度开始。

   我们的默认档「常规」= opus high 或 astra high，比这几家的默认都高。
4. **「强模型规划、中档模型执行」是最一致的约定**：
   - Anthropic 自己的多 agent 研究系统：主控 Opus，子 agent Sonnet。
   - Claude Code 的 `opusplan`：规划用 opus，执行用 sonnet。
   - Aider：architect 模型规划，editor 模型改代码。
   - Cline：Plan 和 Act 两种模式可以配不同的模型。
   - Augment 的指南：协调用 Opus，实现用 Sonnet。

   我们的主控本来就会写完整的任务文件，派出去的活大多已经「说清楚了」，按这个约定应该落在中档或低档。
5. **难度和风险分开定，也是通行的做法**：难度定用多大的模型，风险定多严的检查（ITIL 的标准变更和一般变更）。我们现在的「档」和「影响面」已经是这样分的，这点不用改。
6. **升级要有质量关卡**：级联的研究都说，效果好坏取决于判断「这次做得够不够好」的那一步。我们现成的关卡就是主控审查。Augment 给了一个经验阈值：便宜模型的产出要强模型返工的比例超过约 20%，就不划算了。【二手，厂商经验值】

## 1. 各家怎么规定

### 1.1 Amp：一个旋钮，问「这活多难」【原文】

来源：Amp「the dial」（2026-07-09）、Modes & Models 文档。

四档，每档是「模型 + 强度」的组合：

| 档 | 原话（摘译） | 适合 |
|---|---|---|
| low | 「你确切知道要什么。」 | 修 bug、补测试、重构、描述精确的功能 |
| medium | 「你大致知道要什么。这应该是你的默认档。」 | 杂乱、分好几部分的活 |
| high | 出错不容易看出来又代价大 | 横跨多处的改动、并发；等的时间约翻倍，通常要一轮反馈 |
| ultra | 结果清楚但未知很多 | 迁移、跨很多文件的架构改动 |

- 总规则原话：「从 medium 开始。活清楚就往下调。出错的代价比多等一会儿大，就往上调。」
- 又一句：「往哪个方向选错都要付代价。」选低了，模型来回改不对；选高了，等于用最强的模型改错别字。
- low 档用的是另一家的开放权重模型（GLM），不是同一家的小号。**最低档换一家便宜的模型**，和我们把小活给 pi、omp（deepseek）是同一种做法。
- 另有只读的 oracle 子 agent，专门给第二意见、做难的推理和审查，用的是别家的强模型。这和我们「交叉审查一律给 Codex」是一个思路。
- 文档原话：「按任务选档，而不是按模型名选。」

### 1.2 Anthropic

**多 agent 研究系统**【原文】
- 主控用 Claude Opus 4，子 agent 用 Claude Sonnet 4。比单个 Opus 4 在内部研究评测上高 90.2%。
- 投入多少写成规则放进主控的提示里：简单查事实用 1 个 agent、3 到 10 次工具调用；直接比较用 2 到 4 个子 agent，每个 10 到 15 次；复杂研究 10 个以上，分工要划清。
- 交代子 agent 要有四样：目标、输出格式、用什么工具和资料、任务边界。交代含糊就会重复劳动或漏掉。
- 不适合多 agent 的情况：各 agent 要共享同一份上下文、彼此依赖多、大多数写代码的活（能并行的部分比研究少）、价值低的活（token 约是普通对话的 15 倍）。

**Building effective agents**【原文】
- 「路由」的定义：给输入分类，交给专门的后续处理；适合「类别分明、分开处理更好」的情况。
- 原文的例子：容易和常见的问题交给小而省的模型，难的和少见的交给更强的模型。
- 「主控—工人」模式：中心模型按具体输入拆活、派给工人、汇总结果；例子就是一次要改好几个文件的编码产品。

**Claude Code 文档**【原文】
- 模型别名的说明：`sonnet` 用于日常写代码；`opus` 用于复杂推理；`haiku` 用于简单的活；`opusplan` 在规划时用 opus，执行时自动换成 sonnet。
- 强度说明：

  | 强度 | 什么时候用 |
  |---|---|
  | low | 每个结果你都会看的快速往来：头脑风暴、初稿、改名这类小改 |
  | medium | Opus 5.5、Sonnet 5.5、Haiku 5.5 的默认；范围清楚的日常工程活 |
  | high | 看重验证或边角情况多，比如在已有代码里修 bug；大多数模型的默认 |
  | xhigh | 更深的推理，花更多 token |
  | max | 想让它自己啃下来的难题，比如找安全漏洞；文档提醒「可能收益递减、容易想太多」 |

- 子 agent 一节把「把活路由到更快更便宜的模型（如 Haiku）来控制成本」列为用子 agent 的理由之一。子 agent 不指定模型时，跟主会话用同一个模型。

### 1.3 OpenAI

**Codex 模型文档**【原文】
- 复杂编码和 agent 工作流用 GPT-6.1 Sol；专注、可重复的活用 Luna。
- Astra 是「最强，用于复杂工作」，任务在多步骤、多工具上都要最强能力时才选。
- 强度：先用默认，任务要更多规划、分析或检查时再调高。起点建议是 Luna 用 High、**Astra 用 Light**。大多数活用不着 Max 或 Ultra。不同代的模型强度名不一一对应，要拿熟悉的活试一下低档再调。

**A practical guide to building agents**【二手】
- 先用最强的模型把每一步都做出来，作为基准；再逐步换小模型，看哪里还能接受。
- 不是每一步都要最强的模型：简单的检索、意图分类可以给小模型，难的决定给强模型。

**社区做法**【原文，2026-05 Codex 论坛】
- 在 `.codex/agents/` 里定义几种子 agent，各自固定模型和强度。例如「搭架子」的用 mini 模型 medium，「架构」用强模型 high。主控按名字派活。

### 1.4 GitHub Copilot【原文】

按任务分四类，而不是按模型名选：

| 类 | 说明 |
|---|---|
| 通用写代码和写作 | 「没有特别要求时的好默认」 |
| 快速处理简单或重复的活 | 小而快的模型 |
| 深度推理和调试 | 复杂重构、多步逻辑 |
| 看图（示意图、截图） | 能读图的模型，适合界面活 |

总规则：「拿不准就先用通用模型，再按需要调。」快速、简单的改动用快模型，复杂重构和多步逻辑用推理模型。

### 1.5 Augment 的编码 agent 路由指南【原文，厂商文章，2026-04 发布，06 更新】

| 角色 | 做什么 |
|---|---|
| 协调者（最强） | 规划、拆任务、架构决定、协调多个 agent、挑方案的毛病 |
| 实现者（中档） | 跨文件的实现、写测试、生产代码、验证 |
| 快速档（最便宜） | 找文件、grep、列目录、lint、格式检查、照模板写样板代码、单文件的问题 |
| 审查（别家强模型） | 异步代码审查、难的调试分析 |

- 理由：协调者如果用弱模型，拆出来的子任务有问题，下游的 agent 没办法纠正。
- 升级：便宜档的产出要中档返工的比例超过约 20%，省下的就被重试吃掉了；头一周要盯着它的出错率。（作者说这是经验值，不是测出来的。）
- 生产代码和架构推理，算上审查和返工，强一点的模型总成本反而低。

### 1.6 Aider、Cline、Roo Code：按阶段分模型【二手】

- Aider 的 architect 模式：一个模型负责想（architect），另一个模型负责照着改代码（editor）。最初的组合是 o1-preview 规划、DeepSeek 改代码，在它的改代码评测上创了新高。
- Cline：Plan 和 Act 两种模式可以配不同的模型。官方博客 2025-10 的数据里，最常见的组合是 Opus 规划、Sonnet 执行。
- Roo Code：每个模式记住自己的模型；Orchestrator 模式自己不改文件，只把子任务派给其他模式。

### 1.7 研究：路由和级联【二手，论文没细读】

- **路由**：开工前选好一个模型，难点是开工前的分类要准。
- **级联**（FrugalGPT，斯坦福 2023）：从最便宜的开始，每一步判断「够不够好」，不够再升级。难点是判断要可靠，代价是多跑几轮。
- **两者合起来**（ICML 2025，arXiv 2410.10347「cascade routing」）：先路由到一个模型，不够好再改派别的，直到质量够。作者认为成败关键在「质量判断」那一步。
- 2026 年港科大（广州）有一篇路由综述，按目标、方法、评测整理了这个领域。

### 1.8 一篇关于「委派要写多细」的论文【原文，摘要页】

arXiv 2606.17099（2026-06）：在 10 个小而清楚的任务上，分两档模型跑了 64 次。

- 加写正式的「委派合同」（要求附证据）并没有提高正确率：两种写法 64 次全部通过验收。
- 合同提高的是好不好审：证据充分的情况变多，审查者的疑问变少。
- 代价是 token 多约 13%，耗时多约 38%，弱的那档模型多得更厉害。

对我们的意思：**小而清楚的活，小一点的模型也做得对**；任务书写得重，主要是换来好审，代价是更慢。这和 corral-dispatch 技能「任务书写得越重，对方做得越重」的规矩一致。

## 2. 软件工程里现成的规矩

### 2.1 ITIL 的三类变更【二手】

| 类 | 定义 | 流程 |
|---|---|---|
| 标准变更 | 事先批准、风险低、常见、照固定步骤做、有成功的先例 | 跳过评审，直接做 |
| 一般变更 | 不是标准也不是紧急的，都算这类 | 两级审批，做完复核 |
| 紧急变更 | 必须马上做（如零日漏洞补丁） | 走简化的紧急审批 |

ITIL 管的是「走多重的流程」，不管「谁来做」。它对应我们的「影响面 → 验证预算」，而不是「交给哪家」。可借用的是**「标准变更」这个概念：一类事先说定的、低风险、可重复的活，直接走最轻的路**。我们的 A 层（样式和文案小改）就是这种。

### 2.2 MetaGPT、ChatDev：按角色分工【二手】

- 照软件公司的岗位分工：产品经理、架构师、项目经理、工程师、测试。
- MetaGPT 把标准作业流程写进提示，像流水线一样按顺序传；每一棒交出结构化的产物（需求文档、接口说明），不是随便聊天。
- 它们只按角色分工，不按难度分档。我们的分工表（Claude 管设计和品味，Codex 管实现和审查）就属于这一派。

## 3. 拿来对照我们的规则

| 约定 | 我们现在 | 差在哪 |
|---|---|---|
| 难度定模型，风险定检查，两件事分开 | 「档」和「影响面」分开定 | 已经一致 |
| 审查找别家的强模型（Amp 的 oracle、Augment 的审查角色） | 交叉审查一律给 Codex 重档 | 已经一致 |
| 规划和拆活用强模型 | 主控是 opus | 已经一致 |
| **执行默认用中档** | 「常规」= opus high 或 astra high，是顶级模型 | 默认档偏高 |
| **最低档的判据是「说得清楚」** | 路由的轻档只写「查资料、机械改动、按清单改文字、跑命令」，太窄 | 说清楚了的界面小改、修 bug、补测试都到不了低档 |
| 低档可以换一家便宜的模型（Amp 的 low 用 GLM） | pi、omp 只做项目代码之外的杂活 | 没利用上 |
| **默认在中间，清楚就往下，代价大才往上** | 拿不准就用常规（顶级模型） | 方向相反：拿不准时往上靠 |
| 级联：过不了关再升级，关卡是质量检查 | 没有升层的规则 | 缺 |
| 角色分工（谁擅长什么） | 分工表按角色分，界面全给 Claude | 角色和档位混在一起：界面活无论多简单都给 Claude 的大模型 |

## 4. 对方案草案的影响（主控的看法）

1. **方案草案的 A 到 E 五层，把「谁来做」和「几档」压成了一个维度。** 业界通行的是分开的几个维度：
   - **角色**：谁擅长。设计和品味给 Claude，实现和审查给 Codex。
   - **难度**：说得多清楚、未知多少，决定档位。
   - **风险**：决定验证和审查。

   建议把草案改成这三问，各自独立。低档里再规定「界面小改的低档给 pi、omp」，就像 Amp 的 low 换了一家模型。
2. **低档的判据改成「说得清楚」**，照 Amp 的写法：任务书能写成「把 X 改成 Y」「照 Z 做一份」，不需要再出方案，就算低档。这比「样式和文案」宽，修 bug、补测试只要说得清楚也能进来。要不要放这么宽，要用户定。
3. **默认档往下挪**：照 Claude Code 和 OpenAI 的说明，中档可以是 sonnet high 或 opus medium，Codex 可以是 Sol 或 astra 的低一点的强度。顶级模型加 high 留给「出错代价大」的活。具体组合要拿几件熟悉的活试过再定（OpenAI 文档也是这么建议的）。
4. **拿不准时往中间靠，不往上靠**；加上升层规则，用主控审查当关卡。头十件左右记下返工率，参照 Augment 约 20% 的经验值，看低档值不值。
5. **路由命令**：业界的路由器要么是训练过的分类器（RouteLLM 之类），要么是级联加质量判断。我们现在的做法是「通用分类模型 + 照搬来的阈值」，一半以上的活拿不准。这里有两条路：
   - 让路由只回答「说得清不清楚」「碰不碰要害」这两个问题；
   - 或者干脆不用它定档，改由主控按上面的三问判断。

   这要和 R11 一起定。

## 5. 要用户定的

1. 要不要把方案草案从「五层」改成「角色、难度、风险三问」？
2. 低档的判据用「说得清楚」（宽，照 Amp），还是只限「样式和文案小改」（窄，照草案）？
3. 默认档要不要往下挪（例如 Claude 的常规改成 sonnet high，Codex 的常规改成更低的强度），先拿几件活试？
4. 路由命令以后的用法：只判「清不清楚」和「碰不碰要害」，还是不再用来定档？
