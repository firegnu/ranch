# R12 调研：路由与分工的现状

2026-10-17，ranch 主控。任务 `docs/任务/R12-派活规则和路由策略调整.md`（草稿）。本文只写现在是怎么定的、实际用下来什么样、哪里有问题，不改技能和代码；怎么改等用户定。

依据：
- 规则文字：`crates/dispatch/resources/corral-dispatch/SKILL.md` 第 3、4、6 节（和装在 `~/.claude/skills/corral-dispatch/` 的一致，版本 8299e39）。
- 路由命令：`crates/dispatch/src/rules.rs`（问题、阈值）、`crates/dispatch/src/route.rs`（怎么算结论）、`crates/dispatch/README.md`（重试、超时）。
- 实际记录：paddock 和 ranch `docs/任务/*.md` 开头的「路由：」行，共 120 件（含 Saddle 时期的 T76 一件）。统计用 grep 按记录用语归类，数字是约数。

## 结论先说

1. 每件活要定五样：**类型、交给哪家、几档、影响面、要不要交叉审查**。类型和交给哪家由主控定，不问路由；后三样先问 `ranch dispatch route`，拿不准再由主控按规则定。
2. **交给哪家和几档、影响面互不相干。** 分工表只看活的性质（设计、界面、后端、杂活），所以轻档界面活照规则仍给 Claude Code 的 sonnet，到不了 pi、omp。用户 10-17 三次点名 omp 做的简单界面活，和分工表的文字是反的。
3. **路由经常拿不准。** 问过路由的约 100 件里，档位拿不准约 55 件，影响面约 60 件，交叉审查约 40 件。路由几乎从没给出过「轻」档的结论；最后定成「轻」的 6 件都是主控没问路由、按用户点名定的。
4. **交叉审查和影响面在路由里是同一个信号**：交叉审查是「要」，影响面就一定是「碰要害」。只读调研只要摘要里提到安全或并发，也会被判成「碰要害」。主控推翻路由的 8 次里有 5 次是这种情况（交叉审查从「要」改成「不要」）。
5. **重档的强度和用户偏好不一致。** 用户 10-16 说「effort用high，不要用xhigh」，之后重档开发 agent 都被主控改成了 high（P5-90、P5-123、P5-126），交叉审查仍用 xhigh。技能里的表还写着重档用 xhigh。
6. **有两档的模型实际没用过**：Claude Code 的轻档（sonnet）和 Codex 的轻档（gpt-5.6-luna）在记录里一次都没出现过。

## 1. 总流程

```
用户要做的事
  │
  ├─ ① 类型：主控定（调研 / 设计 / Bug 修复 / 功能变更 / 重构 / 样式文案 / 其他）
  │        只决定任务书里那一行「提示」，不影响下面任何一项
  │
  ├─ ② 交给哪家：主控照分工表定，不问路由（第 4 节）
  │
  └─ 写三五句摘要 → ranch dispatch route
          ├─ tier.verdict          → ③ 几档 → 模型 + 强度（第 5 节）
          ├─ impact.verdict        → ④ 影响面 → 验证预算（第 6 节）
          └─ cross_review.verdict  → ⑤ 要不要交叉审查（第 7 节）
          某项是 null，或者路由调不通 → 主控按兜底规则自己定（第 3 节）
```

先后关系：项目 AGENTS.md 写了的规矩最优先（包括写明「不用路由」），其次是「很费 token 的配置要先问用户」，再次才是路由和分工表。

## 2. 路由命令怎么判

### 2.1 输入和请求

- 主控从标准输入给一段三五句的摘要：做什么、改哪些目录、做错了会影响什么。不写私人数据，**不写打算怎么验证**（写了测试矩阵、录屏，路由就会判重）。
- 命令把摘要和 7 个固定问题一起发给 TypeSafe 的分类模型 `jev-1.13.0`（`https://api.typesafe.ai/v1/systemone`），key 取自环境变量 `TYPESAFE_API_KEY`。任务书本身不发出去。
- 问题和阈值是从旧 Python corral `6923da1` 的 route.py 原样照搬的，测试里固定了规则指纹，没校准过。

### 2.2 七个问题

| 字段 | 题型 | 问的是（原文意译） |
|---|---|---|
| `tier` | 打分，三档 | coding agent 要多少推理能力才能做好？**轻**：查东西、机械改动、按清单改文字或数据、跑命令汇报，几乎不用设计判断。**常规**：按清楚的任务描述实现功能或修一般 bug，单个模块内的正常设计判断。**重**：设计数据模型、并发或事务、跨模块设计、难查的 bug、仔细审查别人的代码；出错代价大或者不容易看出来。 |
| `cross_data_model` | 是非 | 是否新建或改数据库表结构（表、列、约束、迁移）？只读写行不算。 |
| `cross_concurrency` | 是非 | 是否涉及并发、后台任务、锁、重试或数据库事务？ |
| `cross_security_privacy` | 是非 | 是否涉及安全或私人数据（权限、文件系统隔离、记录个人内容、把数据暴露给别人）？ |
| `cross_core_rules` | 是非 | 是否实现或修改产品的核心业务规则、产品依赖的中心决策逻辑？ |
| `visible` | 是非 | 是否只限于呈现（布局、颜色、文字、文档）或只读研究，不加功能、不改输入处理、不改逻辑？ |
| `doc_only` | 是非 | 是否只产出方案、调研笔记或设计文档，不改任何程序代码？ |

### 2.3 从回答到结论

| 输出 | 怎么算 | 结论 |
|---|---|---|
| `tier.level` | 三档概率里最大的那档 | 总有值 |
| `tier.verdict` | 置信度 `confidence` ≥ 0.8 时等于 `level` | 否则 `null`（拿不准） |
| `cross_review.verdict` | 取 4 个 `cross_*` 分数的最大值：≥ 0.8 | 「要」 |
| | 最大值 ≤ 0.2 | 「不要」 |
| | 在两者之间 | `null` |
| `impact.visible` | `max(visible, doc_only)` | 数值 |
| `impact.verdict` | 交叉审查是「要」 | 「碰要害」（不看 visible） |
| | 否则 visible ≥ 0.8 | 「看得见」 |
| | 否则 visible ≤ 0.2 **并且**交叉审查是「不要」 | 「改行为」 |
| | 其余 | `null` |

注意两点：
- 「碰要害」完全由交叉审查决定，两项输出其实只有一项信息。
- 「改行为」要同时满足 visible ≤ 0.2 和交叉审查明确「不要」，门槛很高，所以影响面最常拿不准。

### 2.4 输出样子

成功（退出码 0）：

```json
{"ok":true,"model":"jev-1.13.0",
 "tier":{"verdict":null,"level":"重","score":1.6,"probabilities":{"轻":0.01,"常规":0.13,"重":0.86},"confidence":0.7},
 "cross_review":{"verdict":"要","data_model":0.05,"concurrency":0.92,"security_privacy":0.1,"core_rules":0.3},
 "impact":{"verdict":"碰要害","visible":0.03},
 "usage":{...}}
```

（数字是示意，形状照 `route.rs`。）

失败（退出码 1）：`{"ok":false,"error":"…"}`，原因包括没设 key、输入不是 UTF-8、HTTP 出错、回复格式不对。

调用细节：每个阶段 10 秒超时，最多试两次。只有第一次遇到 429/529 时等 1 秒再试；请求发完之前出错或超时会立刻重试一次。

## 3. 主控怎么用路由的结论

- **照用**：退出码 0 且 `"ok": true` 时，三项照用。
- **兜底**（某项是 `null`，或者路由不可用）：
  - 档：拿不准就用「常规」；审查发现质量不够，再升一档重做。
  - 影响面：主控按第 6 节的表自己判；拿不准就定「改行为」，不往重的一头靠。
  - 交叉审查：主控判断是否碰了数据模型、并发和事务、安全和隐私、核心规则，碰了就做。
- **路由不可用**：不重试，不改用旧的 route.py，不追问用户，三项都自己定，派活照常。
- **推翻**：只有主控知道路由看不到的情况时（返工过、审查发现过问题、用户另有交代）才推翻，并写一句理由。
- **记录格式**（任务文件开头）：
  `路由：<档> / 交叉审查<要或不要> / 影响面：<档>（路由：<各项结论，null 写拿不准，不可用写原因>；推翻：<理由>）`

## 4. 交给哪家

### 4.1 分工表（现行）

| 家 | 负责 |
|---|---|
| Claude Code | 设计和品味：架构、模块边界、数据库设计方案；界面和交互方案；**界面实现**（网页、终端）；配色、文案这类要看了才知道好不好的活 |
| Codex | 方式已定的实现：照方案写后端、迁移、接口、业务规则；修 bug、补测试、批量机械改动、跑很久的活；**两家都做得了的活**；**交叉审查**；前端做完后的浏览器验收 |
| pi、omp | 项目代码之外的杂活：本机清理、一次性脚本、核对数据、跑命令汇报。两家同类，任选，一家手上有活就开另一家。**只接轻档；项目代码里的改动再小也不给** |
| amp | 分工没定：只在用户或任务文件点名时派 |
| agy | 分工没定：只在用户或任务文件点名时派 |

### 4.2 附加规则

- 既要设计又要实现的，拆成两步：Claude Code 出方案，用户定（架构级的决定由用户拍板），再派人实现。**界面活例外，实现也给 Claude Code。**
- 新界面或者没有现成示意的大改，派人实现之前先给用户看样子（文字线框或示意）。规则明确的小调整直接做。
- 拿不准哪家做得了，给 Codex。这条是按订阅定的：Codex 额度宽松，Claude Code 有周限额；订阅变了要改这条。
- 用户让主控自己动手的，不派。
- 一件活一个 agent、一个 worktree；同类活固定交给同一家，不在两家之间来回换。
- 远端 Linux 机器只跑 pi、omp，那边不派活（用户 10-15）。

## 5. 几档：模型和强度

### 5.1 档位表（现行）

| 档 | 什么活 | Claude Code | Codex |
|---|---|---|---|
| 轻 | 查资料、机械改动、按清单改文字、跑命令汇报 | `--model sonnet --effort medium` | `-m gpt-5.6-luna -c 'model_reasoning_effort="medium"'` |
| 常规（默认） | 按任务文件写功能、修一般的 bug | `--model 'opus[1m]' --effort high` | `-m gpt-6-astra -c 'model_reasoning_effort="high"'` |
| 重 | 数据模型、并发和事务、跨模块设计、难查的 bug、交叉审查 | `--model 'opus[1m]' --effort xhigh` | `-m gpt-6-astra -c 'model_reasoning_effort="xhigh"'` |

- pi、omp、amp、agy 用它们自己的默认，不分档，也不带 `--label effort/model`。
- 要先问用户才能开（用户点名算同意）：Claude Code 用 `fable`（任何强度）、opus 开 `max`；Codex 开 `ultra`（它还会自己再开子 agent）。
- 不带参数时，开出来的 agent 用它自己的全局默认，不继承主控的模型和强度，所以每次都要显式带上。

### 5.2 完整启动命令（家 × 档）

前面统一是 `corral start <名字> --unique --cwd <worktree> --env CAIRN_DISABLE=1 [--label effort=… --label model=…] --prompt "<第一句>" --`，后面接：

| 家 | 轻 | 常规 | 重 |
|---|---|---|---|
| Claude Code | `claude --dangerously-skip-permissions --model sonnet --effort medium` | `… --model 'opus[1m]' --effort high` | `… --model 'opus[1m]' --effort xhigh` |
| Codex | `codex --yolo --disable memories -m gpt-5.6-luna -c 'model_reasoning_effort="medium"'` | `… -m gpt-6-astra -c '…="high"'` | `… -m gpt-6-astra -c '…="xhigh"'` |
| pi | `pi` | — | — |
| omp | `omp --approval-mode yolo` | — | — |
| amp | `amp`（不能带 `--prompt`，等 idle 后用 `corral send` 送第一句） | — | — |
| agy | `agy --dangerously-skip-permissions`（必须带 `--prompt`，不带 `--label`） | — | — |

## 6. 影响面：定验证预算

难度定模型和强度，影响面定验证，两件事分开定。

| 影响面 | 什么活 | 开发要做的验证 | 主控审查 |
|---|---|---|---|
| 看得见 | 只影响显示、文档、文案、配色，或只读研究；做错了一眼看得出，随时能改回 | `git diff --check`，加一条能直接看出结果的检查；不要求先写失败测试 | 看 diff，不重跑测试 |
| 改行为 | 写功能、修 bug，不碰下一档 | 一条针对这件活的测试（修 bug 先写测试，确认它因为这个 bug 失败），再跑一次项目的标准测试 | 看 diff，重跑一次标准测试 |
| 碰要害 | 数据模型和迁移、并发和事务、安全和隐私、核心规则 | 上一档，再加边角用例；覆盖矩阵、植入缺陷自检只在这一档可以要 | 同上，再加交叉审查 |

录屏、真实终端录制、在真浏览器里走一遍，哪一档都不是默认要求。

## 7. 交叉审查

- 只给影响面是「碰要害」的活。
- 一律交给 Codex，用重档（gpt-6-astra / xhigh）。如果被审的代码本身就是 Codex 写的，另开一个新的 Codex，不用原来那个。
- 审查者在自己的 detached worktree 里只读审查，意见分「必须改 / 建议改 / 可以不改」；只有「必须改」挡合并。
- 改完由同一个审查者复核，复核两轮还没到「可以合并」，停下来问用户。

## 9. 规则文字和实际做法的出入

1. **重档强度**：表里写 xhigh，实际上开发用 high、交叉审查用 xhigh（用户 10-16）。技能没改。
2. **pi、omp 做项目代码**：表里写「项目代码里的改动再小也不给」，实际上用户点名后 omp 做了 5 件 paddock 代码改动，其中 P5-131a 还是常规档。
3. **界面实现给 Claude Code**：简单界面小改实际给了 omp、agy。

## 10. 结构上的问题（供讨论）

1. **交给哪家不看档位和影响面。** 想让「简单界面活」给 pi、omp，现在的表没有能落脚的地方：它只按活的性质分家，档和影响面只决定模型和验证。
2. **交叉审查和影响面是同一个信号。** 「碰要害」完全由交叉审查决定；只读调研和文档类活一提到安全、并发就被判「碰要害」，`visible`、`doc_only` 的分数再高也没用（P5-23r、P5-90a）。
3. **拿不准太多。** 档位的置信度门槛 0.8，交叉审查和影响面的 0.2 到 0.8 都算拿不准；一半以上的活要主控兜底，路由的结论常常只剩参考价值。阈值是照搬的，没拿实际数据校准过。
4. **路由没有界面这个维度。** 7 个问题里没有一题问「是不是界面活」「是不是照现成样子改」。`visible` 把界面样式、文档、只读研究混在一起。
5. **路由给不出「轻」。** 从记录看路由一次也没给过「轻」档的结论，轻档全靠主控和用户点名。
6. **「重」一词两用。** 档位表的「重」同时指难的开发和交叉审查，而用户要的是开发 high、审查 xhigh，表里该分开写。
7. **有两档模型从没用过。** Claude Code 的 sonnet / medium、Codex 的 gpt-5.6-luna / medium 在记录里没出现过；轻活不是给了 pi、omp，就是按兜底升成了常规。
