## 结论先说

1. **magpie 路由的粒度和我们不同。** 它是一个本机网关，在**同一个 agent 会话里，每一轮对话**决定这一轮交给哪个模型、用多大强度。我们是在**开 agent 的时候**，把一整件活交给哪家 agent、哪个模型、哪一档，开出来以后就不变。它的机制不能直接搬，但它写下的**规则**很值得借鉴。
2. **它的路由规则就三样**：一张按顺序排的规则表，第一条命中的算数；规则可以按「这一轮在问什么」（意图）来分；强度可以让分类模型自动挑。
3. **它也用 TypeSafe 的 Jev**，就是我们 `ranch dispatch route` 在用的那家分类模型，而且把我们碰到的「拿不准太多」处理掉了：
   - 意图只要求可信度 ≥ 0.4（我们要求 0.8）；
   - 强度不设门槛，直接把分数四舍五入到最近的一档；
   - 可信度按各选项的概率重算，因为它发现 Jev 自带的可信度字段口径和别家不一样；
   - 发现 Jev 只看各档名字时在短消息上拿不准（例：「写个纸牌游戏」判成复杂任务只有 0.62），把**每一档是干什么的**写给它以后，同一条判到了 0.99。

   这几条和 R11、R12 的路由调整直接相关。
4. **它的四档强度和判据可以直接参考**，见第 4 节。按它的分法：
   - 我们「常规」那一类（照任务文件写功能、修一般 bug）对应它的 **medium**，我们现在用的是 high；
   - 我们「重」那一类，它拆成 high（跨多文件、原因未知的 bug、有取舍的设计）和 xhigh（并发、性能、安全上的隐蔽 bug，设计架构或算法）两档。
5. **它给出了两种现成的默认取向，由用户选**：
   - 「难的给强、容易的给便宜」：判不出时留在强模型上；
   - 「便宜的先上」：先给便宜的，agent 要高强度时、或者便宜的都失败了，才给强的。

   我们现在相当于前一种，而且判不出的情况占了一半以上。
6. **它不按模型名单分强弱，而是按价格**：每百万 token 输出价 ≥ 10 美元算强模型；价格不超过强模型四分之一的算便宜模型。模型换代时不用改名单。我们的技能里写死了模型名，每次换代都要改表。

## 1. magpie 是什么

一个本机网关（默认 `127.0.0.1:3425`），让 Claude Code、Codex、Gemini CLI、pi、oh-my-pi（omp）等几十种 agent 都能用任意一家的模型。例如 Claude Code 跑在 Kimi 上、Codex 跑在 DeepSeek 上。它改 agent 自己的配置，把请求转到网关；网关负责选模型、换账号、在协议之间翻译。

它的「路由」有两层：

| 层 | 解决什么 | 和我们有没有关系 |
|---|---|---|
| 账号和额度的调度 | 同一个模型有几个 key 或订阅时，先用哪个；额度用完了自动换下一个 | 没关系（我们不管额度） |
| **规则和意图路由** | 这一轮按什么条件交给哪个模型、几档强度 | **有关系**，下面只讲这一层 |

## 2. 规则表：按顺序，第一条命中的算数

一个「路由组」里有几个模型，外加一张规则表。每条规则由几个条件和一个结果组成（`grouprule.go` 里的 `Rule`）：

| 条件 | 意思 |
|---|---|
| `tokens` | 这次请求至少有这么长 |
| `images` | 带了图片 |
| `effort` | agent 自己要的推理强度至少是这一档 |
| `agents` | 来自哪几种 agent |
| `intent` | 这一轮用户在问什么（由分类模型判） |
| `compact` | agent 在压缩对话（可以交给便宜模型） |
| `time` | 一天里的哪个时段（比如避开厂商的高峰价） |
| `folders`、`exceptFolders` | 在哪个项目目录里，或者不在哪些目录里 |

| 结果 | 意思 |
|---|---|
| `use` | 这一轮先交给哪个模型（组里其余的模型排在后面，用来接替失败的） |
| `useEffort` | 同时指定强度：low、medium、high、xhigh 或 max。**模型和强度成对地定** |

规矩：
- 从上往下检查，第一条全部条件都满足的规则算数。
- 能直接判定的条件（长度、图片、压缩、目录）放在前面。命中了就不再去问分类模型，省时间也省钱。
- 一条都没命中，就按组里原来的顺序走，这个顺序就是默认取向。

## 3. 意图路由：用户用几个字描述「这一轮在问什么」

### 3.1 怎么判

- 每一轮**只在开头判一次**：用户刚发出一条消息时判。之后 agent 调工具、回传结果的几十次请求都跟着这个决定走，不再重判。理由是中途换模型会丢掉提示缓存，有的厂商还不接受别家写的推理内容。
- 只给分类模型看**用户最新的这一条消息**：不带前面几轮，不带系统提示和工具定义。Claude Code 加的 `<system-reminder>` 会先去掉；超过 4000 字的，只留开头 3000 字和结尾 1000 字。
- 分类模型拿到一个编号列表（各条规则写的意图）和这条消息，回答一个数字，0 表示哪个都不是。
- 推荐用小而快、不带推理的模型来分类（文档举的是 Groq 上的 Llama 3.1 8B），或者用 Jev。限时 8 秒；同一条消息的答案缓存 10 分钟；分类模型失败后歇 30 秒，期间的轮次不再等它。

### 3.2 判不出时：「是帮手，不是关卡」

- 分类模型答 0、超时、出错、答非所问，都算**没有意图命中**，这一轮照组里的默认顺序走。
- 原话：「意图规则可能让这一轮去了一个你没想到的模型，但不会让它失败。」
- 每一轮为什么这样走，路由页面上都逐条写着，可以事后核对。

### 3.3 怎么写意图（官方文档的建议）

- **描述请求，不描述模型**：写「写测试或修测试」，不写「给 Opus 的难活」。分类模型只看得到这几个字和用户的消息。
- **意图之间不要重叠**：「一个问题」和「一个关于代码的问题」会让小模型乱选，要么合并，要么把区别写明。
- **少而宽，胜过多而窄**：两到五条，8B 的小模型也分得清。每条最多 200 字，一般几个字就够。
- **顺序要紧**：非命中不可的规则（比如超长上下文）放在意图规则上面。
- **「都不是」也是正常答案**：判不出的轮次走默认顺序，所以默认顺序要定成你想要的那个默认。
- 中英文都行，小模型读混合语言没问题。

### 3.4 实测（文档里的数据）

20 条真实的编码消息，中英文都有，分快速提问、测试相关、普通编码三类，用两条意图规则：DeepSeek V4 Flash、GLM-5.3 Flash、MiMo v2.6 Flash 三个小模型都 20 条全对，判断用时的中位数分别是 0.75、1.3、1.9 秒。有一个经代理商接入的 Gemini 3.8 Flash 每次 11 秒，全部超时，结果都按没有意图走了。

## 4. 自动挑强度（`effort: auto`，用 Jev）

组的强度设成 `auto` 时，每轮开头让 Jev 判「这一轮要多少推理」，这一轮的请求就按这个强度发（agent 本来就要了推理时才生效）。

四档和判据（`decide.go` 里的 `jevLevels`，原文意译）：

| 强度 | 判据 |
|---|---|
| low | 没多少要想的：打招呼、凭已知就能回答的问题、机械的或一行的改动、跑一条命令 |
| medium | 要想一些：**一般的 bug 修复，或者在已经理解的代码里加一个小功能** |
| high | 要仔细想：跨好几个文件的改动、原因还不知道的 bug、有取舍的设计选择 |
| xhigh | 要深想：隐蔽的 bug（并发、性能、安全）、设计架构或算法、很长的多步计划 |

细节：
- 用 Jev 的打分题（`score`），把分数四舍五入到最近一档，**不设可信度门槛**，不会出现「拿不准」。
- 用户这条只是接着上一条（「继续」「好」「照做」），就沿用上一轮的强度：把上一轮的强度放进请求的状态里，让 Jev 知道。
- 规则里写了用户自己定义的「档位式」意图（如「简单任务 / 复杂任务」）时，magpie 先问一次 Jev「这几个是不是同一把尺子上的几档」，是的话再告诉它每档对应多少工作量，然后才分类。原因见源码注释：只告诉 Jev 档名时，「写个纸牌游戏」判成复杂任务只有 0.62；告诉它每档是干什么的以后，判到 0.99。
- 意图的可信度门槛是 0.4（`jevSure`），按各选项的概率重新算，不用 Jev 自带的 `confidence` 字段。源码注释说各家决策模型的这个字段口径不一样，概率才是可比的。

## 5. 三个现成模板

`grouptemplate.go`，作者 10-10 加的，目的是「点一下就有一个组，不用自己填规则」：

| 模板 | 规则 | 判不出或失败时 |
|---|---|---|
| **难的给强、容易的给便宜**（smart-split） | 压缩对话 → 便宜模型；带图且只有强模型能看图 → 强模型；意图「难活：设计、调试、跨好几个文件的改动、做计划」→ 强模型；意图「容易的活：一个快速问题、小改动、查东西、跑命令」→ 便宜模型 | **留在强模型**：「难」排在第一位，判不出就停在组里第一个，也就是强模型 |
| **便宜的先上**（cheap-first） | 先给便宜模型，再给另一家的便宜模型，最后给强模型；agent 要 high 强度时直接给强模型 | 便宜的都失败了才轮到强模型。这就是级联 |
| **永不卡住**（never-stuck） | 三家各自最强的模型，排成一串 | 一家挂了或额度用完，接下一家 |

怎么认强和便宜：
- 按厂商标价：每百万 token 输出价 ≥ 10 美元算旗舰（文档举的是 2025–26 年的 Opus、GPT-5、Gemini Pro、Grok 4、Sonnet），超过 100 美元的「想好几分钟」的 pro 模型不算。
- 便宜的那个要求价格不超过强模型的四分之一；不知道价格的，看名字里有没有 mini、flash、haiku、lite 之类。
- 同一类里优先选知名厂商、更新的那个。

分类模型的选法：有 Jev 就用 Jev；否则用最便宜的不带推理的模型。

## 6. 对照我们的做法

| magpie | 我们现在 | 可以借鉴的 |
|---|---|---|
| 每轮判一次，判完这一轮不变 | 开 agent 时判一次，判完整件活不变 | 粒度不同，但「判一次就钉住」的思路一样 |
| 规则表按顺序，第一条命中的算数；硬条件放在前面，命中了就不问分类模型 | 分工表、档位表、影响面表分开查；项目规矩和「很费 token 要先问」写在前面 | 把我们的判定也写成**一张按顺序排的表**：用户点名 → 项目规矩 → 碰要害 → 杂活 → 设计和新界面 → 其余按难度。第一条命中的算数 |
| 模型和强度成对地定（`useEffort`） | 家和档分开定，最后拼成命令 | 一致：分层方案的每层也是「谁 + 哪个模型 + 几档强度」 |
| 意图用几个字写「在问什么」，少而宽、不重叠 | 路由的轻档只写「查资料、机械改动……」，没有界面这一维 | 低档的描述照它的写法改：「小改动、查东西、跑命令」，再加上「照现成样子改的界面小改」 |
| 判不出就走默认顺序，默认顺序由用户选（强优先或便宜优先） | 判不出就用常规，也就是顶级模型 | **默认取向要明说**：是「难的给强」（判不出留强），还是「便宜的先上」（判不出给便宜、失败再升）。这是用户的选择，不该由兜底规则暗定 |
| 强度四档有明确判据；一般 bug、小功能是 medium | 常规用 high；重档用 xhigh（实际已改成 high） | 参照它的四档重写我们的强度判据 |
| Jev 的意图门槛 0.4，强度不设门槛只取最近的一档；把每档是干什么的告诉 Jev | 门槛 0.8，一半以上判不出；只给了三档的一句话描述 | **R11 和路由调整时照它的做法试**：调低门槛，或者改成打分后取最近的一档；把每档的判据写得更具体 |
| 「继续」这类消息沿用上一轮的判断 | 返工照原来的类型 | 一致，返工也可以沿用原来的层 |
| 按价格认强和便宜，不写死模型名 | 技能里写死模型名，换代要改表 | 可以参考，但我们只有几家 agent，写死名字也不难维护。不急 |
| 每轮为什么这样走都留痕，可以事后核对 | 任务文件开头记一行路由 | 一致 |

## 7. 对 R12 的建议（主控的看法，待用户定）

1. **把判定写成一张按顺序排的规则表**，第一条命中的算数。项目规矩、用户点名、碰要害这些硬条件放在前面，命中了就不再看路由的难度结论。这比现在三张表分开查清楚。
2. **默认取向由用户明说**：在「难的给强」和「便宜的先上 + 升层」之间选一个，写进技能。这是把分工讲清楚的关键：现在判不出就落到顶级模型，是兜底规则暗定的，没人选过。
3. **强度判据参照 magpie 的四档**：一般的 bug 和小功能用 medium，跨文件和原因不明的用 high，并发、安全、架构用 xhigh。这和用户说的「effort 用 high，不要用 xhigh」有出入，要用户定是全部封顶到 high，还是 xhigh 只留给最后那一类。
4. **R11 升 jev-1.14.0 时，顺带照 magpie 的做法改路由命令**：
   - 档位改成打分后取最近的一档，不再设 0.8 的门槛；
   - 每档的描述写具体，加上界面小改；
   - 可信度按概率重新算。

   这些会改路由的 JSON 输出（`verdict` 不再出现 null），属于公开约定的改动，要先和用户、paddock 对好。
5. **用法**：用户 10-17 说明，看 magpie 是为了参照它，逐步把我们自己的路由做细，不是要用它。上面几条都按这个意思写，第 6 节的对照表就是可以逐条借鉴的清单。
