# R57：agent 干活时插话摸底

2026-11-09；只调研，不改程序、技能或公开约定。依据任务 [R57-干活时能插话](../任务/R57-干活时能插话.md)。代码基线 `ef61b8a`，运行的 corral 来自不可变目录 `d20e05f`。

## 结论

用户理解的“干活时可以插话”成立：本轮在 Claude Code、Codex、pi、omp、Kimi 的 working 状态送入修正，五家最终都按修正回复；Claude Code、Codex、Kimi 还保留了完整工具记录，证明替换了未开始的步骤。pi／omp 的工具序列证据较弱，具体边界见各节。**阻止 `corral send` 的是 corral 自己的空闲检查，不是这些 agent 一概不能接话。** 但不能只删掉这一检查：各家的提交键、输入确认和轮次事件不同，免确认模式也可能出现抢走回车的提问框。

推荐后续实现**显式插话入口（例如 `send --steer`，名称待实现任务定）**，按适配器送入当前任务；普通 `send` 和 `send --after` 保留现有空闲投递语义。先处理输入确认、轮次归属和提交前复查，再按家开放。`blocked`、`starting`、暂停仍挡；不能确认的家不要退回裸 `keys` 冒充成功。

## 范围、方法与证据边界

所有模型保持本机默认模型和强度；临时工作目录位于 `/tmp/r57-steer.iVkO1L/<家>`。每个测试会话都带 `--label role=test --env CAIRN_DISABLE=1`。未改全局配置、信任记录或 corral 集成；未操作用户的其他会话。所有观测命令和临时 Rust 采样程序都在前台等到退出；只有被测的 `send --after` 按自身设计运行提醒进程，接收者也是自建测试会话。

启动命令的共同形式如下；`R57_DIR` 是各家临时目录，`R57_P` 是下面的基线提示词。每条 start 单独执行，表中最后一列替换 `--` 后面的命令。

```sh
corral start ranch/test-r57-claude --cwd "$R57_DIR" --label role=test \
  --env CAIRN_DISABLE=1 --prompt "$R57_P" -- claude --dangerously-skip-permissions
```

| 会话名后缀 | 启动命令／额外环境 |
| --- | --- |
| claude | `claude --dangerously-skip-permissions` |
| codex | `codex --yolo --disable memories` |
| pi | `pi` |
| omp | `omp --approval-mode yolo` |
| kimi | `kimi --auto`；corral 另带 `--env KIMI_CODE_TRUST_WORKSPACE=1` |
| amp | `amp --dangerously-allow-all`；不带 `--prompt`，先 `wait --timeout 20`，再 `send` 首句 |
| canter | `canter --yolo` |

基线提示词：

> 输入时序测试：不要读文件、不要委派。先单独前台执行 /bin/sleep 25，结束后再单独前台执行 printf BASE_SECOND，最后只回复 BASE。工作中如果收到修正，请下一次能响应时按修正替代尚未开始的步骤。命令都在前台跑完。

观察到 `working/PreToolUse` 后，先验证 `send --force` 仍拒绝，再登记提醒，最后粘贴多行并提交。Kimi Enter 首次命中的是工具名为空的轮开始事件，实际 Bash 开始较晚；Ctrl+S 那次特意等到了 `last_tool:Bash`。Amp 没进入 working，因此没有执行后半段。

```sh
corral send "$R57_NAME" R57_REJECT_MUST_NOT_APPEAR --force
corral send ranch/test-r57-receiver "$R57_NOTICE" --after "$R57_NAME" --timeout 90
corral keys "$R57_NAME" $'text:\e[200~修正 R57_ENTER：取消尚未开始的 BASE_SECOND；改为前台执行 printf STEER_SECOND。最后逐行原样复述：\nR57_LINE_A（甲）\nR57_LINE_B[乙]\e[201~' enter
corral status "$R57_NAME"
corral reply "$R57_NAME"
corral wait "$R57_NAME" --timeout 2
corral after ranch/test-r57-receiver --request-id "$R57_REQUEST_ID"
```

排队方式使用另一段正文：“后续 R57_QUEUE：本消息只要求你在处理它时回复 QUEUE_REPLY，并逐行原样复述：”加真实换行的 `R57_QUEUE_A（甲）`、`R57_QUEUE_B[乙]`。提交键分别为 `tab`、`$'text:\e\r'`（Alt+Enter）、`$'text:\x11'`（Ctrl+Q）；Kimi 插话用修正文和 `$'text:\x13'`（Ctrl+S）。`keys text:` 自己不会加括号粘贴，以上显式加了 `ESC[200~` 和 `ESC[201~`。

临时 Rust 工具约每 250 ms 调一次公开 `status`，记录状态变化、输入时间、最终 `wait/reply` 和屏幕尾部。完整临时记录在 `/tmp/r57-steer.iVkO1L/evidence/`，不入库；下文保留可复核的命令、关键 Unix 秒时间戳及结果，不复制含账户用量等私人信息的完整终端输出。

**证据边界：** 真实工作中发送用的是任务允许的 `keys`，没有改二进制绕过 `send`。五家工作中的 `send --force` 均退出 7 `not_idle`。`keys` 的块间隔是 50 ms，正式 `send` 是 300 ms，两者不能视为相同竞态试验。没有读取 corral 内部状态文件；“输入事件”指 `status` 暴露的归一化事件和时间。事件正文的 digest 没有公开查询入口，所以“现办法能确认”的正面判断是公开时点、模型完整复述和钩子代码共同支持的**代码推断**，没有实际跑通 working 状态的 `deliver/confirmation`。负面判断更明确：`last_input_at` 没变或超过 15 秒，当前匹配逻辑就不能及时确认。

## Claude Code

**已查证（实测）：** Enter 不打断正在跑的 sleep；sleep 返回后执行 `printf STEER_SECOND`，没有执行该轮原定的 `BASE_SECOND`，最后两行原样返回。换行、中文全角括号、方括号保留。启动后的最初基线用 sleep 20、sleep 10，观察时错过插话窗口；完成后在同一会话用统一基线重测一次，没有重开会话。

| Unix 秒 | 关键事实 |
| --- | --- |
| 1794193901.845 | 基线 `UserPromptSubmit` |
| 1794193903.619 | `PreToolUse/Bash`，sleep 开始 |
| 1794193903.791 | 调 `keys` 粘贴修正并 Enter |
| 1794193903.850 | 新 `UserPromptSubmit`，`turn_started` 改为此值 |
| 1794193928.654 | sleep 的 `PostToolUse` |
| 1794193930.126–3930.155 | 下一条 Bash，终端显示 `printf STEER_SECOND` |

**状态／确认：** 原生消息进入正在进行的任务，但 corral 每遇 `UserPromptSubmit` 就重新写 `turn_started`。现有确认算法有及时输入可匹配；并不证明模型在输入事件出现的那一刻已经处理修正。刚插话时 `reply` 仍返回上一轮的 `BASE`，不是当前轮进展。最终 `wait` 为 idle，提醒在最终 Stop 后发出，没有早发或丢失的观测。

**另一个提交方式（文档，未实测）：** `Ctrl+Enter`／`Ctrl+X Ctrl+S` 会立即推进待送消息；可后台化的工具会转到后台，其余情形可能打断原轮。它不是单纯的另一种换行，也不适合作为 corral 默认插话键。本轮遵守前台执行约束，没有触发这个会后台化工作的路径。[官方交互说明](https://code.claude.com/docs/en/interactive-mode#queue-messages-while-claude-works)

**风险实测：** 即使启动带 `--dangerously-skip-permissions`，`AskUserQuestion` 仍弹框并抢走回车，见误按风险一节。

## pi

**已查证（实测）：** Enter 后最终 reply 改为两行修正标记，终端输出检索到 STEER_SECOND；Alt+Enter 那次有保存的屏幕记录显示先 BASE，随后处理后续消息，最终 reply 为 QUEUE_REPLY 和两行排队标记。两种方式均完整保留多行和括号。Enter 那次没有保存完整的第二条命令画面，重复渲染中的标记也可能来自提示词，不能仅凭标记计数独立证明执行了哪个 printf。当前轮 steer 的语义另由本机 `dist/modes/interactive/interactive-mode.js` 第 2774 行的 `session.prompt(text, { streamingBehavior: "steer" })` 及[官方 usage](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/usage.md)支持；本机 1.5.0 随包 `docs/keybindings.md` 的 `app.message.followUp` 是 `alt+enter`。

| 方式 | keys 时刻 | corral 一直保留的 last_input_at／turn_started | 最后 Stop |
| --- | --- | --- | --- |
| Enter | 1794194009.574 | 1794194006.760（基线） | 1794194039.014 |
| Alt+Enter | 1794194283.581 | 1794194281.369（基线） | 1794194314.135 |

**已查证（源码）：** 随包 `dist/core/agent-session.js` 的 `prompt/_queueUserInput` 在排队前调用 input handlers；corral 的 [hook_pi.ts](../../crates/corral/resources/hook_pi.ts) 采集 `input.text/streamingBehavior`。但 [events/raw.rs](../../crates/corral/src/events/raw.rs) 的 `input` 分支只存内部队列，只有 `before_agent_start` 才归一化为 `UserPromptSubmit`。本轮两种追加消息都没有新的公开输入时间，不能靠现有 `confirmation` 认出。

**状态／可靠证据：** 最终完整复述是本次消息被消费的可靠事后证据；不是通用的即时送达回执，不能要求所有真实任务额外复述来弥补。corral 两次一直沿用基线轮号，最后 `wait` 为 idle；Alt+Enter 的 BASE 没有成为我们取到的最终 reply，后续回复覆盖了它。提醒均在整串处理结束后到，没有本次早发或丢失。上一轮有回复时，working 中 `reply` 仍可返回旧回复。

**未知：** 是否所有扩展 input handler 都会放行、原生 input 事件能否作为“已接受”而不是“已尝试提交”，本轮未逐个核实；实现时要处理扩展拦截，不能看见采集器的 input 就无条件报模型已收到。权限风险也包含扩展的 UI prompt，不能仅因内置工具不弹批准框就跳过状态保护。

## omp

**已查证（实测）：** Enter 在原任务的 Bash 尚未完成时就登记了新输入，最终回复改为两行修正标记；Ctrl+Q 则到原任务后才登记新输入，保存的终端记录含 `Printing BASE_SECOND in foreground`，最后回复 QUEUE_REPLY。两种多行文本均完整。Enter 那次还看到 `wait` 工具事件，之后有 Bash 的 PostToolUse，再到 Stop，没有把等待工具的返回当作任务完成。

## Kimi

**已查证（实测）：** Enter 本例严格排到下一任务：先 sleep、BASE_SECOND、BASE，再处理修正并执行 STEER_SECOND，来不及撤销 BASE_SECOND。Ctrl+S 那次则在 sleep 之后、BASE_SECOND 之前读取修正，替换未开始步骤。多行与括号两次都完整；两次都没有打断当前 sleep。

| 方式 | keys 时刻 | 新可确认输入 | 最后 Stop |
| --- | --- | --- | --- |
| Enter | 1794194118.475 | 1794194162.454（约 44 秒后） | 1794194178.622 |
| Ctrl+S | 1794194397.350 | 没有；仍为基线 1794194389.935 | 1794194437.567 |

**状态／确认：** Enter 下 `turn_started` 随下一轮更新；Ctrl+S 下两字段不变，`confirmation` 无法确认。后者并非未送达：终端明确出现修正，模型取消 BASE_SECOND，并且 reply 原样返回两行。本轮最终 wait 均 idle、提醒均在最终回复后发出。Ctrl+S 正在工作时 `reply` 报 `no_reply`，没有像 Claude／Codex 那样返回旧回复，调用方不能假设各家一致。

**已查证（源码）：** [Kimi 适配器](../../crates/corral/src/agents/kimi.rs) 仅把输入 hook 的 `UserPromptSubmit` 当可确认输入；wire 里的轮开始、工具等另作状态依据。本轮 Ctrl+S 没走到新的可确认输入。没有推断 wire 一定不存在其他插话证据，只能说当前 corral 没采用。

**文档补充：** Ctrl+S 在下一个可处理点进入当前轮；Enter 在 `WaitFor` 等后台任务时有自动 steer 的例外，不能把本次前台 Bash 的结果推广到所有 Kimi 工作状态。`--auto` 不弹提问框是本仓库既有启动约定；本轮未挑战它的所有策略边界。[官方交互说明](https://www.kimi.com/code/docs/en/kimi-code-cli/guides/interaction)、[键位／批准框说明](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/keyboard.html)

**可选可靠通道（文档，未试）：** 当前 Server API 提供 prompts 接收回执、带正文的队列快照和按 prompt_id steer；这是研究原生回执的候选。它的实验性 API 和会话占用约束需要另外验证，不能在现有 CLI 会话旁另开写入者冒充已解决。[Server API 的 Prompts](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/server-api.html#prompts)

[amp_plugin.ts](../../crates/corral/resources/amp_plugin.ts) 用 `agent.start/end` 生成输入和结束事件，`tool.result` 报工具结果，没有每次键盘接受的回执。steer 是否另发 `agent.start`、后续默认设置对时序的影响，必须补实测。启动就报 idle 也说明 idle 并不等于“当前焦点一定在正文输入框”。

## 误按风险

### 免确认启动下实际复现了一次焦点切换

在自建 Claude Code 会话发送：“先前台 sleep 8；然后用 AskUserQuestion 问 R57无害选择，ALPHA／BETA 均只是测试标记；等回答，不自己选。”这不是权限授权或真实操作。

1. Bash 开始时 `corral keys ranch/test-r57-claude text:R57_DRAFT`，只输入半句，不提交。
2. `1794194383.645` 观测到 `blocked/PermissionRequest/AskUserQuestion`；屏幕默认高亮 ALPHA，提示 Enter to select。
3. `corral keys ranch/test-r57-claude text:_TAIL enter`。
4. `1794194383.853` 已转 `working/PostToolUse`；屏幕显示 `R57无害选择 → ALPHA`，原来的 `R57_DRAFT` 仍在正文草稿，尾部 `_TAIL` 没有成为新的正文输入；`last_input_at` 没有变化。随后 reply 为“你选了 ALPHA。”

这是**一次确定的误选结果**，不是竞态发生概率测量：我们刻意把最后一段和回车放在框出现后，以验证焦点切换的后果。没有在精确的 300 ms 窗口里做概率或压力测试，也没有误改模型／全局设置。

### 哪些保护仍需要

| 情形 | 本轮依据 | 结论边界 |
| --- | --- | --- |
| Claude bypass 下模型提问 | 上述实际 AskUserQuestion | 免工具批准不免提问，working 会转 blocked |
| Codex yolo | 普通两轮无框；已有 PermissionRequest 钩子 | 未穷举提问、计划和插件弹层，不承诺无框 |
| pi | 采集器包含 `ui_prompt_start/end` | 扩展能提出交互；本轮没实测弹框 |
| omp yolo | 适配器识别 `ask`；固定版本键表显示批准／排队键复用 | 问题和工具批准需分开，Ctrl+Q 并非总是排队 |
| Kimi auto | 现仓库约定不弹提问；本次普通工具无框 | 普通模式批准／提问、数字直接选项均仍存在；本轮未重测旧版的所有框 |
| Amp allow-all | 启动 idle 但未得到输入确认 | 状态无法独自证明编辑器就绪；当前工作中弹层未知 |
| canter yolo | 实际 Folder trust | starting 必须继续挡；运行中的交互能力不能由启动参数推定 |
| agy skip-permissions | 文档和既有适配器读屏规则 | 未实测，不作安全白名单 |

### 回车前复查能缩小窗口，不能消掉窗口

**代码事实：** [cli.rs 的 send_once](../../crates/corral/src/cli.rs) 先用一次 Status 做 idle 检查，再交给 pen 两块数据：括号粘贴正文、延时 0.3 秒、回车。[pen.rs](../../crates/corral/src/pen.rs) 在接收请求时检查暂停和最近真人操作，实际出队写每个块时不重新算 agent 的可输入状态。`keys` 更不查 idle。括号粘贴只保护多行的编辑，不保护后面的 Enter 落在哪个控件。

**建议／推断：** 在正文前、提交键实际写出前重新检查实例、暂停、真人输入和可输入状态／交互变化，检测到 blocked 或状态证据变化就停止提交。这样能抓住已经可见的框，至少覆盖当前固定 300 ms 间隔的一部分。但 hook、终端绘制、状态读取和 PTY 按键处理不是一个原子事务；复查以后弹框、事件滞后、没被适配器识别的菜单仍可能误选。剩余窗口不能给出可信毫秒上限或概率。

正文已经写入但放弃回车时，会留下草稿；不能自动清空、补回车或把它当成安全未送达后重新排队。需要返回可辨识的“已写入／待确认”结果，保留 request_id 供查询。原生按 session／turn／input ID 提交的接口才有机会让“给模型的消息”不经过选择框；是否可用于当前进程和会话必须逐家验证，不能临时双通道混写。

## 送达、轮次和提醒的共同结论

**已查证（源码）：** `confirmation` 在最近 10 条归一化输入中找时间晚于发送且 digest 相同的记录，或最新 `last_prompt` 包含规范化后的正文；默认等 15 秒，无匹配报 3，不补发。`events.rs` 每遇 UserPromptSubmit 都改 `turn_started`。`wait` 和 after 的结束观察看同一实例的 idle／blocked 稳定 0.5 秒，并不绑定发送时的具体任务；识别为 interrupted 时 after 继续等。见 [cli.rs](../../crates/corral/src/cli.rs)、[events.rs](../../crates/corral/src/events.rs)、[after.rs](../../crates/corral/src/after.rs)。

因此不能把三个事实混成一个布尔值：PTY 已写、agent 已接受输入、模型已经消费。队列接受可以很早，消费可以在 15 秒以后；反过来 pi／Kimi 已消费，当前 corral 仍没有匹配输入。收到消息不应无条件另开一轮；`reply` 也不是按消息 ID 对应的答复。

## 做法建议与影响

### 方案取舍

| 做法 | 得到什么 | 代价／问题 | 建议 |
| --- | --- | --- | --- |
| 只把 send 的条件改成 idle 或 working，统一 Enter | 最少改动 | Kimi／canter 会排队；pi／Kimi 确认缺失；焦点误选；旧调用方语义变化 | 不选 |
| 显式插话，适配器选择提交方式、确认和轮次处理；旧 send 保留 | 能逐家兑现“修改当前任务”，旧排队调用不变 | 需补输入确认、提交前保护和消息归属；PTY 仍有剩余竞态 | **推荐作为后续实现方向** |
| 各家统一走原生结构化输入接口 | 有机会避免菜单误按并获得 input／turn ID | 接口、生命周期、认证和版本差异大；不能随意接管现有 CLI 会话 | 能沿用现会话接口的家优先研究，别要求第一步重做整个运行时 |

### 推荐实现的边界（本轮未实施）

- working 下明确要求插话才走该入口；blocked、starting、暂停继续拒绝。保留最近真人操作保护，`--force` 不变成越过状态保护的万能开关；未知家不按 Enter 猜行为。
- Claude／Codex／omp 的 Enter 是第一批候选，但仍要补焦点保护和确认实测。pi 先将原生追加输入与消费事实接进确认；Kimi 用 Ctrl+S 的语义并补可靠证据，不能统一 Enter。Amp 先解决启动并补测；canter 先在允许的目录补测，优先利用已有输入协议；agy 暂不开放。未支持的家继续等 idle，明确说明不支持即时插话。
- 区分“消息被接受”与“新任务开始”。保留已有 `turn_started` 兼容含义时，可增加关联输入和执行轮的可选证据；不要暗改字段语义，让旧版 pony／paddock 把一次插话当成一条完整新任务。按 request_id 追踪已写入、已接受、已消费／尚无法确认；缺回执不重送。
- 新插话不撤销已执行副作用，也不保证能打断当前长工具。普通正文不要隐式变为 slash 命令；`/model`、`!`、补全、已有草稿和多条连续插话的处理需要在实现方案中写清，不能把本轮普通两行文本试验扩大成任意字节安全保证。

这些是待实现时解决的约束，不是已经通过的验收结果。尤其“回车前复查后剩余竞态是否可接受”，需要主控在实现方案中交用户定；本轮没有自行放宽保护。

### pony

[DESIGN §10](../DESIGN.md) 当前主动把 working／starting／blocked 排队，所以只升级 corral 不会让手机插话。后续应区分用户主动修正与自动提醒：用户修正可在能力支持时走显式插话，unsupported／尚未写入的状态拒绝才留队；已接受、已写入但未知的消息不重发。

一轮结束贴回目前以 `turn_started` 和两次稳定 idle 去重，线程对应与“是 pony 送的话开的”也受输入来源影响。同一执行轮可以收到多个 Slack 线程的消息，必须规定最终回复贴往哪里、如何不重复／不漏贴，不能简单把最后一次插话当新轮抢走原任务归属。本轮未发真实 Slack 消息。

### paddock

**本轮仅调研：paddock 不用动。推荐实施方案属于公开命令／JSON 的兼容新增，不是纯内部修改。** 保留普通 send 的旧行为和字段，新增入口／能力／可选送达证据；paddock 在自己的任务里接。

只读核对 paddock `docs/DESIGN.md` 的 P5-87 回复框：当前只给 idle agent 输入，其他状态显示说明；后台调用普通 send，不加 force／after。因此后续需在具备能力的 working 行开放“插话”，显示已接受／排队／待确认的区别，并在旧 corral 不认识新参数时保留草稿或等空闲，绝不 fallback 到 keys。用户草稿和 IME 行为沿用原规矩；消息和最终回复不能继续假设严格一问一答。

任务提供的“回复框碰到 not_idle 排队”等背景不作为当前 UI 的实测事实：本轮核对到的是上述设计文字，没有操作 paddock 界面。若直接改变普通 send 在 working 下的语义，会影响旧版调用方，不能仅按兼容新增处理；这也是选择显式入口的理由。没有改 paddock 仓库。

### send --after 与派活技能

after 有两处独立边界：观察目标何时结束、接收者何时允许收到提醒。[after.rs](../../crates/corral/src/after.rs) 两处都要分别考虑，不能为了人工插话顺手把接收者的 working 也放开。推荐默认仍等接收者 idle；自动通知是否允许 steer 是另一个用户决策。继续用 request_id 查状态，pending／unknown 不等于成功；保留 interrupted 处理和 DONE 核实。目标已收到插话后，应将它视为待完成工作的一部分，不能以一次中间 Stop 代表全部做完。

技能后续应区分“修改当前任务”与“做完后再做下一件”，按能力调用插话或保持 wait／after；解释长工具结束前可能尚未处理修正。`not_delivered` 不再能被文案简单解释为“对方没收到”，尤其已写入／队列等待场景；升级确认结果的语义时一并修正文案。本轮没有修改技能。

双向兼容要求：旧 CLI／新 pen 保持旧 send 行为；新 CLI／旧 pen 缺能力时明确退回，不裸发快捷键。新增状态字段可选，旧读取者忽略；若需要新持久化输入记录，要验证旧版共存不会误认新轮或重复投递。当前公开字段重定义属于另一种、不兼容的方案，不能偷偷并入这一兼容新增。
