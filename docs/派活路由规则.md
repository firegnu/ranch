# 派活路由规则

主控把一件活派出去之前，要定这几样：交给哪家 agent、用什么模型和强度、影响面多大、要不要交叉审查。本文把现行规则从头到尾讲一遍。

- **规则原文**在 corral-dispatch 技能 `crates/dispatch/resources/corral-dispatch/SKILL.md` 第 2、3、5、6 节。本文是对它的说明；两者对不上时以技能为准，并改本文。
- **版本**：R12（2026-10-17 合并，提交 `5f9c430`），版本目录 `versions/9b69e4d`。用户切链接、跑 `ranch dispatch install-skills` 之后生效；之前装的技能还是旧规则。
- **来历**：为什么这样定，见 `docs/任务/R12-派活规则和路由策略调整.md`（第 7 节是用户的决定）。R12 之前的规则见 `docs/调研/R12-路由与分工现状.md`，已被本文取代。

## 1. 总流程

```
写任务书正文 ──► 问路由（Jev）──► 查分工表 ──► 定影响面和验证预算 ──► 补开头几行 ──► 派出去
 做什么/范围/      档、交叉审查、     交给哪家、      写进「怎么算做完」        交给谁、几档、
 不要做/验收       影响面           模型和强度                             路由行
```

1. **先写正文**：要做的、范围、不要做、验收。这几样和交给谁无关。
2. **再问路由**：从正文里提炼三五句摘要，交给 `ranch dispatch route`。路由只判三件事：难度、要不要交叉审查、影响面。**交给谁不由它判**。
3. **查分工表**（第 3 节），定交给哪家、模型和强度。
4. **定影响面**（第 6 节），把验证预算写进「怎么算做完」。最后补上任务文件开头的「交给谁、几档」和路由那一行。打算交给 pi、omp 的，再看一遍正文是不是要写得更具体。

为什么先写正文：先问路由的话，路由说「轻」，正文就容易写得单薄。「这件活说不说得清」也不交给路由判断，由主控对照写好的正文来查（第 4 节）。

**谁先说了算**：项目 AGENTS.md 里的规定，以及第 5 节里「很费 token」那几种配置要先问用户，这两样都排在本文其他规则前面。

## 2. 路由：`ranch dispatch route`

### 2.1 怎么问

```sh
echo "<摘要>" | ranch dispatch route
```

摘要用中文写就行，三五句，说清楚：做什么、改哪些目录、做错了会影响什么。**不写**私人数据，**不写**验收和打算怎么验证。摘要里一提测试矩阵、录屏，路由就会往重里判。

背后调用的是 TypeSafe System One API，模型是 **jev-1.14.0**（R12 从 1.13.0 升上来）。每次问同一组问题，问题和阈值沿用 Corral `6923da1` 的 route.py，没有改过：

| 问题 | 类型 | 问的是什么 |
|---|---|---|
| `tier` | 打分（三档） | 写代码的 agent 要多大的推理能力。轻：查东西、机械改动、照清单改文字或数据、跑命令汇报。常规：照清楚的任务书写功能、修一般的 bug，一个模块内的正常设计判断。重：设计数据模型、并发或事务、跨模块设计、难找的 bug、仔细审别人的代码 |
| `cross_data_model` | 是 / 否 | 改不改数据库表结构（只读写数据行不算） |
| `cross_concurrency` | 是 / 否 | 涉不涉及并发、后台任务、锁、重试、事务 |
| `cross_security_privacy` | 是 / 否 | 涉不涉及安全或隐私：权限、文件系统隔离、日志里的个人内容、把数据暴露给别人 |
| `cross_core_rules` | 是 / 否 | 改不改产品的核心规则 |
| `visible` | 是 / 否 | 是否只是呈现（布局、颜色、文字、文档）或只读研究，不加功能、不改输入处理和逻辑 |
| `doc_only` | 是 / 否 | 是否只产出方案、调研笔记或设计文档，不改程序代码 |

### 2.2 返回什么、怎么算

| 字段 | 怎么算出来 | 主控怎么用 |
|---|---|---|
| `tier.level` | 三档概率里最大的那档，**总有值** | **用这个**定难度 |
| `tier.confidence` | 模型给的置信度 | 写进路由行 |
| `tier.verdict` | 置信度 ≥ 0.8 时等于 `level`，否则是 `null` | **不用**。R12 的 30 条样本里，新旧两版都有 17 条是 `null`，用它就常常判不出 |
| `cross_review.verdict` | 四个 `cross_*` 里最大的概率 ≥ 0.8 是「要」，≤ 0.2 是「不要」，中间是 `null` | 交叉审查 |
| `impact.verdict` | 交叉审查是「要」→ 碰要害；否则 `visible` 和 `doc_only` 取大 ≥ 0.8 → 看得见；≤ 0.2 并且交叉审查是「不要」→ 改行为；其余是 `null` | 影响面 |

后两项是 `null` 时，主控按第 6 节自己判。

### 2.3 路由不可用时

- 退出码 0 并且 stdout 是 `"ok": true` 的 JSON，才算可用。要等命令结束、stdout 和 stderr 都收齐再判断。
- 其他情况都算不可用：档按「常规」算，另外两项主控自己判，照常派活。**不重试，不改用旧的 route.py，也不追问用户。**项目本来没有分派要求的，不会因为路由不可用就自动委派。
- 路由行里写不可用的原因：退出码 1 并且 stdout 是 `"ok": false` 的 JSON 时，照抄它的 `error`；其他情况（找不到 `ranch`、别的退出码、stdout 不是 JSON）只写「路由不可用，原因未知（退出码 N）」。
- 项目写了「不用路由」的，不调用。

### 2.4 推翻和记录

只有主控知道路由看不到的情况时（比如这件活返工过、审查时发现过问题），才推翻路由的结论，并写一句理由。

任务文件开头记一行：

```
路由：<档> / 交叉审查<要或不要> / 影响面：<档>（路由：<tier.level>（置信 <tier.confidence>）、<交叉审查结论>、<影响面结论>；推翻：<理由>）
```

括号里是路由原样给的结论：`null` 写「拿不准」，不可用写原因；没有推翻就不写「推翻」。

## 3. 交给哪家：分工表

从上往下看，**第一条命中的算数**。

| # | 条件 | 交给 | 模型 / 强度 |
|---|---|---|---|
| 1 | 任务文件写了 `执行：主控`，或者用户让主控自己做 | 主控自己做，不派 | — |
| 2 | 用户点名 | 照用户说的 | 照用户说的；没说的部分见 3.1 |
| 3 | 项目 AGENTS.md 有规定 | 照规定 | 照规定；没写的部分见 3.1 |
| 4 | 本轮要改代码，**并且**碰要害（路由的交叉审查是「要」，或者主控判断碰了数据模型、并发和事务、安全和隐私、核心规则） | 设计和界面给 Claude Code，其余给 Codex | high |
| 5 | 项目代码之外的杂活：本机清理、一次性脚本、核对数据、跑命令汇报 | pi、omp | 各自默认 |
| 6 | 要出方案或做取舍：架构、模块边界、数据库设计、新界面、新交互、跨模块的活；涉及界面或产品取舍的调研 | Claude Code | `opus[1m]` / high |
| 7 | 界面活，**并且**过了「说得清」检查（第 4 节） | pi、omp | 各自默认 |
| 8 | 其余界面活：单个组件，可以有小的行为改动，不新做交互 | Claude Code | 试用 `sonnet` / high |
| 9 | 其余：照方案实现、修 bug、补测试、批量机械改动、跑很久的活、查事实或定位问题的调研、前端做完的浏览器验收 | Codex | `gpt-6-astra` / medium；难的用 high |

### 3.1 点名或项目规定只定了一部分时，怎么补

第 2、3 条只决定交给谁。碰要害的活照样要交叉审查，验证预算照样按影响面定。

只定了交给哪家、没定模型或强度时：

- 用户或项目说了的，照用。
- **强度**：按这件活本来会落在哪一条来定。第 4、6 条用 high，第 9 条里难的用 high，其余一律 medium。
- **模型**：按家定。

  | 家 | 模型 |
  |---|---|
  | Claude Code | `opus[1m]`；只有这件活本来就落在第 8 条时，才用 `sonnet` / high（试用） |
  | Codex | `gpt-6-astra` |
  | pi、omp、amp、agy | 各自默认 |

### 3.2 各家的位置

| 家 | 接什么 | 说明 |
|---|---|---|
| Claude Code（opus） | 碰要害的设计和界面、要出方案或取舍的活、新界面 | 设计判断和界面品味 |
| Claude Code（sonnet） | 说不清的界面小活（第 8 条），试用中 | 见 5.2 |
| Codex（astra） | 照方案实现、修 bug、测试、机械改动、查事实、浏览器验收；**所有交叉审查** | 挑细节，跑长活 |
| pi、omp | 项目代码之外的杂活；说得清的界面小改 | 本机默认都是 deepseek-flash（思考强度 high）。两家同类，任选；一家手上有活就开另一家 |
| amp、agy | 分工还没定 | 只在用户或任务文件点名时派 |

### 3.3 拆不拆、先给谁看

- 既要设计又要实现、又不是界面的活，**拆成两步**：先由 Claude Code 出方案，用户定（架构级的决定由用户拍板），再按分工表派人实现。
- 新界面的设计和实现**都给** Claude Code（第 6 条），不拆开。
- 新界面、或者没有现成示意的大改，派人实现之前**先给用户看样子**：一张文字线框或示意，用户选定了再派。规则明确的小调整（换个颜色、加一个提示）直接做。
- **一件活一个 agent、一个 worktree。** 新活不塞给已经开着的写代码 agent：它的工作目录钉死在自己那个 worktree 上，换不了目录，也换不了模型和强度。同一个 agent 只在自己的 worktree 里接后续的返工和复核。
- 要稳定的是「家」，不是某个实例：同类活固定交给同一家，不在两家之间来回换。

## 4. 「说得清」检查（第 7 条用）

四条**全部**满足，才交给 pi、omp。有一条不满足，就按第 8 条交给 Claude Code sonnet。

1. **只改显示**：颜色、字号、间距、对齐、图标、文案；不改数据、状态和输入处理。
2. **有要照着做的样子**：用户给了截图或具体的值，或者项目里有现成的画法可以照。
3. **改动点能一条条列出来**，不新建模块。
4. **没有待定的设计问题。**

这项检查由主控对照写好的正文来查，不问路由。交给 pi、omp 之前，再看一遍正文是不是要写得更具体。

## 5. 几档：模型和强度

不带参数开出来的 agent，用的是它自己的全局默认，**不继承主控的模型和强度**。所以每次开 agent 都要显式带参数，并在任务文件和汇报里写明用的是哪一档。

### 5.1 分档表

| 档 | 用在哪 | Claude Code | Codex |
|---|---|---|---|
| **medium**（默认） | 第 9 条的默认：一般的 bug；在已经理解的代码里加小功能；照方案实现；查事实的调研。路由的 `tier.level` 是轻或常规时用 | `--model 'opus[1m]' --effort medium` | `-m gpt-6-astra -c 'model_reasoning_effort="medium"'` |
| **high** | 第 4、6 条；第 9 条里 `tier.level` 是重的，或者主控判断是跨好几个文件的改动、原因还不知道的 bug、有取舍的设计 | `--model 'opus[1m]' --effort high` | `-m gpt-6-astra -c 'model_reasoning_effort="high"'` |
| **xhigh** | **只给交叉审查**（第 7 节） | — | `-m gpt-6-astra -c 'model_reasoning_effort="xhigh"'` |
| **试用** | 第 8 条 | `--model sonnet --effort high` | — |

- 拿不准就用 medium。
- 审查发现质量不够，按第 8 节返工，**不自己升档重开**。
- **不用 `low`**：paddock 看板只认 medium、high、xhigh 三档标签。
- pi、omp、amp、agy 用它们的默认，不分档，也不带 `effort`、`model` 标签。
- 模型名会随版本变，过时了就改技能里的分档表和本文。

### 5.2 sonnet 先试 5 件

第 8 条现在在试用 sonnet。派之前，先数一下项目任务文件里已经按第 8 条交给 sonnet 的有几件（看开头「交给谁、几档」那一行里有没有 sonnet）：

- **不满 5 件**：照试用派。
- **满 5 件以后**：主控把这 5 件主控审查里的「结果」行汇总给用户，由用户定第 8 条以后交给谁。用户定下来之前，命中第 8 条的活先不派，问用户；其他条照常派。

试用不会延续成长期默认，也不会自动升档。

### 5.3 很费 token 的配置：先问用户

下面这些可以提议，但要先问用户，同意了才开；用户点名就算同意：

- Claude Code 用 `fable`（任何强度）；
- opus 开 `max`；
- Codex 开 `ultra`（它还会自己再开子 agent）。

### 5.4 开 agent 的命令

| agent | agent 命令（后面接 5.1 的参数） |
|---|---|
| Claude Code | `claude --dangerously-skip-permissions` |
| Codex | `codex --yolo --disable memories` |
| pi | `pi` |
| omp | `omp --approval-mode yolo` |
| amp | `amp`（不能带 `--prompt`，等到 idle 后再用 `corral send` 送第一句） |
| agy | `agy --dangerously-skip-permissions`（要带 `--prompt`，不带 `--label`） |

例子，Codex medium：

```sh
corral start demo/dev-backend --unique --cwd <worktree> --env CAIRN_DISABLE=1 \
  --label effort=medium --label model=gpt-6-astra \
  --prompt "先读 AGENTS.md，再读 <任务文件>，照做。命令都在前台跑完，全部做完后，回复最后一行写 DONE。" \
  -- codex --yolo --disable memories -m gpt-6-astra -c 'model_reasoning_effort="medium"'
```

所有派出去的 agent 都带 `--env CAIRN_DISABLE=1`。Codex 另加 `--disable memories`。`--label effort=…`、`model=…` 要和命令里的参数一致，看板靠它们显示档位。

## 6. 影响面：定验证预算

难度定模型和强度，影响面定验证，**两件事分开定**。

| 档 | 什么活 | 开发时的验证 | 审查 |
|---|---|---|---|
| **看得见** | 只影响显示、文档、文案、配色，或只读研究；做错了一眼看得出，随时能改回 | `git diff --check`，加一条能直接看出结果的检查；不要求先写失败测试 | 主控看 diff，不重跑测试套件 |
| **改行为** | 写功能、修 bug，不碰下一档 | 一条针对这件活的测试（修 bug 先写测试，确认它因为这个 bug 失败），加上项目的标准测试跑一次 | 主控看 diff，重跑一次标准测试 |
| **碰要害** | 数据模型和迁移、并发和事务、安全和隐私、核心规则 | 上一档的全部，再加边角用例。覆盖矩阵、植入缺陷自检只有这一档可以要 | 同上，再加交叉审查 |

- 照路由的 `impact.verdict` 定。它是 `null` 时主控按上表判；拿不准就定「改行为」，不往重的一头靠。
- **本轮不改代码的调研、设计，一律算「看得见」，不交叉审查**，不管路由说什么。原因是路由一看到摘要里提安全、并发，就会判成碰要害。R12 样本 #10（只读调研截图失败的原因）在 1.14.0 下就被判成了碰要害，正好由这条兜住。
- 录屏、真实终端录制、在真浏览器里走一遍，哪一档都不是默认。用户要求了，或者验收除此之外确实查不了，才写进任务书；集成验收只走主路径一遍。
- 预算照档执行，不往上加。通过了的验证，相关代码没再改就不重复跑。觉得还要多验，先报告原因，不自己扩大预算。返工只跑针对这次修正的检查和直接相关的回归。

## 7. 交叉审查

只给影响面是「**碰要害**」的活，也就是路由的交叉审查是「要」，或者主控判定碰了数据模型、并发和事务、安全和隐私、核心规则。看得见、改行为的活不做，本轮不改代码的调研、设计也不做。

- **一律给 Codex**，用 `gpt-6-astra` / xhigh，标签 `effort=xhigh`。被审的正好是 Codex 写的时候，另开一个新的 Codex 实例，只给它任务文件和 diff。
- 审查者在自己的 detached worktree 里只读：不改、不提交、不切分支。意见写进主仓库的审查文件。
- 「**必须改**」只给两种情况：任务书「怎么算做完」没达到；碰到的要害上有真实缺陷（会丢数据、并发出错、泄露或越权、核心规则算错）。其余一律「建议改」。只有「必须改」挡合并。
- 改完由同一个审查者复核，复核前先把它的 worktree 切到新提交。**复核两轮还没到「可以合并」，停下来问用户。**

## 8. 审查、返工和「结果」行

- 主控每件都审，按影响面那一档的预算审，核实对方说的，不自己再证一遍。
- 只有两种情况交回返工：「怎么算做完」有一条没达到；做了「不要做」里的事。罕见输入组合下才出错的，记「建议改」，告诉用户。
- 返工交回原来的 agent。**返工两次还没达到「怎么算做完」，停下来问用户**：换一家、升一档，还是放弃。主控不自己换人或升档重开。
- 主控审查结论的最后一行记结果，三选一：

  ```
  结果：一次过
  结果：返工 N 次
  结果：返工两次仍不达标，已停下问用户
  ```

  每件都记。这一行用来回看分工表定得对不对，sonnet 试用满 5 件后的汇总也用它。

下面几件取自 `docs/调研/R12-路由校准样本.txt`。分到哪一条是主控按分工表做的示范判断，不是路由的输出。

| 样本 | 活 | 命中 | 交给 | 档 | 影响面 |
|---|---|---|---|---|---|
| #1 | 侧栏小标题字号 11pt 改 12pt，只改一处常量 | 7（四条都满足） | pi 或 omp | 默认 | 看得见 |
| #30 | 卡片加状态颜色条，颜色照现有主题 | 7（只改显示、有现成颜色、改动点能列出来） | pi 或 omp | 默认 | 看得见 |
| #6 | 侧栏图标加悬停放大动效，改绘制和悬停状态 | 8（改了悬停状态，第 1 条不满足） | Claude Code | sonnet / high（试用） | 改行为 |
| #8 | 新做看板标签页，读任务文件推断状态 | 6（新界面） | Claude Code | opus[1m] / high | 改行为 |
