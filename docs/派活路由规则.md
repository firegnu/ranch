# 派活路由规则

主控把一件活派出去之前，要定这几样：交给哪家 agent、用什么模型和强度、影响面多大、要不要交叉审查。本文把现行规则从头到尾讲一遍。

- **规则原文**在 corral-dispatch 技能 `crates/dispatch/resources/corral-dispatch/SKILL.md` 第 2、3、4、5、6、8 节。本文是对它的说明；两者对不上时以技能为准，并改本文。
- **版本**：R31 把分工搬到数据表，R34（2026-10-21）把默认分工改成「档位 × 类别」。使用新默认表须部署相应 ranch 并更新技能；之后只改本机表，下一次读取就生效。
- **来历**：现行分工见 `docs/任务/R34-在数据表上改分工.md` 的用户原话。路由与验证预算沿用 R12，来历见 `docs/任务/R12-派活规则和路由策略调整.md`。

## 1. 总流程

```
写任务书正文 ──► 问路由（Jev）──► 查分工表 ──► 定影响面和验证预算 ──► 补开头几行 ──► 派出去
 做什么/范围/      档、交叉审查、     交给哪家、      写进「怎么算做完」        交给谁、几档、
 不要做/验收       影响面           模型和强度                             路由行
```

1. **先写正文**：要做的、范围、不要做、验收。这几样和交给谁无关。
2. **再问路由**：从正文里提炼三五句摘要，交给 `ranch dispatch route`。路由只判三件事：难度、要不要交叉审查、影响面。**交给谁不由它判**。
3. **查分工表**（第 3 节）选格子，再调 `ranch dispatch cell <格子>`，定交给哪家、模型和强度。
4. **定影响面**（第 6 节），把验证预算写进「怎么算做完」。最后补上任务文件开头的「交给谁、几档」和路由那一行。打算交给 pi、omp 的，再看一遍正文是不是要写得更具体。

为什么先写正文：先问路由的话，路由说「轻」，正文就容易写得单薄。主控对照写好的正文，按第 4 节判档位和类别。

**谁先说了算**：用户点名、项目 AGENTS.md 的规定先于默认分工；第 5 节禁止的配置一律不开。主控只在用户明说或任务文件写了 `执行：主控` 时自己做。

## 2. 路由：`ranch dispatch route`

### 2.1 怎么问

```sh
echo "<摘要>" | ranch dispatch route
```

摘要用中文写就行，三五句，说清楚：做什么、改哪些目录、做错了会影响什么。**不写**私人数据，**不写**验收和打算怎么验证。摘要里一提测试矩阵、录屏，路由就会往重里判。

背后调用的是 TypeSafe System One API，模型是 **jev-1.14.0**（R12 从 1.13.0 升上来）。每次问同一组问题，问题和阈值沿用 Corral `6923da1` 的 route.py，没有改过：

| 问题 | 类型 | 问的是什么 |
|---|---|---|
| `tier` | 打分（三档） | 写代码的 agent 要多大的推理能力。轻：查东西、机械改动、照清单改文字或数据、跑命令汇报。常规：照清楚的任务书写功能、修一般的 bug，一个模块内的正常设计判断。重：设计数据模型、并发或事务、跨模块设计、难找的 bug、仔细审别人的代码 |
| `cross_data_model` | 是 / 否 | 改不改数据库表结构（只读写数据行不算） |
| `cross_concurrency` | 是 / 否 | 涉不涉及并发、后台任务、锁、重试、事务 |
| `cross_security_privacy` | 是 / 否 | 涉不涉及安全或隐私：权限、文件系统隔离、日志里的个人内容、把数据暴露给别人 |
| `cross_core_rules` | 是 / 否 | 改不改产品的核心规则 |
| `visible` | 是 / 否 | 是否只是呈现（布局、颜色、文字、文档）或只读研究，不加功能、不改输入处理和逻辑 |
| `doc_only` | 是 / 否 | 是否只产出方案、调研笔记或设计文档，不改程序代码 |

### 2.2 返回什么、怎么算

| 字段 | 怎么算出来 | 主控怎么用 |
|---|---|---|
| `tier.level` | 三档概率里最大的那档，**总有值** | **用这个**定难度 |
| `tier.confidence` | 模型给的置信度 | 写进路由行 |
| `tier.verdict` | 置信度 ≥ 0.8 时等于 `level`，否则是 `null` | **不用**。R12 的 30 条样本里，新旧两版都有 17 条是 `null`，用它就常常判不出 |
| `cross_review.verdict` | 四个 `cross_*` 里最大的概率 ≥ 0.8 是「要」，≤ 0.2 是「不要」，中间是 `null` | 交叉审查 |
| `impact.verdict` | 交叉审查是「要」→ 碰要害；否则 `visible` 和 `doc_only` 取大 ≥ 0.8 → 看得见；≤ 0.2 并且交叉审查是「不要」→ 改行为；其余是 `null` | 影响面 |

后两项是 `null` 时，主控按第 6 节自己判。

### 2.3 路由不可用时

- 退出码 0 并且 stdout 是 `"ok": true` 的 JSON，才算可用。要等命令结束、stdout 和 stderr 都收齐再判断。
- 其他情况都算不可用：档按「常规」算，另外两项主控自己判，照常派活。**不重试，不改用旧的 route.py，也不追问用户。**项目本来没有分派要求的，不会因为路由不可用就自动委派。
- 路由行里写不可用的原因：退出码 1 并且 stdout 是 `"ok": false` 的 JSON 时，照抄它的 `error`；其他情况（找不到 `ranch`、别的退出码、stdout 不是 JSON）只写「路由不可用，原因未知（退出码 N）」。
- 项目写了「不用路由」的，不调用。

### 2.4 推翻和记录

只有主控知道路由看不到的情况时（比如这件活返工过、审查时发现过问题），才推翻路由的结论，并写一句理由。

任务文件开头记一行：

```
路由：<档> / 交叉审查<要或不要> / 影响面：<档>（路由：<tier.level>（置信 <tier.confidence>）、<交叉审查结论>、<影响面结论>；推翻：<理由>）
```

括号里是路由原样给的结论：`null` 写「拿不准」，不可用写原因；没有推翻就不写「推翻」。

## 3. 交给哪家：按档位和类别读表

用户点名的照用户说的，其次照项目 AGENTS.md 的规定；未指定部分按下文补齐。其余先按第 4 节判档位、类别，再读对应格子。

| 档位 | 界面和设计 | 其余 |
|---|---|---|
| 低 | `low-design`：pi 或 omp，各自默认模型 | `low-other`：pi 或 omp，各自默认模型 |
| 中 | `middle-design`：Claude Code，`opus[1m]`，high | `middle-other`：Codex，`gpt-6-astra`，high |
| 高 | `high-design`：Claude Code，`opus[1m]`，xhigh | `high-other`：Codex，`gpt-6-astra`，xhigh |
| 碰要害 | `critical-design`：Claude Code，`opus[1m]`，xhigh | `critical-other`：Codex，`gpt-6-astra`，xhigh |

每次派活重新调 `ranch dispatch cell <格子>`；`cell.choices` 给可任选的家、完整 `command` / `argv`、`labels`，模型和强度在 `cell.model`、`cell.effort`。`cell.review` 给交叉审查格子的启动信息，`cell.rework` 给返工后升档的格子名或 `null`。只在退出码 0 且 `ok:true` 时使用；读表失败就报告并停下，不沿用旧参数。读到所需的 `choices` 为空时（包括审查、升档），停下告诉用户，不派。`ranch dispatch route` 不可用的兜底规则不适用于读表错误。

`ranch dispatch table` 列出全部生效格子和家模板。用户可在 `~/.ranch/dispatch.toml` 只写要改的字段，例如：

```toml
[cells.middle-other]
model = "用户选定的模型"
```

同名格子和家按字段覆盖，数组整项替换，其余继承内置表，也可加新格子。可选字符串设为 `""` 表示清除；不支持删除内置条目。每次读取都会重新加载并校验全表，格式错、未知键、未知引用或循环直接报错。`source` 显示 `builtin` / `user`，格子和所引用家分别标来源。完整格式见 [CONTRACT](CONTRACT.md) 的 R31 一节，默认数据在 `crates/dispatch/resources/dispatch.toml`。

R35 的 `table` 还返回每格的中文 `description`、每家的 `efforts` / `models` 可选项和本机文件版本 `local.version`。设置页通过 `ranch dispatch edit <格子>` 修改字段，通过 `ranch dispatch reset <格子>` 删除本机覆盖、恢复默认；写入带 `--if-version <读到的版本>`，文件已被别处修改时会报 `conflict`（退出码 3），须重读后处理。模型和强度清空时启动参数使用各家默认，`agents` 清空时没有可选家。命令参数、输出和错误见 [CONTRACT 的 R35 一节](CONTRACT.md#ranch-dispatch-edit--resetr35)。改表后下次读取立即生效，不需要重装技能。

### 3.1 点名或项目规定只定了一部分时，怎么补

指定了家，碰要害的活照样要交叉审查，验证预算照样按影响面定。只定了交给哪家、没定模型或强度时：

| 家 | 读哪一格补齐 |
|---|---|
| Claude Code | 同档「界面和设计」格；低档点名时读中档格 |
| Codex | 同档「其余」格；低档点名时读中档格 |
| pi、omp | 同类别低档格，选对应一家，用默认模型 |
| amp、agy | 读同名格子，用默认 |

明确指定的模型或强度按 `table` 返回的该家模板代入，同时更新命令和标签；只补没指定的部分，并遵守第 5 节的配置限制。pi、omp 两家同类，任选；一家手上有活就开另一家。amp、agy 仍只在用户或任务文件点名时派。

### 3.2 拆不拆、先给谁看

- 既要设计又要实现、又不是界面的活，拆成两步：先按「高／界面和设计」读表派人出方案，用户定（架构级的决定由用户拍板），再按档位和类别派人实现。新界面的设计和实现都按「界面和设计」读表。
- 新界面、或者没有现成示意的大改，派人实现之前先给用户看样子：一张文字线框或示意，用户选定了再派。规则明确的小调整（换个颜色、加一个提示）直接做。
- **一件活一个 agent、一个 worktree。** 新活不塞给已经开着的写代码 agent：它的工作目录钉在自己那个 worktree 上，换不了目录，也换不了模型和强度。同一个 agent 只在自己的 worktree 里接后续的返工和复核；升档时按第 8 节在同一 worktree 换新 agent。按当次档位和类别读表选家。

## 4. 怎么判档位和类别

档位从上往下，第一条命中的算数：

1. 要改代码，并且碰要害（路由的交叉审查是「要」，或主控判断碰了数据模型、并发和事务、安全和隐私、核心规则）→ 碰要害。
2. 要出方案、做取舍：架构、模块边界、新界面、新交互、跨模块；本轮只出设计 → 高。
3. 路由 `tier.level` 是「重」，或主控判断是跨好几个文件、原因不明的 bug → 高。
4. 路由 `tier.level` 是「轻」，并且不碰要害、改动点能一条条列出来、没有待定的设计问题 → 低。
5. 项目代码之外的杂活：本机清理、一次性脚本、核对数据、跑命令汇报 → 低。
6. 其余 → 中。

查事实、定位问题的调研按上表定档；涉及界面或产品取舍的调研算第 2 条。

类别：界面、设计（含涉及界面或产品取舍的调研）算「界面和设计」，其余算「其余」。

## 5. 模型、强度和启动命令

不带参数开出来的 agent，用的是它自己的全局默认，**不继承主控的模型和强度**。所以每次开 agent 都用读表返回的完整命令，并在任务文件和汇报里写明实际模型和强度。

- Claude Code、Codex 只用 high、xhigh；默认中档用 high，高和碰要害用 xhigh，交叉审查用 xhigh。
- 不用 `low` 强度标签；任务的「低档」用 pi、omp 默认模型，不带强度标签。看板使用 high、xhigh 标签。
- Claude Code 一律不用 `max` 强度和 `fable` 模型，Codex 一律不用 `ultra`；用户点名也先说明，不开。本机表覆盖也不绕过这条。
- pi、omp、amp、agy 用各自默认，不分强度，不带 `effort`、`model` 标签。
- 模型名会随版本变，过时了改本机数据表；下一次读表即生效，不编译、不重装技能。实际参数照读表，并遵守上面的配置限制。

| agent | 完整命令和标签来源 |
|---|---|
| Claude Code、Codex | 所选格子的 `choices` |
| pi、omp | 所选格子的 `choices` 中任选一家 |
| amp | `amp` 格（不能带 `--prompt`，等到 idle 后再用 `corral send` 送第一句） |
| agy | `agy` 格（要带 `--prompt`，不带 `--label`） |

拼接示意：先读 `middle-other`，把占位符换成选中项的返回值；每条标签各传一次 `--label`，空数组不带：

```sh
corral start demo/dev-backend --unique --cwd <worktree> --env CAIRN_DISABLE=1 \
  <读表 labels 对应的 --label 参数> \
  --prompt "先读 AGENTS.md，再读 <任务文件>，照做。命令都在前台跑完，全部做完后，回复最后一行写 DONE。" \
  -- <读表 command>
```

所有派出去的 agent 都带 `--env CAIRN_DISABLE=1`。Codex 的默认模板包含关闭会话记忆的参数，直接用完整命令，不另加分档参数。命令和标签从同一项读出，看板靠标签显示档位。

对 paddock：R34 的分工格子名全换，可选强度从三项减为 high、xhigh 两项；命令、JSON 结构、标签、退出码和状态目录不变。设置页按 `table` 返回的格子名和选项画，不硬编码旧名字。需一起更新 ranch 和技能；本机旧格覆盖不会自动迁移，旧强度覆盖可能不再通过校验，部署时需核对本机表。本轮不改用户配置。

## 6. 影响面：定验证预算

难度定模型和强度，影响面定验证，**两件事分开定**。

| 档 | 什么活 | 开发时的验证 | 审查 |
|---|---|---|---|
| **看得见** | 只影响显示、文档、文案、配色，或只读研究；做错了一眼看得出，随时能改回 | `git diff --check`，加一条能直接看出结果的检查；不要求先写失败测试 | 主控看 diff，不重跑测试套件 |
| **改行为** | 写功能、修 bug，不碰下一档 | 一条针对这件活的测试（修 bug 先写测试，确认它因为这个 bug 失败），加上项目的标准测试跑一次 | 主控看 diff，重跑一次标准测试 |
| **碰要害** | 数据模型和迁移、并发和事务、安全和隐私、核心规则 | 上一档的全部，再加边角用例。覆盖矩阵、植入缺陷自检只有这一档可以要 | 同上，再加交叉审查 |

- 照路由的 `impact.verdict` 定。它是 `null` 时主控按上表判；拿不准就定「改行为」，不往重的一头靠。
- **本轮不改代码的调研、设计，一律算「看得见」，不交叉审查**，不管路由说什么。原因是路由一看到摘要里提安全、并发，就会判成碰要害。R12 样本 #10（只读调研截图失败的原因）在 1.14.0 下就被判成了碰要害，正好由这条兜住。
- 录屏、真实终端录制、在真浏览器里走一遍，哪一档都不是默认。用户要求了，或者验收除此之外确实查不了，才写进任务书；集成验收只走主路径一遍。
- 预算照档执行，不往上加。通过了的验证，相关代码没再改就不重复跑。觉得还要多验，先报告原因，不自己扩大预算。返工只跑针对这次修正的检查和直接相关的回归。

## 7. 交叉审查

只给影响面是「**碰要害**」的活，也就是路由的交叉审查是「要」，或者主控判定碰了数据模型、并发和事务、安全和隐私、核心规则。看得见、改行为的活不做，本轮不改代码的调研、设计也不做。

- 默认只有碰要害两格配置交叉审查：`critical-design` → `review-codex`（`gpt-6-astra` xhigh），`critical-other` → `review-claude`（`opus[1m]` xhigh）。重新读原任务所选格子的 `review.choices`，用返回的完整命令和标签，另开一个审查者，只给它任务文件和 diff。
- 交叉审查换一家：Claude Code 写的交 Codex，Codex 写的交 Claude Code。用户、项目指定或本机覆盖改变了开发者，或原格没配审查时，按实际开发者读对应的审查格；所需 `choices` 为空就停下告诉用户、不派。
- 审查者在自己的 detached worktree 里只读：不改、不提交、不切分支。意见写进主仓库的审查文件。
- 「**必须改**」只给两种情况：任务书「怎么算做完」没达到；碰到的要害上有真实缺陷（会丢数据、并发出错、泄露或越权、核心规则算错）。其余一律「建议改」。只有「必须改」挡合并。
- 改完由同一个审查者复核，复核前先把它的 worktree 切到新提交。**复核两轮还没到「可以合并」，停下来问用户。**

## 8. 审查、返工和「结果」行

### 8.1 agent 有问题时，由主控回答（R36）

- 任务书模板要求：碰到要拿主意的事，agent 停下来，在回复里写清问题、可选办法和自己的建议，然后结束这一轮，等主控回复再接着做；不在自己的窗口里问用户，不开着命令等，不自己换别的办法。主控的决定写进「完成记录」；「做完」一节的 DONE 约定不变。
- 开完后的前台 wait 已停，或收到提醒时，都按派活技能第 5 节查状态和回复。对方仍在、没写 DONE、回复里在问要拿主意的事，由主控照技能第 8 节自己定，但**以用户的回答为准**（R37）。送决定前再运行一次 `corral status <名字>`：`last_human_input` 晚于这次停下的 `state_started`，或 `state` 又是 `working`，就当成用户已经在回答，主控不送，只按 corral 技能「长任务」一节重挂提醒（Claude Code 连后台 wait 一起），告诉用户 agent 问了什么、主控原本打算怎么定。否则用 `corral send` 回决定，带上「命令都在前台跑完，全部做完后，回复最后一行写 DONE」；报 `not_idle` 或 `human_active` 时同样不送、不加 `--force`，重挂提醒，告诉用户 agent 问了什么、主控原本打算怎么定。送成功后重挂提醒，事后在对话里告诉用户定了什么、为什么，决定也记进这件活的「主控审查」。下面先问用户的情况、请用户 attach 的对话框照旧，不受这三条影响。
- 只有两种情况先问用户：技能第 8 节列的隐私、花钱、改用户批准过的设计、删除东西、推送、关掉 agent（合并后清 worktree 和分支、同时关掉住在其中且自己开的 agent，仍按第 7 节的例外；按技能第 5 节升档时，原开发 agent 的完成记录先留在任务文件，再关闭，不用问用户）；或主控真的拿不准，几个办法各有明显代价、又没有依据可选。问时带选项和主控的建议，用户定了再回给 agent、重挂提醒。
- 信任目录、登录，或 `blocked` 的权限框、提问框，需要人操作，主控替不了，仍请用户 `corral attach <名字>` 处理，并重挂提醒。其他空闲或 blocked、没写 DONE 且回复里没有上述问题的，也照旧请用户去看并重挂；又在干活的同样重挂。被打断仍告诉用户、不能当成做完；套墙且停了没写 DONE 时先查 `fence denials`；已退出或不在了但没写 DONE，告诉用户、不再挂提醒。

对 paddock：R36 只改技能文字，通用 corral 技能和使用说明各补一句派活场景由主控回答；R37 只补 corral-dispatch 技能和本节说明，沿用现有状态字段和发送保护；命令、JSON、退出码、状态目录和分工表不变，paddock 不用动。使用新规矩需更新已安装的技能，安装是单独的部署操作。

### 8.2 审查和返工

- 主控每件都审，按影响面那一档的预算审，核实对方说的，不自己再证一遍。
- 只有两种情况交回返工：「怎么算做完」有一条没达到；做了「不要做」里的事。罕见输入组合下才出错的，记「建议改」，告诉用户。
- 每档最多返工一次，交回原 agent；再不过，重新读当前格子，再按返回的 `rework` 读升档格子。默认低 → 中、中 → 高，类别不变。原 agent 的完成记录先留在任务文件，再关掉原开发 agent，不用问用户；新 agent 用升档格子的命令和标签，开在同一个 worktree、同一个分支，接着前一个的提交做。
- 高、碰要害默认没有升档格子；没有升档格子的返工一次再不过，停下问用户。读表程序只提供升档格子名，不自动执行。
- 主控审查结论的最后一行记结果，四选一：

  ```
  结果：一次过
  结果：返工 N 次
  结果：返工 N 次，升到 <档位>
  结果：最高档返工仍不达标，已停下问用户
  ```

  每件都记。N 是这件活累计返工次数，升过档的写最终档位。主控不自己按结果调规则；用户要复盘时，把各件的结果行按档位和家汇总成表给用户，由用户复盘。

## 10. R34 改了什么

- 分工改为四档 × 两类；低档交 pi、omp，中档起界面和设计交 Claude Code、其余交 Codex。路由判法不变。
- Claude Code、Codex 只用 high、xhigh，取消旧试用和定额汇总；最费的配置一律不开。
- 碰要害的交叉审查换一家；审查任务书写法、「必须改」的两种情况和最多两轮复核不变。
- 每档返工一次，再不过按表升档；高、碰要害没有升档格子，再不过问用户。
- 结果由用户复盘；主控应用户要求汇总，不自行调规则。
- 主控只在用户明说或任务文件写了 `执行：主控` 时自己做；读到空的可选家就停下告诉用户。
- 验证预算、任务书写法、R36／R37 的提问处理规矩不变。
